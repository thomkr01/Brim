# Brim Privacy Policy

Last updated: 2026-11-19

This policy explains what Brim ("the bot") stores, why, and how long it is kept. The bot is free and open source. Its code is at [github.com/thomkr01/Brim](https://github.com/thomkr01/Brim).

## What the bot receives from Discord

When the bot is in your server, Discord sends it the events it needs to do its job: member joins and leaves, role and channel changes, audit log entries, and messages in channels it can read. The bot reads message content so that automod and logging can work.

If you send the bot a direct message, it is treated as a ticket: the bot forwards it (with its files) to a staff-only ticket channel in the server you pick, and forwards staff replies back to you.

## What the bot stores

The bot keeps data in a PostgreSQL database. It stores:

| Data | Why | Kept for |
|---|---|---|
| **Server config** (automod settings, log channels, permit roles, limits). Every change is saved as a new version; the newest 200 versions per server are kept, and older ones are deleted. A server can also delete versions older than a number of days (off by default); the current version always stays. | To run the bot's features and to show config history on the dashboard. | As long as the server uses the bot: deleted 30 days after the bot is removed, or when the owner deletes it. |
| **Moderation cases** (action type, target and moderator user IDs, reason, points, expiry), their **proofs** (`case_proofs`: links and short texts staff add, the link of the mod log message that holds a proof file, who added each and when, and the name of the AI connection when the bot owner's AI client did it) and their **edit history** (`case_edits`: the old and new reason, open or closed, that a proof was removed and what kind it was, never its content, who changed it and when, with the same AI connection name). The old reasons in the history stay until the case is deleted. | Warnings, bans, and history for `/case` and warn thresholds; proof and history so staff can check and explain a punishment. | Until staff delete them or the server's own limit for cases (off by default), or deletion is requested. A case whose timed action still runs, and the server's newest case, stay. Proofs and history are deleted with their case; staff can remove one proof at any time. |
| **Verified proof** (in `case_proofs`: a copy of the punished member's own message, stored when Brim punishes by itself and makes a case for it (automod, the catch channel, a Discord AutoMod rule set to warn), when staff act on a report, or when a moderator punishes in a reply to that message: up to 1,000 characters of its text (for a report, its 300 character excerpt), the channel and message IDs, when it was sent (for a message Discord AutoMod blocked: when it was stored) and the names of its files, never the files). Every staff member with the Cases permit in that server can read it on the case page, whatever channel the message was in. | So staff can see what a punishment was for after the message is gone. | 1 year by default (each server sets its own limit, at least 30 days, or keeps them with the case); deleted with the case before that, and when the member's deletion is requested. |
| **Staff notes** (member and moderator user IDs, the note text, when it was written) and **note edit history** (old and new text, who edited it and when). | Private notes staff keep about members; the history shows every earlier version on the dashboard. | Until staff remove the note (its history goes with it), the server's own limit for notes (off by default), or deletion is requested. |
| **Moderator actions** (the staff member's and target's user IDs, the action type, where it was done: Brim, the Discord app, an appeal or the dashboard, the case number, and when). Includes bans, kicks and timeouts staff do in the Discord app, read from the server's audit log. | Moderator stats on the dashboard, so owners can see how active each staff member is. | 1 year, then removed automatically. |
| **Automod strike state** (user IDs, strike counts and timestamps). | Keeps repeat-offender penalties working across restarts. | Until deletion is requested. |
| **Quarantine and lockdown records** (saved role IDs, the channel overwrites a quarantine replaced, lock snapshots). | To restore roles and channel permissions when a quarantine or lock ends. | Removed when the quarantine or lock is released. |
| **Command rate-limit uses** (`command_uses`: the server ID, the staff member's user ID, the command and the time) and **heat panic** (`heat_panic`: the server ID, the user IDs heat panic acts on, and when it ends). | So a restart does not reset the command limits and an active heat panic. | 1 hour for command uses; heat panic until it ends. Removed automatically. |
| **Scheduled jobs** (for example, a timed ban or timeout). | To run them after a restart. | Removed when the job runs. |
| **Server layouts** (`server_layouts`: the roles, channels, permission overwrites and main server settings a Trusted Admin or owner saved as the server layout in Layout Guard, and the user ID of who saved each version). | So Layout Guard can show what changed in Discord after the layout was saved. | The newest 50 versions per server; an older one is deleted when a new one is saved. Removed with the server's data. |
| **Server backups** (roles, channels, permission overwrites, as JSON). | `/backup` and nuke recovery. | A new backup is taken every 3 hours. The newest 10 automatic backups per server are kept by default; the owner can set 1 to 50. A new automatic backup deletes the oldest past that number; a backup staff take by hand deletes none. Removed with the server's data. |
| **Server owners** (the server ID and the user ID of its Discord owner). | To see when a server gets a new owner, and so the Raider List counts one owner with many servers once. | Updated when the owner changes; removed with the server's data 30 days after the bot is removed. When the owner deletes the server's data from the dashboard, the row (server ID and owner ID) is written again at once, because the dashboard needs it to know the owner. |
| **Staff lists** (`extra_owners`, `trusted_admins` and `permit_members`: the server ID and the user IDs of Extra Owners, Trusted Admins and members given a permit by user ID, and who added a permit member and when). | So the bot knows who is staff and what each person may do. | Until staff remove the person or the person leaves the server; removed with the server's data. |
| **Sticky roles** (`member_roles`: the server ID, the member's user ID, their role IDs, when they joined and left). | Gives a member who leaves and rejoins their safe roles back (Sticky roles, off by default). | 30 days after the member leaves, or at once when the setting is turned off. |
| **Names and avatars** (`profile_snapshot`: the server ID, the member's user ID, their last seen username, display name and avatar hash, never the picture itself, and when the member was last seen). | Discord tells a bot only the new name or avatar, so the avatar and name change logs need the last seen one to show what changed. Stored for every member of a server, but only while that server sends one of these two logs to a channel: at a join, at a change, and when Brim reads the server's member list (once a day and after a restart). | Deleted when the member leaves the server (a leave Brim missed is caught at the next daily read), 90 days after the member was last seen (so also when the server turns the logs off), with your own delete request, and with the server's data. After a delete request it is stored again within a day in a server where you are still a member and these logs are on. |
| **Reports** (`reports`: the server, channel and message IDs, the reporter's and the reported member's user IDs, the reason, the first 300 characters of the reported message, or of the message Discord AutoMod blocked, the status, the action, and who handled it and when) and the **report blacklist** (user IDs that may not report, and who added them). | So staff can review a report and act on it. | A handled report: 1 year by default (each server sets its own limit, at least 30 days, or keeps them). An open report stays until handled. The blacklist stays until staff remove the entry. Removed with the server's data. |
| **Appeals** (`appeals`: the server ID, your user ID and username, your answers to the appeal questions, the result, the reply staff wrote, who decided and when, and where the appeal was logged) and the **appeal blacklist** (user IDs that may not appeal, and who added them). | So staff can decide on a ban or timeout appeal, and you see the result. | A decided appeal: 1 year by default (each server sets its own limit, at least 30 days, or keeps them). An open appeal stays until decided. The appeal blacklist stays until staff remove the entry. Removed with the server's data. |
| **Raid log** (`raid_log`: the server ID, the user ID and username of each account in a join raid, the raid's code and the invite code they used). | So staff can see who joined in a raid and act on them later. | Deleted 30 days after the raid; the raid's public link stops working then too. Removed with the server's data before that. |
| **Lockdown updates** (`lock_updates`: the server ID, the staff member's user ID and the update text they posted during a lock). | To show the updates while the lock lasts. | Deleted when the last lock of the server ends. |
| **Verification time outs** (`verify_timeouts`: the server ID, the member's user ID and the time). | So 3 time outs in 24 hours give a 7-day ban, also after a restart. | 1 day, then removed automatically. |
| **Message Builder** (`embeds`, `message_sends`, `message_rules`, `sticky_msgs`, `message_runs`, `message_tag_runs`, `message_counts`, `message_new_channels`, `channel_drafts`, `media`, `message_webhooks`: saved messages and their text, who saved or sent each one, where it was posted, the member a message was sent to by DM, schedules, triggers and sticky messages and who made them, the member and message that set off a trigger and the word found, the member (id and username) who posted a message with /tag and where, channels and drafts staff made, uploaded webhook avatars and who added them, and the tokens of the bot's own webhooks). | So staff can save, post, schedule and edit messages, and edit what was posted. | Saved messages until staff delete them; the last 100 sends of each message; a trigger's member and message until the answer is sent; a /tag use for 1 hour (for the rate limits), deleted by the dashboard the next time it has nothing to send; an avatar no saved message uses, once it is older than 1 day, when that server next uploads an avatar or deletes a message. Removed with the server's data. |
| **Ban Sync records** (`ban_sync_links`: the server IDs, the banned user's ID, who banned and who moderated, the reason, the case numbers and when). Ban Sync was removed on 2026-11-13; nothing writes these any more. | Kept for one release, so a rollback to the older version still works. | Removed with the server's data; the table itself goes in a later update. |
| **Owner changes** (`owner_handovers`: the server ID, the previous and the new owner's user IDs, the user IDs of the Extra Owners, Trusted Admins and quarantine whitelist users the bot removed, the role IDs and names of the permits whose roles it paused, the names of the permits that stayed on, and when). | So the new owner can keep the previous owner's staff, one by one, after the bot removed them at the change, and so the dashboard can refuse the previous owner. | Replaced at the next owner change; removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Setup done** (`guild_setup_done`: the server ID, the user ID of who finished the setup, and when). | So the dashboard stops asking to run the setup wizard. | Removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Raider List entries** (`raiders`: the user's ID, the status, the category, whether the bot owner verified it, a public note of at most 200 characters, who reviewed it and when, and when a scam listing ends or the next appeal opens). | So servers that use the Raider List can act on confirmed raider accounts when they join. | Confirmed entries stay until the bot owner removes them; scam entries are removed 14 days after their last evidence. Removed and rejected entries are deleted after 30 days (a removed one once no server still has a list action to lift), and pending entries nobody reviewed after 90 days. |
| **Raider List evidence** (`raider_evidence`: the user's ID, the server and its owner's ID, what caught them, the case or incident number, counts and timestamps, and for a report the reporter's ID and the reporter's own note of at most 400 characters). Never message text. | So the bot owner can check an entry, and so one owner with many servers counts once. Only the bot owner sees it. | Deleted with its entry (see Raider List entries); kept while an entry is confirmed. Evidence that made no entry is deleted after 90 days. It is not removed with the reporting server's data, since the list is shared by all servers. |
| **Raider List reviews** (`raider_reviews`: who decided, the user's ID, the old and new status, the note and the time). | A record of every review decision. | Kept for good. |
| **Raider List appeals** (`raider_appeals`: the user's ID, their appeal text of at most 1,000 characters, the result, who decided and when). | So a listed user can ask to be taken off the list. | Kept with the entry's review history. |
| **Raider List actions** (`raider_actions`: the server ID, the user's ID, what the list did there and the case number). | So staff see the list's matches in their server, and a removal lifts only what the list did. | Removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Raider List exceptions** (`raider_allow`: the server ID, the user's ID, the staff member who let them in and when). | So the list never acts again on someone staff allowed in that server. | Removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **AutoMod rules changed without a permit** (`automod_rule_untrusted`: the server ID, the Discord AutoMod rule ID, the user ID of who changed it and when). | So Brim takes no action on a rule that someone without a permit created or changed, until a trusted staff member changes it. | Until a trusted change or the rule's deletion; removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Roles Discord hands out by itself** (`unpermittable_roles`: the server ID, role IDs of linked, server subscription, purchase and Onboarding roles, and whether the anti-nuke log already said a permit on one is ignored). | So no permit lookup gives a permit through a role anyone can get from Discord. | Replaced each time the bot or dashboard reads the roles from Discord; removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Approved AutoMod rules** (`automod_rule_approved`: the server ID, the Discord AutoMod rule ID, a hash of the rule's settings, the user ID of who approved it and when). | So Brim acts on a Discord AutoMod rule only while it is as a trusted staff member approved it. | Until the rule's deletion; removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Invite joins** (`invite_joins`: the server ID, the member's user ID, when they joined, the invite code and the inviter's user ID when known, how the join was matched, and why when it was not). | So Invite Tracking can count invites and staff can see how sure a match was. | 90 days, then removed automatically. |
| **Invite credits** (`invite_members`: the server ID, the member's and the inviter's user IDs, the code of their first join, how it was matched, whether it counts, whether they are still in the server, when they first and last joined and left, and how often they joined). | `/invites` counts, the leaderboard and `/invites who`. | While the bot is in the server; removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Invite links made by Brim** (`invite_links`: the server ID, the code, the user ID of the member it counts for, the channel ID, the use limit, and when it was made, expires and was deleted). | So joins through a link from `/invites create` count for the member who made it, and for the link limits. | While the bot is in the server; removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Bot profile changes** (`bot_profile_ops`: the server ID, the user ID of the owner or Extra Owner who made the change, which field, set or reset, the nickname or bio text that was set, an image's SHA-256 (never the image), the outcome and when). | So owners see who changed Brim's profile in the server, and so one change runs at a time. | Removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. |
| **Bot status** (`bot_presence`: the status and activity text Brim shows, the user ID of the bot owner who set it and when). | So the bot shows the same status after a restart. | Until the bot owner changes it. |
| **Short-lived records** (`pending_confirms`: a Yes/No question's action with its target IDs; `command_uses` and `heat_panic` above). | So a Yes/No question still works after a restart. | Until it is answered; an expired one (more than 70 seconds old) is removed when the next question is asked. |
| **Join Gate records** (the punished user's ID, whether it is a bot and who added it, the filters that matched, the action, and Discord's error if it failed). | To show staff every Join Gate action on the dashboard. | 30 days, and at most the 1,000 newest per server. |
| **Anti-nuke action log** (`action_log`: the server ID, the user ID of who did the action, the action type, the target's ID, how to undo it, whether it was undone, and when). | So anti-nuke counts actions across a restart, and staff can undo them on the dashboard. | 90 days, then removed automatically. Brim's own quarantine records stay while that quarantine lasts. |
| **Nuke incident records** (who was quarantined and what was reverted). | Recovery history after an attack. | Until deletion is requested. |
| **Dashboard sessions** (your Discord user ID and username, your Discord OAuth access token, a CSRF token, and a step-up timestamp). | To keep you signed in to the dashboard. The OAuth token is stored encrypted. | 7 days from sign-in, or 24 hours after you last used the dashboard if that comes first; then removed automatically within an hour. |
| **Dashboard two-factor setup** (your user ID, the TOTP secret and, while a setup by DM code is not confirmed yet, that 6-digit code). | Optional second factor for dashboard changes. | Until you remove it or deletion is requested; an unconfirmed setup stays until you confirm or remove it. |
| **MCP and update records** (`mcp_tokens`: the name of each token and the bot owner's user ID who made it, stored as a hash; `mcp_writes`: each change an AI client proposed, with the token, server, action, target and outcome, the request itself removed once it no longer waits for a code; `update_runs`: who started each update and how it went). | An audit trail of what the AI connector and updates changed. | `mcp_tokens` and `update_runs` are kept for good. A server's `mcp_writes` are removed with the server's data: 30 days after the bot is removed, or when the owner deletes it. Only the bot owner sees them. |
| **AI read log** (`mcp_reads`: which MCP tool read a server's data, when, and which login: a dashboard token name or an OAuth login). | So the server's staff see on the History page when an AI client read their server. | 90 days, and removed with the server's data. |
| **Dashboard change log** (`dashboard_audit`: the server ID, the user ID of who changed something on the dashboard, the change line the config-changes log channel shows, the config version it saved, and when). | So a server keeps a record of its dashboard changes, also with no config-changes log channel. | 90 days, and removed with the server's data. |
| **Tickets** (server, ticket number, channel, your user ID, open and close times, who closed it, the panel it came from, who claimed it, its priority, the time of its last message and of the first staff answer, and which staff member opened, claimed, noted or closed it and when, never what was written), where its closed log file is, and which staff member published a ticket panel and your ticket preferences (whether to confirm before sending, the server your last ticket message went to). | To route ticket messages between you and the server's staff. | A closed ticket: 1 year by default (each server sets its own limit, at least 30 days, or keeps them); the server's newest ticket stays so its number is not given again. Your ticket preferences: until deletion is requested. |
| **NSFW image scans** (`nsfw_scans`: for an image found NSFW, the server, channel, message and user IDs, a SHA-256 hash of the image, never the image or its link, the model's scores and staff feedback; for a clean image only its hash and the threshold it was clean at, nothing about who posted it). | So the scan acts once per image, staff can mark a wrong hit, and a clean image is not scored again. Images are only held in memory while they are scored. | 30 days. A row staff marked "Not NSFW" is kept until the server is removed, since it is the server's allow for that image. |
| **Web verification address hashes** (`verify_ips`: the server ID, a keyed hash of the IP address, never the address itself, the user's ID and the time). The key is made when the dashboard starts and is held only in its memory, so the hash cannot be turned back into an address, also not from a database copy. | To warn staff in a private log channel when several accounts verify from the same address within a day. The VPN block compares the address with downloaded lists in memory and stores nothing. | 1 day. |
| **Rescue keys** (a hash of the key, not the key itself, and the secret of the key's authenticator, encrypted with the key, so it cannot be read without the key; an older key holds that secret in plain text until the owner makes a new key). | Lets a server owner reclaim bot ownership if they lose their Discord account. | Until the key is used, the owner makes a new key, or deletion is requested. Removed with the server's data. When the server changes owner, a key made before the change keeps working for 7 days (no new key can be made in that time) and then stops working; it is deleted when the new owner makes a new key or at the next owner change. |
| **Rescue claims** (`rescue_owners`: the server ID, the user ID of the account that used the rescue key, the user ID of the server owner account at that time, and when). | That account holds Brim's owner level in the server instead of the owner account. | Until that account gives it back or Discord ownership of the server moves to that account (a move to any other account keeps it), so a server data deletion, or the purge after Brim left the server, keeps it: otherwise the owner account would get the bot back. One row per server. |
| **Data requests** (`data_requests`: your user ID and username, whether you asked to see or delete your data, the answer, who answered and when, and how many rows were found per table, never their content). | So the bot owner can answer your request and keep a record of it. | 1 year after the request, then removed automatically. |
| **Logs** (the bot's and the dashboard's log files: user IDs and usernames, server, channel and role IDs, what the bot did and the errors it got, and the dashboard request lines without their query text). | To find and fix faults. | The log files: 24 hours, then deleted automatically. The container log (the same lines, kept by Docker) holds up to 30 MB per service, so it can reach further back or less far. The bot owner's AI client (see Optional services) reads them with secrets, login codes and session IDs masked. |

When a server logs message edits and deletions, the old text of an edited or deleted message is posted in that server's private log channel (a bulk delete as a text file). A case's reason (also the old one when it is edited) and a proof staff add are posted in the server's mod log channel; a verified proof is not. These copies, like ticket files, are on Discord under the server's staff control: Brim does not delete them, also not when the server's data or yours is deleted.

Message content is not written to the database, except: the first 300 characters of a reported message (Reports), the punished member's message kept as verified proof of a case (Verified proof), what you write in an appeal, lockdown updates staff post, a reporter's note to the Raider List, and the text of messages staff save in the Message Builder. When staff close a ticket, the conversation is posted as a text file in the server's private ticket log channel on Discord, where it stays until staff delete it. In servers that log message edits or deletions, the bot keeps a short-term in-memory cache of recent messages (up to 50,000 messages per server, for 24 hours, then discarded) so it can log them. This cache is lost when the bot restarts.

The bot does not sell data, show ads, or send data to third parties beyond Discord and the hosting provider that runs the bot, and the optional services below. The dashboard's fonts are served by the dashboard itself.

### Optional services the operator can switch on

- **Cloudflare Tunnel**: when the dashboard or the MCP server is reached through it, all their traffic, including your IP address and browser details, passes through Cloudflare, which processes it for the operator. The dashboard sends Cloudflare nothing more.
- **Cloudflare Turnstile**: when web verification uses it, Cloudflare's captcha on the verification page sees your IP address and browser, like on any site that uses it.
- **AI connector (MCP server)**: the bot owner can let an AI client read the bot's data: server config, cases (with reasons and the proof staff added, not the copies of members' messages), staff notes, logs from the last 24 hours (member IDs and names masked), raid and join gate logs, appeals and reports (without message text or answers), and more, but not NSFW scans. Each read of a server is listed for its staff on the dashboard History page. What the AI client reads goes to the AI provider whose client the bot owner connects. The bot owner chooses that provider, and its own terms and privacy policy apply.
- **Off-site database backups**: the operator can upload a full copy of the database every day to a cloud storage provider (Backblaze B2). Each copy is encrypted on the server before it leaves, with a key the provider never gets. The copies hold everything above, are kept 7 days on the server (not encrypted there) and 30 days at the provider (deleted there the day after), where nobody can delete them earlier, so they are not deleted early when a server's data is deleted. If a copy is ever restored, deleted servers and removed staff grants are deleted again (see Deleting data).

## Why the bot stores it

Only to run the features you turn on: moderation, logging, automod, anti-nuke, backups, and the dashboard. The bot does not use this data for profiling or advertising.

## Who can see the data

- Server staff see moderation data for their server through Discord and, if they sign in, the dashboard. Staff only see what their permits allow; Discord permissions give no access.
- The bot's operator can access the database to run and maintain the bot.

## Deleting data

- **Delete it from the dashboard.** A server owner can delete all of the server's stored data under Miscellaneous > Delete server data. This needs the authenticator code and the server's name typed in, and it cannot be undone. The bot stays in the server and goes back to its default settings.
- **Remove the bot from your server.** This stops new data collection. All of the server's stored data is deleted automatically 30 days after the bot is removed, unless the bot is added back before then.
- **See or delete your own data.** DM Brim `/mydata show` to get a file with what it stores about you (staff members' and reporters' IDs, report reasons, the text of staff notes, and the proofs and edit history of your cases left out), or `/mydata delete` to have it deleted. The bot owner checks each request on the dashboard first. A delete removes what Brim stores about you as a member in every server: cases with their proofs and edit history, notes, reports, appeals, closed tickets, strike state, moderator actions done to you, invite, verification, join gate and raid records, NSFW scans, your stored name and avatar and your dashboard login, and your ID in older config versions. A report or appeal staff have not handled yet and an open ticket stay until staff handle or close them, and are deleted about an hour after that. A warning that still counts (a warning ends after one month, or earlier when staff remove it or a warn threshold clears it) stays with your ID until it ends, so a delete request does not clear it. About an hour after it ends it is deleted, or loses your ID and its reason if it is the server's newest case. A server's newest case and ticket stay without your name, reason, proofs and history, so their numbers are not reused. Kept: Raider List entries (they have their own appeal on the dashboard), appeal and report blacklists, staff lists (a server's owner changes them), your dashboard 2FA and a running quarantine. What you did as staff is not part of it. You get a DM when it is done. Log files are deleted after 24 hours anyway.
- We aim to complete deletion requests within 30 days.
- Backups for a server (the `/backup` copies of roles and channels) are deleted with that server's data. Full database copies (see Optional services) are deleted only when they expire, after at most 31 days. If one is restored, a server deleted after the copy was made is deleted again, and Extra Owners, Trusted Admins, permits, permit holders and Raider List allows removed, rescue keys replaced, dashboard 2FA reset and MCP tokens revoked after it are removed again. For this the bot keeps a deletion log (`erasure_log`: which table, and the server, user, permit or token IDs or the key hash of what was removed; no names or content) for 35 days. It is not removed with a server's data, since it must outlive the backups. A person's data deletion request carried out after a copy is carried out again after that copy is restored, so the log keeps that person's ID for those 35 days.

## Children

Discord requires users to be at least 13 (or the minimum age in your country). The bot does not knowingly collect data from anyone below that age beyond what Discord sends for server activity.

## Security

Data is stored in a private database. Dashboard sessions expire after 7 days, or after 24 hours without use. Dashboard changes are protected by CSRF checks and optional TOTP step-up. No system is perfectly secure. If you find a security problem, report it privately through the issues page by asking for a private channel.
