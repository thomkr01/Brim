# Pitfalls: Login, 2FA and MCP

Index and rules: [PITFALLS.md](../PITFALLS.md).

**A second code was free to guess, it shared the dashboard's lockout, and a cut-off change was stored as failed.**
After a right DM code, a wrong authenticator code put the MCP change back to pending without counting a try, so one DM code could be replayed with new authenticator guesses until the owner's 2FA locked, and that lockout was the one dashboard login uses: an AI client could lock the owner out of the dashboard. The change ran inside the request, so when the MCP server gave up after 30 s the handler could be cut off halfway, and the 15-minute sweep then wrote `failed` for a change that may have run; the AI saw "dashboard unreachable" and would propose it again. Each guard counted only the first factor, and the request that the client could drop wrote the outcome.
*Avoid:* every wrong code on a change counts a try, whichever factor (`reopen(true)` in `mcp::confirm`), and counts towards the token's 24-hour revoke; MCP authenticator misses have their own lockout in `TotpAttempts` (`mcp_fails`) with the replay guard shared; the change runs in its own task and writes its outcome there (not after awaiting the task in the dropped request); every status write after a claim needs `status = 'running'`; a cut-off or erroring run is `unknown`, and a confirm of a closed change says what became of it. `auth::attempt` has only these two callers; the bot's hourly sweep (`welcome.rs`) now writes `unknown` instead of `failed`. The DM names the server with its id first (`server_label`): a name is set by server staff and could copy another server's name and id; `plain` also strips control, bidi and zero-width characters.

**One fixed MCP token read and wrote everything, and the AI saw more than it needed.**
`MCP_TOKEN` in `.env` was shared by every AI client, could only be changed on the server, and its holder read every server with no trace staff could see; the OAuth login got the write tools too; the AI read NSFW scan rows and member ids and names in log lines. Access was granted per installation, not per client, and reads were not logged.
*Avoid:* every MCP login is a dashboard token (`tbmcp_`, checked by hash through `mcp_token_name`, revoked on the dashboard and refused at once) or an OAuth login that only reads (no write tools listed, a write call refused); writes forward the caller's own token, so the dashboard checks the same login. Each read of a server writes `mcp_reads` before the answer goes out; a read the log cannot record is refused. The MCP role writes only that insert, in an explicit `SET TRANSACTION READ WRITE` (its default is read-only); the grant names only `guild_id, tool, via` (with its own `id` or `at` it could block or bury the real rows); only tools that take a `guild_id` log it, and `jobs` without one logs every server it listed. `mcp_token_name` is SECURITY DEFINER with `public.mcp_tokens` and `pg_temp` last, so a temp table cannot shadow it; a token of the wrong shape is refused before any query. A Raider List verify acts like a confirm, so it alerts too. `redact` masks member ids and names and keeps server, channel, role and message ids. The owner gets a security alert DM (a queued `raider_notify` job, so it outlives an update's restart) on Raider List confirms, updates and token changes (owner decision).

**Three throwaway servers are three owners.**
Strong evidence from 3 different server owners listed a user by itself. Anyone can make 3 accounts, give each a new server and invite Brim, then get any user listed and banned in every server that enforces the list. Root cause: "different owners" was taken as "independent witnesses" without asking what an owner costs.
*Avoid:* evidence keeps its source server's member count and the time the bot joined it (`Detail.members`, `Detail.bot_joined`); only servers with `RAIDER_MIN_MEMBERS` members that had the bot for `RAIDER_MIN_DAYS` count; a bot account never lists by itself; an automatic listing only alerts until the bot owner verifies it (`UNVERIFIED_ALERT_ONLY`). One owner's raid or spam detection makes no entry until a second owner flagged the user. One person can still own three qualifying servers, so `RAIDER_AUTO_OWNERS` is 5. Other source counts are fine: Ban Sync counts the users a source shares (a rate limit, not a vote), and the dashboard's owner counts only sort the review queue.

**A member without a permit could make the bot search for and answer hundreds of names.**
`commands::run` looked up each name and replied per miss before any permit check, and automod waits for that loop. *Avoid:* check the invoker's permit perm before any lookup, look up at most `MAX_NAMES` (10) names, give the missed names one reply.

**MCP `logs_tail` filtered before it masked, and read whole files.**
`contains` matched the raw line and `redact` ran after, so `contains: "postgres://user:a"` revealed a masked password one character at a time. Each hourly file was read whole. *Avoid:* mask first, then filter (`tools::tail`); read at most the last 64 MB of a file (`read_end`) and say in the answer that older lines were not read. That notice is a line too, so the stop test is `>= n` plus a truncate.

**A URL checked by prefix lets look-alike hosts through.**
MCP OAuth registration took any `https://` redirect and checked localhost with `starts_with("http://localhost")`, which `http://localhost.evil.com` passes. A stranger could register their site, send the owner a login link and get a token for everything the MCP reads. *Avoid:* parse the URL (`reqwest::Url`) and compare scheme and host exactly against an allow list. OAuth redirects go only to the exact callbacks in `MCP_OAUTH_REDIRECTS` or the owner's own computer.

**A refresh token that issues a fresh one with a full lifetime never expires.**
Each MCP refresh gave a new 30-day refresh token, so a stolen one could be renewed forever (only rotating `MCP_OAUTH_SECRET` stopped it). *Avoid:* carry the login time (`auth`) through every refresh and cap the new token at login time plus the limit.

**Any role could switch the erasure log off for its own deletes.**
`note_erasure` and `log_erasure` skipped logging whenever the setting `brim.erasing` (before: `tommybot.erasing`) was `on`, and any session may set a custom setting, so the dashboard's role could `SET LOCAL brim.erasing = on` and delete Extra Owners, permits, a rescue key or 2FA without a log line; a later restore brought them back. Root cause: a setting says nothing about who set it. *Avoid:* a skip that only the owner may grant needs a proof only the owner can write. Migration 4056: `purge_guild` and `restore_erasures` call `brim_owner.erasing_on`, which writes the transaction id (and its start time, so a row restored from another database cannot match) into `brim_owner.erasing`, a schema no other role may use (not `public`: an older image grants every table there again); `brim_owner.erasing(guild)` checks flag AND row, and the row names the purged server (NULL only for a restore): the dashboard may call `purge_guild` itself, and the log triggers are deferred to commit, so a purge of an unused server id in the same transaction would otherwise hide its other deletes. Postgres 16 already refuses a non-superuser role to keep the flag as its own `ALTER ROLE ... SET` default, but a role can keep other defaults (the MCP role could turn its read-only default off): `db::set_dashboard_role` and `set_mcp_password` clear them (`RESET ALL`, also per database) at every start. No other function reads a session setting for a decision.

**One dashboard 2FA step-up unlocked the 2FA-gated actions in every server.**
`dash_session.step_up_until` had no server, so `require(.., true)` and the bot's `fresh_2fa` (whitelist save, adding a Trusted Admin, main roles, backup clear, delete and load) took a step-up done anywhere. *Avoid:* the step-up stores its server (`step_up_guild`, migration 4012). The prompt sends the server of the page it opened on. `Sess::stepped_up_for(guild)` and `fresh_2fa(app, user, gid)` accept it there only. `/api/me` returns `step_up_guild` for pages that check first (`stepped_up_here`). Account pages (profile, update, MCP tokens, Raider List review) keep `stepped_up`. An MCP confirm's code counts for the change's server. Test fixtures that set `step_up_until` also set `step_up_guild`.

**A Trusted Admin could hand a permit role with the anti-nuke or quarantine whitelist (or View Mod Stats) to an alt in Discord.**
In a server whose permits are not listed by member, `guard_permit_roles` let every immune actor through, while the dashboard's `keep_exemptions` kept those permits Owner/EO only. *Avoid:* the bot twin asks the actor's level. Owner and Extra Owner pass. A Trusted Admin's grant of such a role (`owner_only_roles`) is taken back and logged, nobody punished. This includes roles with dangerous permissions, which `guard_perms` spares for a Trusted Admin. A bot path is never weaker than its dashboard twin.

**A Trusted Admin could give the quarantine role itself dangerous permissions or a channel override.**
This reached every quarantined member, staff too, around the staff release rule. *Avoid:* `guard_perms` asks for Owner or Extra Owner when the role (or role override) is the quarantine role. A Trusted Admin's change is undone and logged, never punished.

**The rescue authenticator secret sat in plain text next to the key's hash.**
A database read alone gave the second factor of a rescue claim. *Avoid:* a secret that only the key holder needs is sealed with the key (`ops::seal`, opened at claim time). The row keeps only the hash. Older rows stay plain until the owner makes a new key.

**Log lines served to the AI connector kept login codes, state and session ids.**
Request spans logged the full URI, so `/auth/callback?code=...&state=...` and member search text went into the files `logs_tail` reads. `redact` masked only tokens and URLs. *Avoid:* request spans log the path, never the query. A new secret kind that can reach a log line gets a pattern in `mcp::tools::SECRETS` and a case in `masks_secrets`.

**A rescue claim from outside the server used up the key for nothing.**
The claim made the claimer an Extra Owner, which `api::level_of` counts only for a member. Owner rule: a lost account must be recoverable from a new account that nobody let in, so there is no member rule, and the claim moves the Owner level itself (next entry). *Avoid:* a grant that only counts under a condition is checked against that condition before anything single-use is spent. Here the grant (bot owner) has no member condition, and `let_in` unbans the account and makes a one-use invite.

**Owner level came from Discord ownership alone, so a lost owner account could not be replaced.**
A rescue claim moves Brim's Owner level. `rescue_owners` (migration 4048) names the claimer and the Discord owner at claim time. `permits::bot_owner` gives the Owner level to the claimer. The Discord owner account is paused until the claimer gives it back (`rescue_give_back`). The claim moves with Discord ownership (`on_owner` updates `discord_owner`) and ends only on a give-back or when ownership lands on the claimer (a sale needs a give-back first). Ending it when Discord ownership moved was wrong: a thief holding the old account handed the server to an alt and had the bot back at once. *Avoid:* never decide trust from `GuildInfo::owner` or Discord's `owner_id` directly. Levels go through `permits::resolve`; `level_members`/`member_roles`/`unentitled_roles` map in SQL; the bot uses `App::bot_owner` (owner's DMs, owner skips); the dashboard uses `api::bot_owner`/`owner_state`. Discord facts (the owner cannot be acted on, has every permission: `target_above_bot`, `can_invite`, the rank in `hierarchy`) keep the Discord owner. `guild_owners` holds the bot owner, so a claim and a give-back reach `on_owner` (queued `owner_check`) as a handover: the previous holder's Extra Owners, Trusted Admins and strong permits are paused, with Keep on Overview. A server without Brim answers like a wrong key and is not counted; code tries count on the key row only. The column is `server_id`, so `purge_guild` keeps the row and cannot give the bot back. `on_owner` appends the previous lists when the bot goes back to the owner the last change paused (else a give-back right after a claim loses the paused owner's Extra Owners). `owner_check` inserts skip only a job that is not leased: a running one may have read the state before the claim. shortcut: the erasure log does not record a give-back, so a database restore from before it brings the claim back; add `rescue_owners` to migration 4035's lists (and `restore_erasures`) if that matters.

**A rescue code checked without using up the key could be replayed.**
The rescue claim needs no replay guard because a right code deletes the key. The Secure my account press checks the same key and code but keeps the key, so the same code worked again within its 30 s (and in a claim). *Avoid:* any second use of a secret that is not used up stores the last code step in the write itself (`rescue_key.last_step`, migration 4050, `where last_step is null or last_step < $step`). Every path that checks the code (claim and press) refuses a step at or below it and counts it as a wrong code on the shared `code_fails`. The press also refuses a key made before the server's last change of owner, even inside the 7 days a claim allows. The press has its own limit (`PRESSES`): counting presses in the claim's per-user limit let whoever held only the Discord account (a claim needs no step-up) send 6 claims every 10 minutes and keep the owner's button refused. A new Rescue Key clears `last_step`. The alert's link is checked (https, parses, 512 characters at most), because Discord refuses the whole DM for a bad button link and the bot does not retry a 4xx.

**The rescue key outlived an ownership change for good.**
`claim_key` never looked at `owner_handovers`, so a previous owner could claim their key and become Extra Owner in the new owner's server at any time. A fix keyed on the one `owner_handovers` row per guild was wrong: its `at` moves on every change, so a second change brought an expired key back or gave an old key 7 more days. *Avoid:* a key made before the last handover (`owner_handovers.at > rescue_key.created_at`) works for `RESCUE_GRACE_DAYS` (7) and is then refused (`permits::rescue_expired_sql`, built from the constant; one SQL for the claim, the prompt and the bot's job). `on_owner` deletes, in its transaction, a key made before the previous handover, so only the handing-over owner's key gets the 7 days, once, and sets `at = clock_timestamp` after the config lock. `rescue_regenerate` checks the owner and the 7 days and inserts under the same lock, and refuses inside the 7 days with the date. Then the physical owner gets a full-page prompt (`page_access` `rescue_prompt`, `RescuePrompt`; a new key refetches the access) and a DM from the `rescue_expired` job that `on_owner` queues. Test claim, prompt and regenerate inside and after the 7 days, a key made after the handover, and a second handover (bot `a_second_owner_change_...`). No migration.

**Login and captcha failures showed raw JSON or "internal error".**
A cancel on Discord's consent screen (no `code`), a second login tab (state mismatch) and a reused code answered with a deserializer message, JSON or a 500. A Turnstile outage showed "internal error". *Avoid:* `auth::callback` answers these with a short page and a login link (`login_failed`). `verify::turnstile_ok` maps a send or parse failure to "The captcha check could not be reached".

**Auto Setup stays at Trusted Admin level.**
It sets `antinuke.quarantine_role`, and `lockdown.main_roles` while Monitor Public Roles is on, which Save puts behind the Owner bar. This is on purpose (owner rule: "if Auto Setup may do it, a Trusted Admin may"). *Avoid:* do not raise Auto Setup or its score fixes to Owner without asking the owner.

**Dashboard lock buttons skipped the lock permits.**
Lock, unlock and lock update on the dashboard needed only Editor, so a member could lock a server type or lift a lock that chat would refuse them, also during panic mode's mod command lock. *Avoid:* below Trusted Admin, `may_lock` asks the same permits as chat (`lockdown` or `lock_updates`, plus `missing` for each kind, shared in `automod::lockdown`) and refuses while `mod_lock` is on. The per-permit command rate limit of `gated` is not mirrored (no dashboard rate limits yet).

**A refused Discord login token gave a 500.**
When Discord refused a session's OAuth token (authorization removed, or token expired), `/api/guilds` and the verify page's submit answered 500 "internal error", and the dashboard showed "Could not load servers" with no way back except logging out by hand. `Discord::user_guilds` turned every HTTP error into the generic internal error. *Avoid:* every call that uses the session's own token goes through `auth::user_guilds`, which deletes the session and answers 401 on a Discord 401. The UI and the verify page send a 401 to `/auth/login`.

- **The 2FA check ran before the DM code.** `confirm` checked the TOTP code first, so anyone holding an MCP token could send wrong TOTP codes and lock the owner out of dashboard 2FA for 10 minutes. *Avoid:* when a request carries several secrets, check the one the caller must already hold (the DM code) first, and touch shared lockout counters only after it passes.

- **An approval showed less than it approved.** The MCP code DM cut the change at 1500 characters, so the end of a long change was approved unseen. Same class: `embed_post`'s DM showed only `{repost}` and not the embed it posts; a rollback's preview diffed the permits copy in the last config version instead of the live tables (a rescue-claimed Extra Owner was removed without showing); the embed could be edited between the DM and the code; a `target` on an action without `{t}` in its path was never checked but went into the DM's inline code, so backticks and a fake block could reshape it. *Avoid:* an approval shows all of what runs or refuses (propose says "split it"). Drop input an action does not use before it reaches the approval. Preview what the action really reads (the stored embed, live permits). Store a hash of what was shown and refuse at confirm (`stale`) when a fresh preview differs (migration 3100 `preview_hash`).

- **A check before a slow call did not hold for the write after it.** 2FA enrollment checked "not confirmed", sent the DM, then upserted the secret with no condition. A confirm during the DM had its secret replaced while staying confirmed, so a stolen session could end up holding the owner's 2FA. Confirm had the mirror race: it marked confirmed whatever secret was stored by then. *Avoid:* put the precondition in the write itself (`do update ... where not confirmed`, `update ... where secret = <the one checked>`) and treat 0 rows as refused. (The rescue-key regenerate replaces on purpose.)

- **A host allow list let any page on that host catch an OAuth code.** MCP OAuth took any path on a known client host, and a client id signed under that rule stays valid for 10 years. *Avoid:* compare host and path exactly (`REDIRECTS`), no query or port, and check the redirect again at `/authorize`, not only at registration.

**Sessions, public links and the edge trusted too much.**
- A session lasted 7 days whether used or not, kept the same id through a 2FA step-up, and stored the Discord OAuth token as plain text. *Avoid:* `dash_session.last_seen_at` (migration 4032) ends a login after 24 hours without use (refreshed at most every 5 minutes). A step-up moves the session to a new id and leaves the old id 30 s without the step-up (`totp_verify`), so a copied cookie never gains it. The token is stored with `auth::seal_token` (key stream from the client secret and the session id). The cookie is always Secure: the dashboard refuses to start with an `http://` URL other than localhost.
- `CF-Connecting-IP` was believed from any sender: a container or a host process could pass web verification's alt-account and VPN checks with a made-up address. *Avoid:* `auth::edge_only` keeps the header only on a connection from the `cloudflared` container (DNS name, looked up again after 30 s). New dashboard code that needs the visitor's address reads that header after this layer. The MCP server reads it raw, for its login rate limit only.
- The rate limiter keyed only on the `sid` cookie, so no cookie or a random one per request was never limited. *Avoid:* every route also takes from a per-address bucket (4x the session budget), `brim_core::ratelimit`. The MCP login routes have their own (`limit_login`).
- Rescue claims: 5 per user in memory only, a key without an authenticator worked alone, and every failed claim posted a log line. *Avoid:* wrong codes count on the key row (10 an hour, then the key waits; a wrong key cannot raise it, so nobody without the key can lock the owner out; no per-server lockout, by owner rule). Keys without a secret are refused and the owner is asked for a new one. Failed claims post once per server per hour with the count of the hour before (`claim_failed`).
- Viewers read every holder of Extra Owner, Trusted Admin and each permit, also in history diffs, and could export it. *Avoid:* `api::hide_holders` on every route that returns permits to a Viewer (`get_config`, `diff_versions`). The Overview score leaves out the ownership-change rows for Viewers (they name paused and kept holders). Check any new route that names permit holders. Export is for Editor and up. Session and address buckets share one map, so their keys carry a prefix (`sid:`, `ip:`): a cookie `sid=ip:<address>` drained another address's bucket.
- The MCP login limit (first 20 at once) failed `crates/mcp/tests/oauth.rs`: test requests carry no `CF-Connecting-IP`, so they all share one bucket, and the local run's output filter hid the failure. *Avoid:* check a new limit on a route with tests against the number of requests those tests send. Read the whole `test result` list of every crate, not the first failure only.
- Raid links never expired and uploaded pictures were served by their hash from any server. *Avoid:* raid pages and `raid_log` rows end after 30 days (hourly sweep). A new upload gets a random link (`media.token`). Older uploads keep their hash link so posted messages keep their picture.

- **A security refusal went through a command frame a Trusted Admin may edit.** The backups command's owner-only, 2FA and "not while locked or in panic" refusals and the revert command's owner refusals were plain strings sent through `cmd.backups` / `cmd.revert`: `||{text}||` plus a fake Confirm 2FA link would hide the real refusal from the owner. Root cause: the frame decision looked only at `Said::edited`, not at whether the text is a security text, and the slash path framed every answer. *Avoid:* such refusals are Security entries (`botmsg::SECURITY_ERRORS`), and `reply::Said::security` (set from the entry's group) keeps them out of every `cmd.<command>` frame: prefix `commands::say_said`, slash `run`'s `frame` flag (`slash::unframed`), settings `send_said`. A command answer that must not be framed returns a `Said`, never a `String`. The load-while-locked refusal is also checked in `backup_cmd` (`reply.backups.locked_load`); `backup::load`'s own string is for its other callers. Still open (needs a decision): backups load/delete/clear results and permit and panic-lock refusals (`gated`) use the command frame; the held-staff release refusal goes through the moderation result entry; `t!tshoot lockdown` and Raider List report owner-only refusals are ordinary entries.

**The 2FA lockouts lived in memory.**
The 5 wrong codes in 10 minutes, the code replay guard, and the 5 tries in 10 minutes for a rescue claim and for Secure my account were kept in the dashboard process; a restart reset them and a just-used code worked again. *Avoid:* a security counter lives in the database: `dash_fails` (counted by `auth::tries` under an advisory lock, so parallel tries can not pass the limit) and `dash_totp.last_step` (migration 4058). Test: `totp_locks_after_five_misses_and_refuses_replay`.

**Logout left the `sid` cookie in the browser.**
`jar.remove(Cookie::from("sid"))` sends `sid=; Max-Age=0` with no path, so the browser applied it to `/auth` and kept the cookie set with `Path=/`. Same at the login callback for `oauth_state` and `login_next`, and at Secure my account. The session row was deleted, so no access remained. *Avoid:* a removal cookie must carry the same path as the cookie it removes: `jar.remove(auth::cookie(name, String::new(), st.secure))`, the same builder that set it; a test checks the `Set-Cookie` of a removal.

**A header was trusted behind any proxy.**
Web verification reads the visitor's IP from `CF-Connecting-IP`, which only Cloudflare's tunnel sets for us; behind another proxy, or with the port open, a visitor sends their own and skips the alt and VPN checks. *Avoid:* DEPLOY.md states that only Cloudflare Tunnel is supported for web verification. A new header-based check names the one deployment it trusts.

- **Two authenticator entries with one name.** The login 2FA and the rescue key QR both used the issuer "Brim", so the app showed two "Brim" entries; the owner typed the rescue code at step-up and got "code rejected" and then the lockout. *Avoid:* each secret a person scans gets its own issuer name ("Brim" and "Brim Rescue"), and the code prompt says which entry to use.

- **The landing page flashed after login, and some actions had to be pressed again after the 2FA code.** The web app drew the landing page while it still waited for `/api/me`. The 2FA prompt resumed an action by clicking its control again, which fails for a request sent after an await (Overview Fix all when the step-up ran out mid-run, config import) and for a control that closes or changes before the code (import Apply, Channel Setup push, Delete server data, Load backup, panic mode). *Avoid:* see `crates/dashboard/ui/PITFALLS.md` ("The landing page showed..." and "After the 2FA code..."): wait for `/api/me` before choosing a view, and use `run_resumable` for those requests.

- **A 2FA refusal showed a server state.** Pressing Verify in the "Confirm it's you" dialog before setting up an authenticator showed `totp not enrolled`; a wrong code showed `invalid code`; a second setup showed `totp already enrolled`. `ApiError::Forbidden` sends its text as is, and the dialog shows it word for word. *Avoid:* a refusal a person reads says what is wrong and what to do, in a sentence (`auth::WRONG_CODE`, `NOT_SET_UP`, `ALREADY_SET_UP`, `NOT_SET_UP_MCP`). Code that reacts to a refusal compares against the constant, never a copied string (`mcp.rs` counts a guess with `auth::WRONG_CODE`). Only the text changed: which codes pass and the lockout are the same. Checked: every `ApiError::Forbidden` in `auth.rs`, `mcp.rs`, `ops.rs` (the Rescue Key refusal "invalid rescue key or code" already says what is wrong and is kept, since `secure.rs` compares it).
