# Pitfalls: Messages: builder, previews and emoji

Index and rules: [PITFALLS.md](../PITFALLS.md).

- **`v["key"].as_array_mut` added `"key": null` to a body sent to Discord.** serde_json's `IndexMut` inserts a missing key as null, so filling variables in an embed without fields sent `"fields": null`. *Avoid:* read optional keys of JSON that leaves the process with `get_mut(..)`/`pointer_mut(..)`, never `v["key"]` on a `&mut`.

- **A value filled into a message pushed it past Discord's limits.** Variables and role mentions differ in length from their tokens, so a text that passed the save check could be refused at send time, and `{guild.icon}` with no icon was sent as an image link. *Avoid:* cut every filled text to its Discord limit after filling, cut member-chosen values to 100 characters, and leave out an image slot whose filled value is not an https link.

- **An edit in place sent the raw text.** The edit path of publish replaced the filled `content` with the saved text so it could clear old text, which posted `{guild.name}` as typed. *Avoid:* only default a missing key; never overwrite a filled body with the saved one.

- **Old copies answered from the newest version.** Menus on a copy posted before the Sent log (`mb:<embed>:<row>`) were answered from `embeds.published`, which every new Send overwrites. *Avoid:* a posted copy answers from its own stored body: by its send id, else by its Discord message id, and the newest version only when neither is stored.

- **One unreachable copy blocked the delete.** Delete removed up to 101 Discord copies inside an open transaction and stopped at the first 403, so earlier copies were gone, the message stayed, and every retry failed the same way. *Avoid:* commit the database change first, then remove the Discord side best effort and say what was left.

- **"Allow @everyone" let a filled-in name ping everyone.** `allowed_mentions.parse = ["everyone"]` applies to the text after variables are filled, so a server or display name containing "@everyone" pinged the whole server. *Avoid:* build pings only from what the author's own template contains; add "everyone" only when the template itself has @everyone or @here.

- **A picture showed in the preview but not in Discord.** The browser loads a link that Discord's image proxy cannot (a site that answers Discord's fetch with 403), so the preview looked right and Discord silently showed nothing. The preview also drew the thumbnail top left (a `float` inside a flex column), not top right. *Avoid:* after a send or edit, read Discord's answer: an image slot with width 0 was not loaded, so say which slot and why. The preview uses the same layout classes as the editor (`.embed.th` + `.thumbslot`), never its own copy.

- **A picture Discord showed was reported as not loaded.** Discord answers a send before its image proxy has fetched a link it has not seen, so the answer had width 0 and the Sent log said "Discord could not load the big image" while Discord showed it seconds later (bot and webhook alike). *Avoid:* width 0 in the first answer is "not yet", not "failed": read the message again (after 2 s, then 3 s) before warning; keep the first answer only when it cannot be read back.

- **Two first sends made two webhooks in one channel.** The webhook was looked up, then made, with no lock, so two sends at once each made one and the row kept only the last. *Avoid:* "find or make" of an outside resource runs under a lock on its key (here `pg_advisory_xact_lock` per channel), and the made-again path names the stale id so a racing caller reuses the fresh one.

- **A gone webhook looked like a gone message.** Discord answers 404 for both "Unknown Webhook" (10015) and "Unknown Message" (10008). Treating every 404 as "copy deleted" hid live copies from the Sent log, and Delete left them up. *Avoid:* read Discord's error `code`, not only the status; delete a copy as the bot when its webhook is gone, and keep a webhook while copies it posted are still up.

- **Webhook messages lost their buttons.** Discord ignores `components` on webhook execute and edit unless the request has `with_components=true`. *Avoid:* every webhook execute and edit path sends `with_components=true`.

- **Brim's own cleanups deleted its own Message Builder webhooks.** The webhook spam cleanup deletes webhooks made in the last 10 minutes, and a backup restore with "delete webhooks" deletes every webhook not in the image; both hit the Message Builder's webhooks, and nobody could edit the copies they posted. *Avoid:* a bulk delete of a Discord resource skips the ones Brim depends on (`msghooks::ours`). A restore that cannot read that list deletes none.

- **A record of "who did it" was lost to a race.** The dashboard marked copies as gone when Discord answered "Unknown Webhook" before the audit log entry came; the entry then found nothing to do and wrote no log. *Avoid:* when two paths can notice the same event, the later one fills in what it adds (here `hook_gone_by` and the log) instead of returning early on "already done".

- **The Sent log trim dropped answers still waiting to be deleted.** Keeping the last 100 copies removed rows whose `delete_at` was still ahead, so "delete after" never deleted those answers. *Avoid:* a row with pending work (`delete_at`) is never trimmed; trim only finished rows.

- **The webhook-deleted log gave one advice for every copy.** The "Message Builder Webhook Deleted" log said "send the message again, then delete the old copy in Discord" for all copies, but a sticky copy is replaced at its next repost and a trigger answer with a delete time is still deleted on time. *Avoid:* advice in a log or notice matches what happens to each kind of copy (kept, timed, sticky); check every source of `message_sends` when one text covers them all. A trigger answer whose timed delete failed was forgotten too: the claim clears `delete_at` first, so a failed delete writes a "delete it by hand" warning on its Sent log row. A sticky copy counts as sticky only while a sticky still holds it (`sticky_msgs.send_id`).

- **A rename of variables missed a check on the old name's prefix.** The Message Builder read the server from Discord only when a used variable began with `server.`; after `{server.name}` became `{guild.name}`, no send filled it and members saw the raw text. *Avoid:* such a check is one function beside the names (`msgvars::needs_guild`), never a copied string; a rename greps for the old prefix as a string (`"server."`), not only the whole names. Variable names follow `botmsg::public_name` (Discord things keep Discord's API names, Brim's own are `function_name`); code passes values by code name, and `to_code`/`to_public` convert at the edge.

- **The code kept old Discord names behind a name map.** The first rename changed only the names members see: defaults still said `{server}`, code passed `("server", ..)`, and `public_name` mapped it to `{guild.name}`, so a reader took the old name for a missed rename. A hidden spot also matched the old name (the dashboard examples gave the real server name to `"server" | "name"`). *Avoid:* a Discord thing has Discord's name in the code too (`guild.name`, `channel.name`); only old copies on load are mapped (`OLD_DISCORD_NAMES`). A rename greps for the old name as a match arm or a list item (`"server" |`, `&["server"]`), not only as `{server}`.

- **A bot message copy could keep a Message Builder variable that it never fills.** `botmsg::unknown_vars` only counted `{a_z}` names, so a saved copy with `{guild.name}` or `{role:1}` passed the save check, and the member got the raw text: bot message templates fill only their own variables. *Avoid:* a check that refuses unknown variables reads every `{...}` name the senders could treat as a variable (letters, digits, `_`, `.`, `:`); a test holds one of each kind. A built-in message also cannot hold buttons (code adds them), an embed time or `<t:+N>` (only the Message Builder sender fills those): `dashboard/src/botmsgs.rs` `problem` refuses them.

- **A bot message copy with an empty footer or author made Discord refuse the whole message.** `botmsg::render` dropped an all-empty embed and an empty description, but kept `{"footer": {"text": ""}}` or an author with no name. Discord answers 400 and the DM or ticket message is lost; the ticket footer code also saw "a footer" and left out the server footer. *Avoid:* after filling, `render` removes every embed part whose text is empty (description, footer, author); `render` is the only place that fills these templates (test: `tickets::msgs::tests`).

- **A log group had one editable frame, so a server could not word one log type alone.** `log.<group>` framed every log of the group. Owner rule: one entry per log type, as for command replies. *Avoid:* a log type with a fixed title has its own entry `log.<group>.<title slug>` (`botmsg::LOG_TYPES`). `events::framed` takes the group key and finds the type by the embed's title: the type's saved copy wins, else the group's (`log.<group>`, where all older edits sit, so no migration), else the log as built. A log whose title holds a name or number stays on the group entry. A new log type is one title in `LOG_TYPES` (its group's list); a test checks the title is really sent (an audit title from its `LogEvent`, anything else as a literal in the source), so a typo cannot leave a dead entry. The group must be the kind the code sends that title with. Security groups (anti-nuke, panic, join raid) have no types, only the locked group entry. Kits and backups copy `bot_messages` by key and need no change. Callers of `framed`: `send`, `send_private`, `reports`.

- **A log built outside the logger skipped the event route and the ignore lists.** `events::send_log` looks the channel up by kind only (`target(kind, None)`) and never reads `ignored_users` or `ignored_roles`, so a log of an event (the timeout end) went to the kind's channel instead of the event's, and an ignored member was still logged. The dashboard cannot send a framed log at all (its `post_log` knows no Bot messages entries), so a dashboard log (case delete) would not be editable. *Avoid:* a bot log of one `LogEvent` goes through `events::send_event_log` (event route, custom types, ignore lists, frame); a dashboard or sweep log is queued as a job (`case_delete_log`, `old_cases_log`, like `case_log`) and sent by the bot with `send_log`. A new log type is one title in `botmsg::LOG_TYPES` that the code really sends (a test checks it); a new kind is also in `LOGS`, `LogKind::ignorable` (security-type kinds false) and the dashboard's `LOG_KINDS`. twilight reads only the audit change keys it knows, so AutoMod rule and app permission details arrive as `other` and the log says some settings are not shown. Check every `send_log*` caller and every `LogKind` match.

- **A noisy log type took the kind route or the general channel, so a vote or sign-up flooded a channel nobody chose for it.** `LogConfig::target` falls back from event to kind route to the general channel; that is wrong for poll votes and event sign-ups (one vote is one message), and Auto Setup gave every event the shared `discord-logs` channel. *Avoid:* list an event that must stay off until a person picks a channel in `LogEvent::quiet`, not in a `matches!` of its own; `target` then uses only its own event route or a custom type, Auto Setup (`sections::log_channels`) skips it, and the logger builds nothing for it without a route (`Logger::vote`, `Logger::signup`). Same package: (1) state that decides whether a gateway event is news (boost level, open threads, published messages, ended polls) lives in the `Logger`, in memory and bounded (`MAX_KEPT`, `MAX_THREADS`, `first_time`); the first sight of a guild only records it (`Logger::seed` at `GuildCreate`), so a restart logs nothing false. (2) A thread archive is held for `HOLD` and dropped when an audit `ThreadUpdate` for the same thread arrived within it; only an archive with no audit entry is Discord's own. (3) A stage audit entry's target is the stage instance, so `render::audit` leaves out the Target line and the Channel line names the stage. (4) An update of a message with no cached copy is never read as a publish (it would hide the edit log), so the cache also runs while only the publish log is on. (5) A bounded map evicts its oldest entry when full (a "stop inserting" cap leaves new scheduled events unnamed). Known limit: the new state events (boost level, thread open/archive) are applied after the config read, so two events of one thread or guild in the same instant can swap. (6) A poll's vote-count updates are never a "Message Edited" log; only the finalized one is, once. Check every `LogEvent::ALL` user (dashboard schema, Auto Setup, the botmsg title test), every `LogKind` match, `guild_of` in `events.rs`.

**A saved edit of a DM sent outside any server was never sent.** The raider notice DM was saved on the Bot messages page, but it is sent with no server, so the copy lookup read nothing and sent the default. The data request DM has the same path, but it is locked. *Avoid:* an entry sent outside a server is listed in `botmsg::BOT_WIDE`: its one copy is stored under guild 0 (`botmsg::copy_guild`), and only the bot owner may save it (`botmsgs::may_edit`). Every sender with no server reads that copy: `reply::dm_msg` with `None`, and `reply::frame_embeds` (async, takes the app). Callers: raider notices in `raiders/review.rs` and `raiders/tasks.rs`, data request in `datareq.rs`. Not live tested.

## The preview of a default message missed the buttons Brim adds
Default messages can carry buttons that code adds (`giveaway.running`, `ticket.confirm`, link buttons under logs). The editor and preview drew only the stored message. The bot now saves the real button rows with its samples (`previews.rs`, `added_buttons`, key to rows); `added_buttons_belong_to_real_messages` fails when a key is not a message. Label and emoji come from the same builders and constants the bot posts with (`enter_row`, `claim_row`, `link_row`, `GO_MESSAGE`, `GO_POLL`, `GO_CHANNEL`).
*Avoid:* a new button under a default message is added to that table in the same change. The preview must never show an example that the bot cannot post (a running giveaway shows a count of winners).

**A picture variable stayed as typed text in the link slot.** `fill_value` skips every `url` key, so only `fill_links` fills a link. *Avoid:* a new link variable (`{sponsor_picture}`, `{banner}`) goes in the `LINKS` list of `fill_links` in `botmsg.rs`, and its message key must be one that calls it (`feed.*` and `giveaway.*`). An empty or non-web value then drops the slot, so Discord never gets an empty link.

## Stock emoji in bot messages

**The "Ticket Closed" DM showed a stock mailbox next to Brim's own emojis.** The title used `TICKET_CLOSE`, but the first line had the Unicode `📪` typed in. A typed Unicode emoji never turns into a Brim emoji, so it shows the system look. The same was true for the first line of every punishment DM, the verify and appeal DMs, the verify panel and captcha titles, the join raid and voice raid log titles, the Bot check logs, the lockdown update lines, the note title, and the dashboard owner alerts (MCP token, Secure my account, update, "Not you?"). *Avoid:* a message Brim posts never has a typed emoji. Use a constant from `crates/logging/src/emoji.rs` (its fallback is the Unicode emoji, so tests and self-hosted bots still work) in a `format!` (`{{server}}` for a placeholder). The dashboard loads the ids too, so its owner alerts use the constants the same way. `emoji::fill` (`{e:name}` tags) drops an emoji that is not uploaded and has no fallback: use it only for server owners' own text. A new emoji needs its icon in `assets/icons` first. Left on purpose: the sample values in the editor variable lists, and test strings. The giveaway Enter default is the Brim ticket (`{e:giveaway_enter}`): a server owner's own button emoji stays, but the default is never a typed Unicode emoji.

## Emoji tags with underscores showed as italics in the preview
The CONGRATS word is eight tags in a row (`{e:congrats_1}{e:congrats_2}`). The dashboard preview read the underscores between two tags as an emphasis pair, so the word showed as raw text with slanted parts, because `md::inline` set emphasis before `icons::fill_tags` drew the tags. *Avoid:* `inline` keeps a `{e:name}` tag whole, like a code span. A name a default uses must also be in the `icons!` list in `icons.rs`, or the preview shows the tag as text. A default that opens a text with an emoji word has an empty first line when the emojis are not uploaded (`emoji::fill` drops the tags); Discord trims it.

## A fixed line in a default shows in every state of that message
The CONGRATS word was a fixed first line of the ended giveaway card, so a giveaway that nobody won said CONGRATS above "Result: Nobody". *Avoid:* a line that must not show in some state is a variable alone on its line (`{ga_congrats}`, code name `congrats`, passed by `giveaways.rs`), empty in that state; `fill_text` drops a line whose variables are all empty. When a default gets a celebratory or state-bound line, search for the same pattern: a state without that fact needs its own default or an empty variable.

## The test send of a default message posted raw emoji tags
"Send test to me" posted `{e:trophy}` and the CONGRATS tags as text in winners, reroll and every other message whose text sits above the embeds, because `fill_emoji` fills only the title, description, footer and fields of embeds. *Avoid:* the test send fills every text of the message with `fill_all` (all strings, like the bot's own `fill_tags`), so it matches the real post.
