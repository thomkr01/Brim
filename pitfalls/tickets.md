# Pitfalls: Tickets

Index and rules: [PITFALLS.md](../PITFALLS.md).

**Ticket commands skipped the gates every other command has.**
`tickets::on_message` runs before `commands::ignored`, and answered "no access" with no cooldown to quarantined members, in voice-channel chats and with "Ignore Permit 1 Commands" on. Its admin commands were listed as Manage Tickets in `t!commands`, `-h` and the dashboard, but need Owner, Extra Owner or Trusted Admin. Ticket DM and panel answers of Owner, EO and TA also went through the word and invite filters. *Avoid:* a command path of its own repeats `commands::ignored`, `ignore_no_permit` and `cooled_down`; the help table names the real bar (`"immune"` in `general::CMDS`, `access::command` on the dashboard) and the refusal names it too; a filter on member text skips immune levels (`dm::bypasses`, a failed lookup filters).

**A deleted panel category stopped every ticket of that panel.**
`panel::open` and `public::ensure` used the saved category id as is, so after staff deleted it every create failed with a vague error. *Avoid:* as in "A saved id can point at something deleted": `tickets::category_live` (cache, then Discord, only 10003 is gone) before using a panel category, else the ticket category through `ensure_category`, which `public::ensure` also calls.

**The dashboard knew only the ticket category, not the panel categories.**
Channel Setup (`fixed_by`, `own_access`), the Message Builder's create refusal, `embeds::bot_channel` and lockdown read only `tickets.category`, so a channel in a panel's own category could get its access reset or a bot post. *Avoid:* every check for "this holds ticket channels" uses `tickets::categories` (raw config, so a panel that does not parse keeps its category). A full category (50 channels) made every panel ticket fail: `panel::open` counts the children first and goes on to the ticket category, else `reply.ticket.categories_full` and one owner DM a day (not `alert_owner`: that shares the attack alert slot). `dm::send_mail` does the same check, and asks the type before it makes the channel.

**`closeall` said "all closed" when closes failed, and the metrics endpoint died on one error.**
Failed closes were only logged, and `metrics::serve` returned on the first `accept` error (EMFILE). *Avoid:* a bulk action reports "closed X of Y" (`tickets::close_all`, after a Yes/No through `confirm`) and does not delete the channel that holds its own answer; an answer to a message that may be gone is best effort, never `?`; a long-lived listener logs an accept error and goes on, with a cap on parallel answers.

**Two tickets at once made two ticket categories.**
`tickets::ensure_category` looked for the category and created it when missing, with nothing between. *Avoid:* a per-server `tokio::sync::Mutex` holds look and create together (one bot process per database); per server, because it is held across Discord calls.

**A ticket was marked closed before its log and channel delete, and a half-opened one blocked the member.**
`staff::close` set `closed_at` first, so a restart before the delete left a live channel that no longer counted as a ticket (no close, no relay), and a second close returned silently. `dm::create` took the number with `channel_id = NULL`; a restart before the channel was made left that row open forever, and the unique open-ticket index then refused every new ticket of that member in that server.
*Avoid:* tickets have a `status` (`creating`, `open`, `closing`, `closed`, migration 3930; no CHECK against `closed_at` yet, so an image rollback can still close). A close claims `open` → `closing` and queues `ticket_close_check` in the same transaction, treats a 404 on the channel delete as done, then sets `closed`; the check closes a ticket still `closing` whose channel is gone and opens any other one again (staff told). `on_channel_delete` leaves a `closing` ticket to its close. `claim_number` removes the member's own `creating` row older than 10 minutes; a create whose row was removed meanwhile deletes its channel. A member DM that finds its ticket channel gone (deleted while the bot was offline) closes that ticket and asks for the message again. `closeall` takes only `open` tickets. Not covered yet: a channel made just before a restart stays as an empty orphan (phase C).

**A DM into the server skipped the server's protections.**
Ticket DMs are relayed into a staff channel but were never read by automod, and new tickets opened during a raid or lockdown and without limit, so a raid could flood staff with scam links and slurs through the bot. Root cause: the filters hang off guild `MessageCreate`, and a DM has no guild.
*Avoid:* text that the bot carries into a server goes through that server's filters. `tickets::dm::filtered` runs the word (local list; Discord's AutoMod never sees a DM), scam, phishing and invite filters before a ticket opens or a message is relayed; new tickets wait during a raid or lock (`lockdown::raid_or_lock`, shared with auto-dehoist) and are capped at 3 per member and 20 per server per hour. A quarantined member opens a ticket only when given no reason (automatic quarantines, or staff with an empty reason), since tickets are then the only way they learn why; a staff quarantine with a reason gets a short refusal (`tickets::dm::quarantined_with_reason`, counting only cases since the current quarantine row began, so an old lifted case does not block): the staff intro says "Quarantined", and a quarantine DM without a reason says they can DM Brim while tickets are on (`reply::reach_staff`). Automatic quarantines (anti-nuke, rate limits, the Raider List, a rejoin) queue a `quarantine_dm` job (`reply::queue_quarantine_dm`), so the DM never holds back the containment or the revert, and queue none during a join or voice raid, for a bot, or for a join quarantine. The DM is also skipped during a lock or raid and is sent at most once per member per 24 h (a `quarantine_dm_cooldown` marker job), so a re-quarantine loop cannot spam a member. Not covered: shortener lookups and attachments.

**Ticket snippets and the blacklist had no count cap.**
Holders of the weak Manage Tickets permit could add entries without end, and each add writes a full config version. *Avoid:* one rule in core (`sections::tickets_cap_problem`, `MAX_SNIPPETS` 100, `MAX_BLOCKED` 1000), run by the bot's ticket commands on the locked config inside `settings::save` (two adds at once cannot both pass) and by the dashboard's `validate` (save, import, rollback). Refuse only a new entry: lists stored above the cap keep working and can be edited or shortened. The dashboard shows "N of cap" from the schema (`cap`), not a UI copy.

**A ticket member could write a staff line into the transcript.**
`history` put message text into `[time] Name (Role): text` lines without touching newlines, so a DM holding `\n[2026-11-03 09:10:00] Mod (Staff): ...` became a staff line in the transcript and on the dashboard page. *Avoid:* `tickets::staff::line` indents every continuation line, and the dashboard parses only lines that start with `[`.

**A ticket lookup ran for every message in any category.**
`ticket_here` queried `tickets` for every plain message in a channel with a parent, also on servers without panels. *Avoid:* return before the query when the channel is not in the ticket category and the server has no panels.

**Seeing a ticket channel was enough to talk as staff, and any Viewer could read transcripts.**
A plain message in a ticket channel was relayed to the member by DM before any permit check (only the command branch checked), so anyone a wrong overwrite let into the channel could DM the member as staff. The transcript route needed only Viewer and served any bot file named `ticket_log_` in any channel of the server. *Avoid:* every relay path checks the same live rule (`tickets::commands::allowed`: a Manage Tickets permit; admin commands Owner/EO/TA). Access roles are removed (permits only): any holder of a plain Discord role got ticket staff power, and nothing guarded who gave that role. The default Admins and Moderators permits get Manage Tickets (Auto Setup, migration 3931). The transcript route needs `api::staff(.., &["tickets"])`, a channel the server's config ever named as its ticket log, a `cdn.discordapp.com` URL before and after redirects, and at most 25 MB, also while reading. Limit: config history keeps 200 versions, so a log channel older than that is refused until transcripts are recorded per ticket (phase B).

- **A bot-kept message took over messages staff posted.** `public::sync_post` edited every `ticket_panel_posts` row in #open-a-ticket, so a Publish (a chosen subset, or a menu) into that channel was rewritten to the bot's message on the next save, and with every panel off the old buttons stayed. *Avoid:* code that keeps its own message in sync touches only the rows it posted (`posted_by = app.me`), and removes its message when there is nothing left to show.

- **A new DM button answered after its REST work.** The member's ticket type menu in the DM saved the type, posted, logged and updated staff buttons, and only then answered Discord, so a slow API showed "This interaction failed". *Avoid:* every new button handler defers first and edits the answer at the end, also when it copies a flow (`staff_button` kindset) that already does.

- **A new text field's default reached servers that never chose it.** Giving `tickets.panel_text` the new default through serde would add that text on top of the own panels of every server whose config has no such key, including restored versions and imports. *Avoid:* a new field that changes what members see defaults to "nothing new" when missing; the new default is written together with the default it belongs to (`save_id` writes it with the default panel), and a migration moves only rows that are exactly the old default.

- **"The last server used" sent DMs to the wrong server's staff.** With confirmation off, a DM ticket message went to the last server the user wrote to, so a message with files meant for another server landed in the wrong ticket. *Avoid:* a DM goes straight on only when the user shares exactly one ticket server with Brim; with several, they pick the server for each message (`tickets::dm`). `ticket_users.last_guild` is no longer read or written.

- **A ticket pinged and gave access to roles that no longer exist (`@unknown-role`).** Nothing removes a permit role row (`permit_roles`) when the Discord role is deleted or re-made, and the stored ids in `tickets.ping_roles` and a panel's `ping_roles` go stale the same way. `tickets::staff_roles` (channel overwrites, at creation and in the public-channel resync) and `panel::ping_staff_roles` (the staff ping of every ticket) read those rows as they were, so the intro showed two `@unknown-role` mentions and the overwrites carried dead ids. The dashboard's role picker lists only live roles, so a dead id stays in the saved value with no way to untick it (not changed: the picker's list can be stale, and dropping unlisted ids there could remove a valid new role; the bot skips dead ids instead). *Avoid:* every place that mentions or grants access to a stored role id first drops ids the server no longer has (`tickets::live_roles` / `live_ids`, which keep the list when the role lookup fails); the same for a new role mention anywhere else. The DB rows stay: `relink` re-points them when Auto Setup or the Overview Fix remakes a role. Checked: every `staff_roles`, `ping_staff_roles`, `ping_roles` and `<@&` in `tickets/`. Role pings in other modules read roles from config the dashboard validates at save, not from permit rows; not changed. Also: the ticket type is in the channel name (`name-type-number`, `tickets::kind_name`, set at creation for a panel type and in `workflow::set_kind` for every later change). Discord allows two renames per 10 minutes per channel: a refused or slow rename (5 s limit) is only logged and the type change stands. Nothing finds a ticket by its channel name (lookups use `channel_id`).

- **#open-a-ticket showed a bare "Open a ticket" title over a "New panel" button.** The panel message text was written only together with the default panels; a server that pressed Add panel got an empty text, and the Add button named the first panel "New panel". Root cause: a default kept in config is written once, on one path, so every other path gets nothing. *Avoid:* a message's look is a Default messages entry (`ticket.panel`), so the default always applies until the server saves its own, on every path. The ticket greeting is the one config text the owner wanted on for every server: its serde and schema default is the default greeting and 4055 filled the empty ones; an empty greeting a server saves still sends none (the 2026-11-15 rule above still holds for other new fields). The first panel the Add button makes is labelled "Open a ticket". Migration 4055 moved each written panel text into an edited version of the entry, and the dashboard tells the bot (`pg_notify('ticket_panel')`) when Default messages change, so the posted message follows without a Tickets save.

## Ticket type buttons
- A panel with the type switch on posts one button per ticket type: `tk2:open:<panel>:<typehash>` (menu option value `<panel>:<typehash>`, form id gets the hash as a sixth part). *Avoid:* take the type only from a hash that matches a type in the current list and only while the panel shows more than one button (`button_types`); anything else gets `form_changed`. Never read the type name from the id.
- `panel_message`, `types_problem` and `button_types` are the one source for the posted message, the save check and the dashboard preview. The preview is drawn from `POST .../tickets/preview` (the page keeps no copy). Test: `the_preview_is_what_publish_posts`.
- A type name is the button label: at most 80 characters with the switch on. The save refuses more than 25 buttons on the panel message.
- `{ticket_type}` is empty for a ticket with no type (a DM ticket has one once the member picks it before the channel); every `tags` caller passes the type or "".
- Migration 4059 renames only the exact untouched 4057 panel. A panel with any other setting keeps its name.
