# Pitfalls: Messages: limits and checks

Index and rules: [PITFALLS.md](../PITFALLS.md).

**An embed-only message was logged as an empty "-" line.**
The message cache kept only text and file names. *Avoid:* the cache keeps the embed count, and every log that shows cached content goes through `CachedMessage::text` (or `cache::shown` for a live message): text, then "(1 embed)". Delete, edit and bulk delete all use it.

**A kick in one server hid a leave log in another, and a self-delete was blamed on a moderator.**
The logger kept kick and ban audit entries by user id only, so a kick of X in server A within 10 s dropped X's "Member Leave" log in server B. It joined a message delete to a moderator's audit entry on author and channel for 60 s, so X deleting their own message was logged with that moderator as Responsible. *Avoid:* removals are kept per (guild, user); an audit delete names one gateway delete only, seen before it or within `HOLD` after, and is removed once it matched. A later delete then shows no Responsible line instead of a wrong one.

**The raid alert DM linked the panic log.**
`alert_owner` always took `LogKind::Panic`, but join and voice raid logs go to `JoinRaid`. *Avoid:* the alert takes the kind of the log it points to.

**Another Discord bot was named in Brim text.**
Rule: never name another Discord bot anywhere Brim text lands: code, comments, docs, commit messages, PR text, issues. Say what the rule is, not where it comes from. *Avoid:* before a commit or PR, check `git diff origin/main` and `git log origin/main..HEAD` for the names of other bots.

**An edit in place keeps the text it does not name.**
The post sent no `content` when the text was empty, so editing a message posted with text left the old text on Discord while the dashboard said "edited".
*Avoid:* a PATCH of a message names every part the saved version can clear (`content: ""`); a new post may leave empty parts out. The appeal log edit keeps the text on purpose; other dashboard PATCH calls edit channels, roles, rules, not messages.

**A saved link could run script in the preview.**
Drafts may hold a link still being typed, and the preview opens a link after "Open this link?". A button or title link `javascript:...` saved through the API or MCP would run with the session of whoever opens the preview (an Editor's draft acting as the Owner).
*Avoid:* the save refuses any link scheme other than http(s), even in a draft (`embeds::link_ok`); the preview opens only http(s) links (`open_link`). Preview markdown links were already http(s) only (`md::inline`); image slots show only https images.

**A new key in a saved row broke the previous image.**
Saving `"components": []` on every message made the previous image (after a rollback) refuse to save or duplicate any of them; its check allowed only `content` and `embeds`.
*Avoid:* write a new key only when it holds something. Only messages that use a new feature (buttons, "when sent" footer time) are ones a rollback cannot handle; the PR says so.

**A Discord file link was stored, and it stopped working after about a day.**
Slash punishments saved the `proof:` attachment's CDN URL in `cases.proof`. Discord signs file links and they expire after about 24 hours, so proof on cases older than a day no longer opened (dashboard Records, mod log). The ticket relay's "Attachment N" fields had the same link. A file link looks lasting, but is not.
*Avoid:* never store or post a Discord file URL as the lasting place of a file. Put the file on a message Brim owns and keep that message's jump link (`commands::send_case_log`: the proof goes onto the case's mod-log message). A file already on the same message needs no link. When a file cannot be kept (no Mod Logs channel, too large, download failed), tell the moderator the link expires; never drop it silently.

**A button on a saved message opens what a panel opens, so it needs the panel's proof.**
The ticket button's check accepts only messages recorded in `ticket_panel_posts`, and the panel sync edits or deletes every message in that table, so a saved message listed there would be rewritten into a panel. An "I accept the rules" button that gave the verification roles itself would be a way past the captcha, a raid's raised mode and the suspicious-account check.
*Avoid:* a ready-made button is stored as an `action` (`rules`, `ticket:<type>`), never as a `custom_id`; the dashboard makes the id when it sends and drops such buttons from a DM copy. `tickets::panel::posted` accepts a saved message's copy only by its Sent log row in the same server whose button names that ticket type. The rules button runs the Verify button's own decision (`verify::decide`) and gives roles only where that is a plain grant (`accept_step`); otherwise it sends the member to Verify. Posting a ticket panel takes a Trusted Admin, so saving, sending or editing a copy of a message with a ticket button does too (`embeds::opens_tickets`). An undo button on a mod log builds the typed command from the stored case (`undo::command`) and runs `modcmds::run` as the presser, so it has no checks of its own to forget; a presser with no permit is refused before any lookup or claim.

**The message cache logged content older than 24 hours.**
`MessageCache::remove` ignored `TTL` and `prune` ran only on an insert into the same guild, so a quiet guild (or one the bot left) kept text past the 24 hours PRIVACY.md promises. *Avoid:* `remove` answers like `get` (expired is missing), and `flush` (every event and the timer) runs `prune_all`, which also drops guilds with nothing left.

**A saved message could hold control characters.**
`embeds::limits` checked lengths and shapes, not characters, so U+0001 (the preview's placeholder marker) could be saved through the API or MCP and forge preview HTML. *Avoid:* `limits` refuses any C0 control character or DEL other than `\n`, `\r` and `\t` in every text of the message and names the path (`embeds/1/author/name`).

**A member's text closed the log's code block or spoiler.**
`diff` broke a fence with `replace("```", ...)`, which leaves a real fence in a run of 4, 5 or 7 backticks, so a message could close its diff block and forge lines (a fake "Responsible") in the staff log. The report logs had the same bug with `replace("||", ...)`. *Avoid:* break every character of the delimiter (`` ` `` and `|`), not the delimiter string; the test tries runs of 3 to 8 backticks.

**A log embed could pass 6000 characters, and a change to a new permission showed an empty "Changes".**
`Log::build` did not count the author line toward Discord's 6000 total, so the log was refused and lost. `perm_diff` used `from_bits_truncate`, so a change to only unknown bits (bit 48) gave no names. *Avoid:* every text part of an embed counts toward the total; `perm_names` names unknown bits as `Bit N`.

**An entry's link fields were never filled, and an empty one made Discord refuse the message.**
`botmsg::render` fills text only, never `url` or `icon_url` (so member text cannot become a link), so a feed entry with `{image}` as its picture or `{link}` as its title link sent the literal placeholder; a template link whose variable was empty (a GitHub event with no page) sent `"url": ""`, which Discord refuses for the whole message (the feed then stops). *Avoid:* feed entries fill their link fields with the feed's link variables only (`fill_links`), and anything then not an http(s) link is emptied; `render` drops every empty embed, author, footer, image and thumbnail link for all entries.

**A Message Builder rule kept running after its saver lost the level to make it.**
A schedule, trigger or sticky message is saved by an Owner, Extra Owner or Trusted Admin, but the runner never asked again. *Avoid:* `msgrules::saver_may_run` reads the level of `updated_by` before every schedule run, trigger answer and sticky repost (`sticky_msgs` for stickies). Below Admin it turns the rule off with the reason in `issue` (shown on the card) and logs once (the update matches `enabled`, so a second run changes nothing). A save by someone with the level sets `updated_by` and `issue = null`. An unread level fails the run and pauses nothing. No migration.

**A thread passed the built-message channel check.**
`embeds::bot_channel` compared a thread's parent only with the ticket category, so a schedule or sticky could post in a thread of a log, appeal, verification or ticket channel. *Avoid:* pass `embeds::parents` (the parent and, for a thread, its parent) and compare each with the bot's own channels and the ticket category.

**Message Builder Send and Delete had weaker checks than Edit and Save.**
Send (`publish`) did not refuse Brim's log, ticket, verification and appeal channels, which edit, the schedule and trigger rules and the Builder's new channel refuse, so an Editor could post a fake log line as the bot. Delete needed only Editor, with no `emergency_gate`, so an Editor could delete a message that pings, sends as a webhook or runs by itself (which only a Trusted Admin may save), with its rules and every copy, also during a lockdown. *Avoid:* Send asks `bot_channel` like edit. Delete reads the row `for update`, calls `emergency_gate` and the same `trusted_only` check as save. Same class as "A second way to change something had a weaker check than the main way".

**A new automated send went out as "manual" and skipped every per-minute cap.**
`/tag` runs called `send_copy` with no rule and no answer, so `send_copy` filed them as `manual` (cap 0), and only the per-member limit held them back: ten permit holders could post 60 messages a minute. *Avoid:* every path that sends without a person at the dashboard has a server-wide cap. `/tag` checks it in the bot's queue insert (10 a minute per server), next to the per-member and per-channel limits.

- **A Message Builder access refusal answered 400.** The "pings members" and "sends as a webhook" refusals for staff below Trusted Admin were `BadRequest`, so the access matrix could not tell them from bad input. **Rule:** a refusal because of who the caller is answers 403 (`ApiError::Forbidden`). 400 is only for input that is wrong for everyone. The matrix in `tests/e2e/deep.js` runs in CI, and any answer other than 401/403 to a refused user fails it.

- **A saved log or command reply without `{text}` dropped the bot's own text.** `{text}` was only an important variable, and `events::frame_over` laid the saved frame over the log, so a frame with no `{text}`, or with it in a second embed, content or a link, sent only the frame and lost the log details or command answer. *Avoid:* every entry whose template has `{text}` gets it as `Def::required` (with `Def::what`). `botmsg::missing_text` looks for it only where every sender shows it (the first embed's title, description, fields, footer and author text, since `bot_embed` and frames send the first embed only). The dashboard save and kit import refuse such a copy (`botmsgs::problem`), a backup load leaves it out (`msgbackup::bot_messages_to_load`), and `botmsg::render` sends the default for a stored copy without it (copies from before the check, or brought back by Undo). The UI notice (`ui/src/botmsgs.rs` `missing`) repeats the rule for display only. MCP has no bot message write.

- **Short replies were fixed sentences in code, outside the Bot messages page.** Verification side replies and `/tag` answers were `Ok("...".into)` strings and `format!`. *Avoid:* a short reply is an entry `reply.<area>.<name>` (one message = one entry, default = today's sentence as message text, values as named variables), and every sender calls `reply::say(app, gid, key, vars)` (text, embeds, `edited`). Channel sends use `commands::say_said`; interaction replies put the same text and embeds in the response. A command's reply goes through its `cmd.<command>` frame only while the server has no edited version of the entry (`commands::send_reply(.., frame)`). `botmsg::uses_stored` is the one test of "is the edited version used" for `render` and `say`. A test scans the source for `"reply.` ids (unknown key = panic at send time) and fails on an entry no code sends. A member-typed value (a tag name) is only a variable, filled in one pass, never searched for more variables. Still fixed text, for later packages: the owner/Extra Owner verify answers, the DM-failed, "Check your DMs" and "Verification done." lines (`verify.rs`), the dashboard's tag result text, `Slash commands are disabled` in `slash.rs` and `general.rs` (same words as `reply.tag.slash_off`, to merge into one entry in P7). Not live tested.

- **Lock notices and short lock replies were literals in `lockdown.rs`.** The "The server is locked" notice, the "Lockdown Updates" post and the lock command's short answers could not be reworded. *Avoid:* entries `reply.lock.*` (`botmsg::lock_replies`). The two notices are embeds whose `{text}` is the update list the bot builds (`lockdown::updates_text`, empty until staff send one, so `{text}` is required but may render empty). The rest are message text. `lockdown::update` returns `reply::Said`. `fail_key` builds the "Lock Result:" reply from an entry: an edited version with an embed replaces the result embed, text only goes in the usual embed. Permit checks and `commands::gated` are unchanged. The notice default is byte-equal to the old one (test `lock_notice_numbers_updates_past_the_dropped_ones`). Lock result, loading and overview embeds and `LOCK_TYPES` belong to later packages (plan section 13). Not live tested.

- **The confirm prompt, Undo button and menu answers were literals.** "Do you want to proceed?" and its lines, the Undo refusals and the Message Builder menu's "Slow down" and "no longer in use" could not be reworded. *Avoid:* entries `reply.confirm.*`, `reply.undo.*`, `reply.menu.*` (`botmsg::confirm_and_button_replies`). The prompt is an embed whose required `{text}` is the target list the bot builds (`{seconds}` optional). The rest is message text sent with `reply::say`. A sentence inside a bigger result ("Command failed", "Failed to ban", the lost ticket permit in `closeall`) uses `reply::say_line`, which falls back to the default when an edited version has no text. Code-built text that is not an entry (`modcmds::run` results, `cmdcfg::button` refusals) becomes a `Said` with `From<String>`. Only the words changed: in `undo::handle` the no-permit stop still comes before any case lookup and before `Acting::claim`; `press` keeps the command settings check, the `not_current` check and `modcmds::run`; the click-time `tickets` permit re-check in `confirm.rs` is unchanged (test `a_press_needs_the_permit_of_its_command`). The prompt default is byte-equal to the old one (test `ten_second_question`). Left as is: the Undo reason "Undo of case #N" and the Action Log line on the mod log (package D1). Not live tested.

**The bot update alert went out titled "Raider List".**
Every bot owner DM was a `raider_notify` job sent in the editable `dm.raider_notify` entry, so the update and MCP token alerts carried the Raider List title and an edit could blank them. *Avoid:* the update alert and the MCP token made/revoked alerts are fixed text in code (`raiders::alert_owner`, `fixed: "update"` or `"mcp"` in the job), each in its own embed ("Bot update", "MCP token") with the mention and user ID of who did it. Never editable entries, not on the Bot messages page (owner rule, for security). Later "all embeds editable" packages must keep it. A bot build without `fixed` sends the job `text` in the old entry; the update that installs this change shows the old title once. Raider List confirm/verify alerts stay in `dm.raider_notify`; panic, join raid and voice raid alerts stay in the editable `dm.owner_alert`.
