# Pitfalls: Dashboard server: channels and roles

Index and rules: [PITFALLS.md](../PITFALLS.md).

**The security score missed a main role with Mention @everyone.**
The role loop and `stripped` used `DANGEROUS` for every role but @everyone, while the overwrite check used `EVERYONE_DANGEROUS` for main roles too. *Avoid:* `role_mask` gives @everyone and the main roles `EVERYONE_DANGEROUS` in the role row, `strip_targets` and `stripped`. Staff roles stay out (`staff_mention_note`).

**Hiding channels from @everyone can open read-only channels and shut out bots.**
The first standard set for open channels (@everyone denied View, main role allowed View, Send, History) looked only at the main role's own bits. A role allow beats an @everyone deny, so a channel read-only by "@everyone: no Send" became writable for every member. Denying @everyone View also hid every open channel from other bots (and Brim without Administrator), and a member count that skips bots said nobody loses access. A lock's unlock deletes the main-role overwrite it made, so a change during a lock is half undone.
*Avoid:* when a role is let in where @everyone was, add only the bits @everyone does not deny (View apart). Give managed (bot) roles the same bits as the main roles. Run only when verification gives a main role, nobody without one is left out, and no lockdown is active; check that on the server side of a Fix too (`channel_access::blocked`). Auto Setup's Information category and catch channel use the same check before hiding anything from members without a main role.

**A role id saved in the config can point at a role deleted in Discord.**
Auto Setup and Create Member role made a Member role only when the main-role list was empty. A deleted main role kept its dead id, so no Member role was made, the Overview "Main roles" check passed, "Move to main roles" stopped with "none of the main roles exist any more", and the same dead id as verification role gave members who passed the captcha no role.
*Avoid:* a check or "make it if missing" step tests that the saved role still exists in Discord, not only that the list is not empty. `checks` counts only live main and verification roles. `member_role_named` drops dead main and verification role ids before deciding; verification whose roles were all deleted gets the main role (verification with no role does nothing). Quarantine and staff roles already check this (`quarantine_missing`, `staff_roles` `alive`); EVERYONE_TO_MAIN skips dead main roles; channel gates (`channel_access::blocked`) count members without a live main role, so a dead id blocks them.

**A new Information category hid itself from members who could not verify yet.**
Information was always made with @everyone denied View and main roles let in, even with verification off or giving no main role, so members without one lost #announcements and #rules. The access gate (`config_gate`) reads saved main-role ids, so a main role deleted in Discord passes it. Every hiding plan wrote @everyone's deny first, so a refused role write after it (Brim without Administrator) left the channel to staff only.
*Avoid:* a step that hides a channel from @everyone checks [`blocked`] first and, when blocked, leaves it readable (Information then denies only Send) until the standard set may run; the Overview row and its Fix then make it verified-only. The Overview row is hidden, and its Fix refused, while a saved main role no longer exists. Every plan writes main and bot roles first and @everyone's deny last (`standard_overwrites`, `info_overwrites`); bot roles always keep access. The catch channel follows the same rule (`move_catch` moves it with its own overwrites when blocked); new "Text Channels"/"Voice Channels" categories get no overwrites and wait for the standard set.

**A channel set up for an old main role kept current members out, and nothing saw it.**
Information was made while the saved main role was one deleted in Discord; the Member role came later. Information denied @everyone View and let in no current role, and `info_overwrites` returned nothing once @everyone was denied, so the Overview row, its Fix and Auto Setup all left it hidden. The verification channel had the gap the other way: made before the Member role existed, verified members kept seeing it, and the wizard's "Setup channel" reused it without its overwrites.
*Avoid:* a check of a channel Brim owns tests every role it must hold, not only whether @everyone is kept out; a reused channel gets the overwrites a new one would. `info_overwrites` (main roles get View and History, lose Send and threads unless allowed) and `verify_overwrites` (each role verification gives is denied View) are used by Auto Setup, the wizard, the Overview row and its Fix. The catch channel already merges current main roles (`catch_overwrites`); open channels stay skipped when @everyone is denied and no main role is let in (that is how a private channel looks). The ticket log channel moves into Logs when elsewhere (`ticket_log_to_logs`, Overview row "Ticket log not with the other logs").

**Auto Setup took two minutes, because each channel move was its own call.**
Information, loose channels, the catch channel and the ticket log each sent their own `PATCH /guilds/{g}/channels`. That route has a strict rate limit; the client waits at most 10 s for a 429 and tries 3 times, so about 10 channels took two minutes and the catch move failed with 429.
*Avoid:* collect every move of one run and send once (`channel_access::send_moves`); a step only pushes its entries (`information`, `sort_loose`, `move_catch`, `ticket_log_to_logs`, `verification_first`). Discord refuses the whole list for one bad entry (a category holds at most 50 channels), so after a refusal each move is tried alone. Name a refused move in the result. Never list a channel twice in one call.

**Channel access waited for every member to have the Member role.**
Auto Setup and the Overview Fix skipped locking normal channels while any member had no Member role, so on servers with old members the channels stayed open and the Overview row returned after each Fix. Owner rule: a member who has not verified must not have access.
*Avoid:* no guard on members without the role. The first time verification is turned on (`verify_started`, one row per server, migration 4011), the bot gives the verification roles to every human member who is not quarantined (`verify::on_saved`); later joiners verify as usual. A server where verification was already on is in `verify_started` from the migration, so its members without the role lose the channels: the lock queues `verify_sweep`, which gives each a DM and the normal time limit, then the kick with a DM and a rejoin link (`verify::sweep`, `verify::deadline`). The sweep runs only once the first-time grant finished for every member (`verify_started.granted`; a failed or running grant never counts, so a failed step never removes members who should have had the role). Roles given pass the same filter as a normal verify (`verify::safe_roles`: no permit roles, no dangerous permissions). Left out: bots, quarantined members, anyone with a permit or Owner/Extra Owner/Trusted Admin (also at the deadline), members with a running time limit, servers where only suspicious joiners must verify. Queue the sweep only after the channels really became Member-only.

**A stored staff role deleted in Discord broke the channel fixes, and Fix All called it fixed.**
The Overview row "Staff cannot use their channels" looked only at staff roles Discord still has, but its Fix and the Information part of "Channels without the standard permissions" wrote overwrites for every stored staff role (permit and level roles). A deleted one gave 404 and an "internal error" toast, and `info_access` stopped each Information channel at that write (staff go first), so members never got Information. That Fix answered ok with a `failed` count the page ignored, so Fix All counted it as fixed and the row stayed.
*Avoid:* every write of a stored role id checks it against Discord's role list first (`channel_access::alive`, `live_staff`, shared by the row and the fixes). A refused write says which channel and role and why (`channel_access::put`); an unexpected error names the issue, not "internal error" (`internal_text`, never the URL). A refused staff write in Information does not stop the member writes there (only a member or bot write does; @everyone's deny comes last). A fix that answers ok with `failed` or `catch_stays` shows as partly fixed (`refused` in the Overview page). The quarantine channel fix refuses with a plain reason when the stored quarantine role was deleted. `staff_access`, `information`, `info_access`, `verify_access` filter; the standard set and catch channel already stop when a main role is gone; Auto Setup's own staff roles are made in the same run.

**A free permission grid could undo the shapes Brim keeps.**
The first Advanced grid took any role and ran after the quarantine and verification steps, so it could let the quarantine role or @everyone (past verification) into a channel, edit the verification channel, or hide a channel from a staff role without the owner check. "Read-only" and Public also read and changed Send denies during a lock, so Public could unlock a locked channel.
*Avoid:* a free editor of overwrites is applied before every shape Brim owns (quarantine, verification), which always win. It takes only roles the server may set (`Ctx::grid_role`: no quarantine, bot or managed roles), refuses @everyone View while main roles exist and the verification channel, and a staff role's View deny counts in `unstaffed` like hiding the channel from staff. Admins only and Owner only count there too. Nothing in Channel Setup reads or changes Send while `recovery::no_backup_now` says a lock is on (`Ctx.locked`).

**Auto Setup deleted the server's own channels and roles that had a matching name.**
`drop_named` deleted every text channel named like a log channel (`#mod-logs`, `#reports`, `#appeals`, ...) or `#verify-here` that the config did not use, and `quarantine_role` deleted every unused role named Quarantine, before it made a new one. The code cannot tell a leftover of an earlier Brim setup from a channel or role the server made itself, and anti-nuke ignores the bot's own deletes. *Avoid:* a setup never deletes a channel or role it did not make in this run. It takes over the oldest unused one with that name (`oldest_unused`). A log channel is moved into its category and its overwrites are replaced in full by the category's current ones (only adding denies left an old allow or Manage Permissions reading the logs). `#verify-here` gets the overwrites a new one would. Their messages stay. A Quarantine role must pass the same `unfit` check as a picked one (not @everyone, not managed, below the bot). No member may hold it (`ops::held_roles`; a held one would lock its members out with no quarantine row, case or release). It is stripped of its permissions. Other same-named ones are left alone.

**Auto Setup lost a save made during its Discord calls.**
Auto Setup decided "no custom permits yet" from its first read and then replaced `permits.custom` with the two default permits, so permits saved during its 10 or more seconds of Discord calls were gone. A save in that time also made its final `commit` return 409 after the roles and channels were made, and the level roles were written with no config version. *Avoid:* decide from the read in the final transaction (`no_custom`). Write the level roles together with a `bump`, under the config lock and only for levels nobody changed since the first read (`new_levels`). Put the setup's changed fields onto the newest version under the config lock (`put_changes`) instead of refusing the whole run.

**Overview read the member list once per row.**
`members_without` (up to 20 pages of members) ran once for each of the two rows with the same arguments, and the Channel Setup draft check read the guild, roles and channels again. *Avoid:* read the members once per request, and pass the score's `Live` to `channels::overview_check` (`world_of`).

**"Setup channel" left no config-change log line and posted a second panel.**
`verify_channel` committed a version without `log_change`, and posted the verify panel on every press, also into the channel that was already set. *Avoid:* every route that commits a version calls `log_change` with it. The panel is posted only into a new or taken-over channel.

- **A Tickets save refused "<id> is not a channel or role of this server" for an id the page had loaded.** The bot clears `tickets.category` when its category is deleted. A page loaded before that still held the old id, and `put_section` ran `check_ids` (id not in the stored config, not in the server) before the version check, so the stale page got a refusal instead of "reload". *Avoid:* `put_section` answers `Conflict` before any other check when `expected_version` is not the newest. Every section page goes through it, so no page can write an id the stored config dropped. A check that compares new with stored values runs only after the version is current.

**A route read data that its page hides.**
The Appeal Blacklist page is hidden without the `appeals` permit perm (`access::page`), but its list route needed only Viewer, so any Viewer could read the user ids by the API. The page rule and the route check are written apart. *Avoid:* a route needs at least what its page needs (`api::staff` with the same permit perm), for every route of a hidden page. Test: `the_blacklist_needs_the_appeals_permit_perm`.

- **A Discord create in a request handler was not cancel-safe.** "+ New channel" ran Channel Setup's create inside the handler, so a closed tab could leave a made channel with no log line and the push lock held until rollback; a failing step after the create (its position) read as "not made" and a retry made a second channel. *Avoid:* run locked Discord work in `tokio::spawn` (like push); once the thing exists, later step failures are warnings.

- **A failed permission lookup greyed usable channels.** The channel picker used `member_roles(..).unwrap_or_default`, so a failed lookup of Brim's roles judged it by @everyone only and disabled channels it can post in. *Avoid:* when an input to a permission check is missing, skip the check (no reason shown); never compute it from a default.

- **A refused Member write left a channel hidden, and Overview then called it private.** The standard set wrote each main role's View, then @everyone's deny, and counted a refused write but went on. A channel whose Member write failed (429 or missing permission) lost @everyone's View with no main role let in, which `standard_overwrites` reads as private: Overview and the Fix skipped it, while members could not see it. *Avoid:* a deny that hides a channel from @everyone comes last and is skipped when any allow before it on that channel failed (as `info_access` does); test it with a refused role write.

- **A channel hidden from every member read as "private on purpose", so Overview and the Fix left it hidden.** Before #303 a run could write @everyone's View deny after a main role write failed (429). `standard_overwrites` called any channel with @everyone denied and no main role let in private, so the half-done channel never showed in Overview and no Fix or Auto Setup run repaired it; Administrator roles (bots) in Discord's access list made it look like someone was let in. *Avoid (owner rule):* a channel is public unless Channel Setup limited it or it is one of Brim's own layouts. Private means: @everyone denied, no main role let in, AND some overwrite other than a bot (managed) role allows View. Channel Setup's limited channels deny the main roles and always let the Brim member in (also on a channel that was hidden already, or a deleted staff role would leave it looking half done); the Logs, Staff and Staff Chat categories let the Brim member in; a jail lets the quarantine role in; logs, verification, catch, Information and tickets are skipped by id. Read only real overwrites, never Discord's access list (Administrator shows there). `private_overwrites`, `is_public`, `private_channel_of` and the lockdown "private" flag mean "hidden from @everyone" for log channels and display only; they stay as they are.

- **Channel Setup called every members' channel "Staff only".** `access_of` read "@everyone denied View" as limited, but with verification every members' channel denies @everyone and lets the main role in, so #general, the text and voice categories and the ticket category showed "Staff only" and the panel offered "Only these roles". Editing such a channel would have hidden it from members; picking "Everyone" also cleared @everyone's View deny, which let unverified members in. *Avoid:* limited means @everyone denied AND no main role let in (as `private_overwrites`); open with a main role is the standard set (main roles in, @everyone out). The row badge comes from the server (`tag_of`): none for a members' channel, "Unverified" for the verification channel, "Staff" for a staff-only one (the Owner and Trusted Admin level roles count as staff), a custom role's name, "Members read only" where the main roles cannot send (Information).

- **A deleted catch channel stayed set, and every save logged a failed warning post.** Nothing noticed a catch channel deleted in Discord: no Overview row and no fix, and `catch::post_notice` (run after each save) logged "404 Unknown Channel" each time. *Avoid:* a stored channel Brim depends on gets an Overview row when it is gone (`catch_gone_check`), with a fix that makes it again in the shape Auto Setup makes (`sections::make_catch`, shared with the catch setup button); background posts into a gone channel return quietly and leave the telling to that row.

- **A colour set by hand must survive Auto Setup.** Auto Setup and the Member role fix give the Member role green (`MEMBER_COLOUR`) when they make it, take one over, or find an earlier colourless one named Member (or the Custom name). *Avoid:* only a role without a colour (0) gets one; a main role with another name keeps its look. The staff roles are Brim's layout and always get their colours.

- **Settings the score only warns about passed the "serious problem" check.** Verification level and content filter are `Warn` rows, and `layout::blocking` keeps only `Bad` ones, so a push could set both to off and save that as the correct layout. *Avoid:* compare a change to a guarded setting with live on its own (`roles::weaker`); a `Bad`-only filter is not a safety check for everything.
