# Pitfalls: Messages: texts in the Bot messages page

Index and rules: [PITFALLS.md](../PITFALLS.md).

- **Report, case, note, whitelist and catch channel replies were literals.** *Avoid:* entries `reply.report.*`, `reply.case.*`, `reply.note.*`, `reply.whitelist.*`, `reply.catch.warning` (`botmsg::report_case_replies`). Report answers are `Said` (`reports::tell`, ephemeral); mod command results use `reply::say_line` (`modcmds::say`) and still pass the command frame. One sentence, one entry (`reply.undo.no_case` is merged into `reply.case.no_case`). Limits in note, reason and proof replies are written in the default; a test ties them to `NOTE_MIN`, `NOTE_MAX`, `CASE_TEXT_MAX`. Traps: (1) the Close case button compares the reply with `modcmds::closed_text` (async, same entry per server); never compare a reply with a hard-coded sentence. (2) The catch channel skips posting when its warning is already there, found by embed title; the check also takes the edited title or text, and the old "Catch channel" title still counts. `cmd.whitelist` is locked, so its replies are locked entries until the security package opens them with guards. Only words changed: report permit, `gated`, `cmdcfg::button`, log channel, `permits::check`, whitelist 2FA/permit checks run as before. Still code: report and AutoMod report logs, their Action Log lines, User Info embeds, `reply::case_text`, note card, proof list, Interactive Whitelist embeds, "Unknown case type", whitelist usage line, Report Message form title.

- **Ticket command results, staff notices and the paused DM were literals.** *Avoid:* entries `reply.ticket.*` (`botmsg::TICKET_REPLIES`, one embed each, red for a refusal), `reply.closeall.*` and `ticket.paused` (`{reason}`; server footer and time added by code). `workflow` results are a `Line` (entry key and values) said in the server's words later; `Ok(None)` means nothing more to say. A sentence built from parts is one entry per case (`command_only_on`/`_off`, `note_no_log_deleted`/`_kept`, `closeall.partly_anon`), never a variable holding English words. Ticket log lines (`workflow::log_update`) keep their own text. Still code: ticket permit refusals, "not set up yet", panel ticket relay refusal, usage lines of `reply`, `snippetadd`, `reassign`, the `tickets_cap_problem` cap text (shared with the dashboard save), the DM type pick's "This ticket is closed." when no server is known.

- **Errors, usage lines and permit refusals were literals.** *Avoid:* entries in `botmsg::error_replies` (`reply.error.*`, `reply.settings.*`, `reply.invite.*`, `reply.appeal.*`, `reply.nsfw.*`, `reply.raider.*`) and `reply.ticket.*` rows. A parser keeps returning its text; the send point puts it in `reply.error.wrong_use` with `reply::say_wrong` (`reply::UNKNOWN_COMMAND` has its own entry); a usage line goes in `{text}` of `reply.error.usage` or `reply.ticket.usage`. `build` marks `{text}` required only when the first embed shows it, so a message-text entry with `{text}` got no required placeholder and an edit without it dropped the usage line. A message-text entry sets `required` and `what` itself (as feed posts do); the scan test checks it.

- **Security texts could not be reworded, and a long author name made Discord refuse a whole message.** *Avoid:* anti-nuke, panic, join raid, whitelist, and the owner security, invite back, rescue key, MCP decision and 2FA code DMs are entries with `Def::security` (group "Security"): only Owner and Extra Owners save, revert, undo or import them (`botmsgs::may_edit`), Revert all leaves them, each change is an audit line with old and new version (`change_line`). A required placeholder counts only as plain text in the first embed's title or description, within its first 10 lines (`botmsg::fact_places`, `visible`: not in a spoiler, link target, `<...>` or code block language tag; footer, author, field do not count). An edit cannot hold control, zero-width or text direction characters (`hides_facts`). Logs need `{title}` and `{text}`, rescue DM `{name}` and `{page}`, 2FA DM `{code}`. `render` sends the default when an edit's own words push a fact past Discord's limits (`keeps_facts` looks only in the same places; a spare copy in a footer spoiler does not count; a value too long for the default too keeps the edit). Never accept a placeholder anywhere `shown` looks or search every string at send time (`{title}` in the author line, or a footer-spoiler copy, would pass); `frame_over` must not drop a frame's author. 2FA and MCP decision DMs stay per server; the 2FA DM is sent with no server, so a server's edit never shows. The dashboard's `Discord::dm` reads a bot-wide entry's copy under guild 0. `botmsg::limit` cuts title, description, footer, fields and the author name (256): an author over 256 made Discord refuse the whole message.

- **DMs with no server were literals, and the data request DM was locked.** DM ticket commands (usage, confirmation on/off, "No server found", server menu, "request expired", "cancelled", "wait a few seconds", "message was deleted", "This ticket is closed.") are sent before a server is chosen, so no server's edit applies. *Avoid:* bot-wide entries `reply.dm.*` (`botmsg::outside_replies`, group "Outside a server (bot owner)"), listed in `botmsg::BOT_WIDE`, one copy under guild 0 that only the bot owner changes; senders call `reply::say_wide` (`tickets::say_dm` for a channel, `say_wide_line` for text in the menu). A test ties the group to `BOT_WIDE`. Outside DMs that state facts about the recipient (`dm.data_request`, `dm.raider_notify`) are `Def::strict`: P8 fact rules apply (`{text}` as plain text in the first embed's title or description, no hiding characters, default sent when an edit loses it), without the Security chip or Owner/EO rule. `msgbackup` and kit import skip outside entries. Left: the dashboard shows an outside entry as editable to a server Admin, who gets the server's refusal on save.

- **A security text changed without a 2FA code, and a backup load replaced security texts without a log line.** *Avoid:* `botmsgs::may_edit` asks `require(..., step_up = true)` for a security text (save, revert, undo); the kit import checks it separately (it does not use `may_edit`) when the applied part holds a security text; a preview needs none. Every new route that writes `bot_messages` must go through `may_edit` or make the same check. The backup load needs 2FA (dashboard `recovery::load`, command `fresh_2fa`) and writes one `dashboard_audit` line per security text whose copy changed (`botmsg::change_line`, shared with the dashboard), under the user who asked, in the load's transaction. The bot does not post these lines to the config change log channel; the Backup Loaded server log covers the load.

- **Moderation logs and command answers built their facts in code; a fields-only log had no place for a frame.** *Avoid:* the 13 keys in `botmsg::FACTS` (`log.mod_command.*`, `reply.mod.*`: case log, case edits, proof, note logs, "Case Deleted", "Old Cases Removed", punishment result, several-member result, short case line) are the whole message with named placeholders (`{case}`, `{kind}`, `{member}`, `{moderator}`, `{duration}`, `{reason}`, `{changes}`, `{when}` ...), `Def::details`, `Def::strict` (P8 fact rules, default sent when an edit loses a fact, old and new version in the audit line), not Security. A log names its entry with `Log::entry` and its values with `Log::var` (a later value replaces an earlier one); `events::framed_with` lays an entry of facts over the whole log (fields replace; a frame still adds its fields). Code builds each log itself until a server edits the entry; `mod_texts_tests` lays the default beside every builder. An older frame around `{text}` keeps working: `{text}` holds every fact (`missing_text`, the editor's `missing`). Facts may stay in fields where the default has them (`fact_strings`). `render` drops a field with an empty value (Discord refuses the whole message for one). Answers: `ModTexts::load` reads the three `reply.mod.*` copies; `result_embeds_with`/`summary_with` use them; the `Applied.text` each command builds stays code, because the result embed and confirm path read it back (`Case #N: kind <@id>` first line, then notes). A variable an entry lists but a sender forgets shows as literal `{name}`; the case log sets every purge variable to empty. An edited answer is still wrapped by the command's `cmd.<command>` frame; short replies that become one whole entry (`say_said`) are the exception. Still code: the "Add Reason" pointer embed, the purge note in the channel.

- **Server event logs from the audit log built their facts in code, and the values never reached the sender.** *Avoid:* the types in `botmsg::AUDIT_LOGS` (member, role, channel, server, invite, webhook, emoji, sticker, event, thread, pin) are entries of facts (`is_facts`) with one template (`audit_entries`): `{by}`, `{channel}`, `{target}`, `{when}`, `{reason}`, `{changes}` (changes, "Not Shown" line and extra information as one block, which `render::audit` cuts from the lines after the reason). `render::audit` returned a finished `Embed`, so `Log::var` values were lost through `Entry`, `LogMessage`, `send_event_log`; now `Entry` and `LogMessage` carry `vars`, `events::send_entry` passes them to `framed_with`, and every builder sets every placeholder, empty ones too. A test in `render.rs` lays the default beside the built log (overwrite, update with a reason and no executor, webhook, prune). A variable name means the same in every area. `missing_text` and `keeps_facts` accept `{text}` wherever the old frame rules did (D1 entries too); counting an old frame only when `{text}` is in title or description silently skipped frames with `{text}` in footer, author or a field. An empty audit reason is no reason (the template drops a bare label).

- **The gateway and bot-made event logs built their facts in code, and two senders dropped a log's values.** *Avoid:* entries of facts in `botmsg::EVENT_LOGS` (message edit/delete/bulk delete, poll, publish, member join/leave, voice, event sign-up, boost level, automatic thread archive, Member Renamed, Timeout Ended, user name/avatar; group, title, lines `Label|value` or a line as written). `event_entries` builds each template, takes every placeholder a line shows as a variable, and every one shown outside a link target, except `{when}`, as required. A placeholder not in `FACT_VARS` panics when the list is built. Builders use `Log::fact(label, var, value)` (leaves an empty line out, still sets the variable) and return a `Log`, not an `Embed`, so `Entry`, `HeldLeave`, `HeldArchive` keep the values until `LogMessage` (`Log::parts`). `send_log_rows` and `send_log_pinging` must pass the values (as `send_event_log` does) or an edited entry shows `{name}`. Tests: `Logger::handle`, `flush`, `handle_voice` check every log of facts against its default (`reads_as_default`). A line whose only value is an empty code span (`` `{case}` ``) was kept as a bare label; `fill_text` drops it.

- **Automod, Discord AutoMod rule, Join Gate and verification logs built their facts in code.** Logs whose title holds a name (`*alex has been warned!*`, `alex's Verification Result:`) or share a title (five "Verification" logs, two "Rule Not Approved" logs) fell into one entry, so one edit had to fit different texts. *Avoid:* each is its own entry of facts in `botmsg::FACTS` (`botmsg::d3_entries`), as D1: the builder names its entry with `Log::entry` when the title cannot, sets every placeholder with `Log::var` (empty ones too); `d3_texts_tests` lays every default beside the builder. A sentence that differs per call (`taken_log`) is one entry per sentence (`given::BOT_TAKEN`, `OFFLINE_TAKEN`, `CHANNEL_TAKEN`), not a `{what}` placeholder. Filter-log message content is in a spoiler, so `{content}` cannot be required there; member, filter and channel are. A log with its own entry must skip a typed entry of facts with the same title ("could not read the rule" took "Rule Not Approved"'s edit); a typed frame (old "Verification") still applies. Each `FACT_VARS` name has one meaning for all entries (Join Gate refusal is `{refused}`; `{failed}` is D1's count). An old frame that kept `{text}` only in a footer, field or spoiler is judged by the fact rules and the default is sent. Still code: panic "Server Locked" log in `automod.rs`, join raid logs in `joingate.rs`, `users_only.rs`, `verify/deleted.rs` (anti-nuke log; D4), "NSFW Image Found" (`nsfw.rs`), "Webhooks Deleted" (`webhooks.rs`).

- **The general command answers built their facts in code, and a page turn dropped the command's saved frame.** Page buttons (`settings::handle`, kinds `about`, `ginfo`, `cmds`, `cases.*`, `tkblock`, `tksnip`, settings panels) rebuilt the page without the `cmd.<command>` frame, so an edited frame vanished on page two. *Avoid:* answers of `info`, `roleinfo`, `serverinfo`, `about`, `ping`, `invites` are entries of facts in `botmsg::ANSWERS` (`answer_entries`, one embed per message: a page is its own entry); code passes values only, through `reply::answer`, which fills every unset placeholder with empty, so no raw `{name}` reaches Discord. One entry holds every variant of its answer, because a bare `**Label:**` line whose placeholders are all empty is dropped; a line of free words with an empty placeholder keeps its words (an edit should put an optional value behind a label). Values in a field carry their own code style (an empty field must be blank to be dropped); values in a line do not. `answer_texts_tests` keeps the former builders as reference, compares every default, moves every placeholder and checks that a copy losing the required fact sends the default. A page turn lays the command's frame like page one (`settings::page_command`). Titles holding a name use the name's placeholder (`{member.username}'s Info:`), not `{title}`. Still code: plain refusals of `info` and `invites`, link maker refusals, flag block words (`Spam`, `Managed`, `No Avatar`).

- **Lockdown, auto slowmode, backup and scheduled action logs and the lock command answers built their words in code.** *Avoid:* logs are entries of facts as D1 (`botmsg::d5_entries`); the startup-check "Scheduled Action Failed" has its own entry so it cannot take the job give-up's edit (same title). Lock answers ("Brim Lockdown:", channel locked/unlocked, "Lock Result:", "Active lockdown modes:") are entries of facts (`botmsg::lock_answers`, `reply.lock.*`): each builder returns its embed with its entry and values (`lockdown::Entry`), and `lockdown::own` swaps in the server's edited version only when there is one (`reply::say(..).edited`); code keeps building the default and `d5_texts_tests` lays each default beside it. `Reply.text` stays code, like `Applied.text`. A short reply sentence a server edited with an embed still replaces the whole "Lock Result:" embed (P4 rule); without one the "Lock Result:" entry frames it.

- **Ticket, report, appeal and catch channel logs built their facts in code, and the dashboard posted its logs without any edited version.** `Discord::post_log` sent `log.build` as it was, so the dashboard's appeal log and "Lockdown Update" ignored a server's edit. *Avoid:* entries of facts as D1-D5 (`botmsg::d7_entries`, test `d7_texts_tests`, the dashboard's in `appeals.rs`) for New Ticket, Ticket Closed, the five "Ticket Updated" sentences (one entry each), message report log (headline is the author line), "Discord AutoMod Report", "Appeal Not Accepted", appeal log, two catch channel logs. `events::send_private` (ticket logs) takes a `Log` and passes its entry and values, as `send_log` does; `framed_log` does the same for report logs. `over`, `bot_embed`, `parts` live in `tommybot_logging::overlay` so the dashboard lays an edit over its logs the same way (`discord::framed`: own entry, then the group; the copy's fields are added, so the appellant's answers stay). Link fields are never filled from placeholders, so a copy's author line keeps the log's icon unless the copy sets one. Footers, the ticket closer's author line and the report thumbnail stay as built unless an edit sets its own. A Ticket Closed "Changes" list whose first line was over 1024 bytes made an empty field (Discord refuses the whole log); the field is left out. Still code: permit sync logs go to the anti-nuke log (D4).

- **Security logs built their facts in code, and an entry of facts with `{text}` let a frame skip every fact rule.** *Avoid:* one entry per text in `botmsg::SECURITY_LOGS` (anti-nuke, panic, join raid, permit sync, verification channel, log channel, NSFW, webhook spam; group Security, so Owner/EO, 2FA and backup audit rules of P8 and #416 apply); every placeholder shown is required; the title stays `{title}`. Senders call `overlay::security_log(title, key, values)`, which renders the default, so sent log and default cannot drift; complex builders (`antinuke::report_log`, `panic::report`, `joingate::trigger_log`) name their entry with `Log::entry` and `fact`/`var`. `d4_texts_tests` keeps each old builder beside the new one. `over` fills any unset placeholder with empty. A default over 10 lines (nuke report) may keep its facts up to its own length (`fact_places`). Rule: a security entry of facts never offers `{text}` (a test checks every one): `is_frame` takes any copy showing `{text}` as an old frame and skips `hides_facts` and every required fact, so `||{text}||` under a calm title would pass; the frame exception is only for copies saved before an entry had facts. NSFW and webhook spam logs are security entries in the ordinary automod group: a security log never takes a non-security group's frame (`framed_with` must not fall back to the `log.auto_mod` frame any Admin may edit). Old copies saved on those two entries before D4 lack the required facts, so the default is sent.

- **The security command panels could only be framed, and the whitelist menu and result skipped every edit.** `t!antinuke`, `t!ancaps`, `t!anpanic`, `t!antinukerestore`, `t!joinraid` built their rows in code; the whitelist menu and saved result were posted with `create_message` and the interaction answer, so not even `cmd.whitelist` reached them. *Avoid:* each panel is one entry of facts in `botmsg::PANELS` (`reply.panel.<command>`, group Security, so Owner/EO, 2FA and the audit line apply); whitelist answers are `reply.whitelist.prompt` and `reply.whitelist.saved`. Every value and row number is a required placeholder: the number is its own placeholder named as the code (`{3}` fills `[3]`, `{4a}` fills `[A]`), because people type it to change the setting; the on/off sign after Status (`{toggle}`) is required too. No `{text}` (D4 rule). A panel may put all rows in one list: `fact_places` counts as many lines as the default has in all. `settings::panel_vars` fills the entry from the same rows `panel` reads; `panel_texts_tests` keeps `PANELS` equal to `settings::maps` and each default equal to `panel`; a new row in a security panel needs its line in `PANELS`. The `cmd.<command>` frame still lies over the panel. A reply a command sends outside the reply helpers gets no edit: send every answer through an entry or `command_reply`. A security entry offers no placeholder whose value a server sets freely: `{prefix}` may be `||` or three backticks, and the save check reads the template before filling, so `{prefix}{status}{prefix}` would hide a fact; the footer gets the prefix after filling (`settings::with_prefix`). `limit` must drop the last fields until an embed fits Discord's 6000 total (it cut only the description, so an edited fields-only copy was refused and nothing posted); a security text then sends its default.

- **The other settings panels and the reply after a setting changed were still code text.** *Avoid:* `t!statics`, `t!heat`, `t!hfilters`, `t!joingate`, `t!verification`, `t!misc`, `t!raiderlist` are entries of facts in `botmsg::SETTINGS_PANELS` (group Settings panels, same rules as `PANELS`: every row number, value and on/off sign required); the changed reply ("✅ [7B] Name: value") is `reply.settings.changed` with `{row}` and `{value}` required. A security panel's setting (join raid), a setting only Owner and Extra Owners may change (misc, main roles) and the Trusted Admins line use the Security copy `reply.settings.changed_security` (`settings::changed_key`), so a Trusted Admin cannot reword the answer (misc must not get the general copy). The Security copy is sent without any `cmd.<command>` frame (`send_said`): the Trusted Admins line answers `t!statics`, and `cmd.statics` is not a security text, so a Trusted Admin could put the list in a spoiler there. A paged panel (`t!hfilters`) is filled whole, then cut into pages of its cards (`settings::page_of`); a page turn uses the same entry, never `panel`. The whole filled panel goes through `limit`, so a paged panel must stay under Discord's 6000 in all (the test compares every page with `panel` and fails if fields were dropped). The misc Prefix row is the one panel value a server sets freely (`{prefix}`); it is not a security text, so it stays.

- **The settings error replies were code text.** *Avoid:* `settings::edit_for`, `resolve` and `no_such_row` return a `Refusal` (entry plus values), never a sentence; `Refusal::say` sends the server's copy, `Refusal::text` is the default (tests compare it with the old text for every row). Entries (not a switch, not a list, not valid, out of range, takes one of, not a role/channel of this server, nothing found, ambiguous, no such row, "Not saved: ...", 2FA replies, main roles and Trusted Admins refusals, "Only the person who opened this panel can use it") are in `botmsg::SETTINGS_ERRORS` (each with a Security copy `<key>_security`, chosen by `settings::changed_key` as for the changed reply, or, when no row was found, by whether the panel has any such row) and `botmsg::SECURITY_ERRORS` (always Security). What went wrong is a key variable (`{row}`, `{typed}`, `{min}`/`{max}`, `{options}`, `{reason}`); no entry offers `{text}`. A Security copy is sent without the `cmd.<command>` frame (`send_said`). `settings::save` keeps its `String` refusal for other callers; the settings command uses `save_with`, whose "Not saved" is an entry. `needs_2fa` is one entry for settings, whitelist and backups replies (`needs_2fa_line` where the reply is only text). Bot-not-user refusals (`users_only::refuse`) are security entries, one per list.

- **The dashboard's Configuration Changed log had no Bot messages entry.** `api::log_change` posted it with `post_log`, which knows no entries; general command answers (help, dashboard, invite, config), invite link replies and report User Info embeds were also code. Root cause: the log is not a `LogKind`, so per-kind frames in `botmsg::logs` never covered it, and the D packages listed areas, not every sender. *Avoid:* a dashboard log goes through `discord::framed` with its own entry (`log.config_changes`) and `post_embed_with`; a command answer is an entry rendered with `reply::answer` or `reply::say`, never a `Log` or `format!` in the handler. A refusal helper returns an entry key and values (`invite_cmds::Reply`); tests render the default to compare with the old text. When adding a sender, check every `Log::new` and `post_log` in the bot and dashboard.
