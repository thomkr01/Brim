# Pitfalls: Database and migrations

Index and rules: [PITFALLS.md](../PITFALLS.md).

**Command rate limits were shared across servers.**
`RateLimiter` and `command_uses` were keyed by (user, action), so a mod's uses in server A counted in server B and could quarantine them there. *Avoid:* key is (guild, user, action); `command_uses` has `guild_id` (migration 4005, nullable for a rollback); rows without a guild are skipped at the restart seed. Any per-user in-memory state must hold the guild in its key.

**A dropped sqlx transaction kept the push lock after the answer.**
sqlx only queues the ROLLBACK on drop; it runs when the pooled connection is returned in a spawned task, so the advisory lock (`lock`, `pg_try_advisory_xact_lock`) outlived the response and the next PUT or Push got "a push is running" (about 1 in 60 runs of `draft_is_saved_discarded_and_pushed_only_when_safe`).
*Avoid:* a transaction that holds an advisory lock which others try-lock ends with an awaited `rollback` or `commit` on every path before the answer, early returns included (`release` in `dashboard/src/channels.rs`; the whole push runs in one task that releases at the end). Drop is only the fallback for a cancelled request or dead process. Other `pg_advisory_xact_lock` users (`bot/settings`, `bot/tickets`, `dashboard/store.rs`, `core/cases.rs`) wait instead of trying, so a late ROLLBACK only delays them.

**Advisory locks on raw ids share one key space.**
`report` locked the reporting owner's user id, then `add` locked the reported user's id, both as plain `pg_advisory_xact_lock(id)`. Owner A reporting B while B reports A took the two keys in opposite order: deadlock.
*Avoid:* give each kind of lock its own key, `pg_advisory_xact_lock(hashtextextended('<kind>:' || id, 0))` (as `raider_user:`, `raider_owner:`, `channel_drafts:`). Other raw locks (`cases::create`, ticket numbers, config saves) take one guild id per transaction, so they cannot cross.

**A count checked a cap, then a second statement inserted.**
`token_create` counted live MCP tokens, then inserted in a separate statement: parallel requests at 9 tokens all saw room (up to 20 made against a cap of 10). `propose` (open MCP changes, each a DM to the owner) and message reports (10 per reporter an hour) had the same gap. A single `INSERT … SELECT … WHERE (SELECT count(*)) < n` does not help under READ COMMITTED: parallel statements do not see each other's uncommitted rows.
*Avoid:* count and insert in one transaction under `pg_advisory_xact_lock(hashtextextended('<kind>:' || key, 0))` (`mcp_tokens:` and `mcp_writes:` global, `reports:` per guild and reporter), taken right before the insert and never held across a Discord call. A unique index is enough when it already lets only one win (`appeals_one_open`). Already safe: appeals daily limit (unique open index); Raider List report cap, ticket numbers, config saves (locked); Ban Sync hourly cap (sequential jobs; an owner's import can overlap a share job by a few, left as is); in-memory caps (rescue claims, verification remakes, 2FA fails) check and push under one Mutex.

**A cache filled after an await kept an older value than the NOTIFY that cleared it.**
`App::cfg` read the newest config, awaited, then inserted it. A save whose NOTIFY removed the entry between the read and the insert left the older config cached until the next save. *Avoid:* the config cache has a generation that every forget moves, and a load caches only under the generation it started with (`CfgCache`). Any lazy cache with an external invalidation needs the same.

**A try limit was checked in one statement and counted in another.**
MCP confirm compared the DM code in one UPDATE and counted a wrong code in a second, so parallel confirms all reached the compare before the count hit 3: about N guesses per change instead of 3. The cap was per change and a refused change frees its slot, so a token could loop propose and guess without end (each change DMs the owner).
*Avoid:* the compare and the count are one UPDATE with `attempts < MAX_TRIES` in its WHERE, so the row lock queues parallel guesses and no code is compared past the cap; a right code costs no try. A token that sends 9 wrong codes in 24 hours (three changes' worth, counted by `attempts`, so a change left to expire still counts; refused-only counting let two misses and an expiry escape) is revoked with its open changes closed (`revoke_if_guessing`); the claim UPDATE also needs a live token (a confirm already past the token check cannot run); the owner gets a DM and makes a new token to use MCP again (owner decision). Already atomic: dashboard 2FA (`auth::attempt`, one mutex), rescue claim (one mutex), job queue.

- **A lookup by Discord message id had no index.** `message_sends` is read by `posted_id` on every press of a saved message's menu or button (`msgmenu`, the sticky cleanup), but only `embed_id`, `guild_id` and `webhook_id` were indexed. *Avoid:* a table read from an interaction gets an index on the id the interaction carries, in the migration that adds the read (4039 adds `message_sends_posted`).

- **A wrong "left" mark would have purged a server the bot is still in.** `on_ready` marks every server missing from READY as left, and the hourly purge deleted its data 30 days later without asking Discord. A sharded bot's READY does not list every server. *Avoid:* `welcome::purge_removed` asks Discord (GET guild) about every marked server each hour: an answer clears the mark, 404 or 403 with code 50001 purges once due, any other error (Cloudflare 403, 5xx) waits an hour (test: `a_wrongly_marked_server_is_not_purged`).

**A restore into a new Postgres stopped on the MCP role.**
`pg_dump` writes the grants to `tommybot_mcp` but not the role or its `ALTER ROLE ... SET`, so `restore-test.sh` (`ON_ERROR_STOP=1`) failed, and a real restore lost the read-only setting; the migration that makes the role never runs again. *Avoid:* anything a migration makes outside the schema (roles, role settings) is made again by `db::set_mcp_password` on every start with `MCP_DB_PASSWORD` set (settings and connection limit too), and a restore creates the role first. restore-test.sh runs the exact DEPLOY.md restore (schema replaced in one transaction) and checks the role's grants.

**Member lookups on scheduled_jobs scanned the table, and fake report ids collided.**
Every member update with "Remove Main Roles on TO" on ran a `payload->>'user'` DELETE with no index. Native AutoMod reports used seconds times 1000 plus a random byte as the message id, so blocks in one second hit the unique key and were lost. *Avoid:* migration 4006 indexes `(guild_id, kind, payload->>'user')`; a made-up key uses milliseconds plus 20 random bits.

**Hourly prunes and the anti-nuke seed scanned whole tables, and the first prune deleted months in one statement.**
The `action_log` and `mod_actions` prunes and `seed_windows` filter on `created_at` alone, but both indexes lead with `guild_id`. Unban and appeal checks filter `action_log` by guild and target, the dashboard bell `appeals` by user: no index either. *Avoid:* a query that filters on a column no index leads with gets one (migration 4009, plain `CREATE INDEX` because sqlx runs each migration in a transaction); a prune of a large table deletes in batches (`welcome::prune_batched`, 10,000 rows a statement).

**Rows pruned only on their next use outlived the promised time.**
`verify_ips` was pruned only when someone verified on the web and `verify_timeouts` only on the next write for the same server, so a quiet server kept user ids past the 30 days and 1 day PRIVACY.md states. *Avoid:* every retention PRIVACY.md promises has a global prune in `welcome::purge_left`'s hourly list.

**Stored rows outlived the one use they had, and a "salted" hash could be reversed.**
`verify_ips` was kept 30 days while the alt check reads only the last day, and its hash was SHA-256 of the OAuth client secret, the server and the IP: the secret sits in .env and in the MCP container, and all IPv4 addresses can be tried, so the addresses could be recovered. Every NSFW scan, clean or not, kept the member, channel, message and the model's scores. Moderation records (cases, notes, reports, appeals, tickets) and config history had no time limit. Root cause: retention was picked from the feature, not from what the reading query needs, and a pseudonym was keyed with a secret that has other uses. *Avoid:* keep a row only as long as the longest window its readers use, and store only the columns they need (a clean image needs its hash, not who posted it); key a hash that must not be reversed with a key no other service, file or dump holds (`verify::ip_hash` makes one at start, in memory); a record type with no natural end gets a per-server limit (`retention` section, `bot::retention`), and a sweep never deletes an open item, a running timed action, the current config or the row a number sequence is read from (`MAX(case_no)`, `MAX(number)`).

**A data delete kept a member's live warn and then cleared its points anyway.**
Owner rule: warns stay until they expire. `PLACES` keeps a warn that still counts, but `ANONYMIZE` then set `user_id = 0` on every case the delete left, and `warn_points` reads by `user_id`, so an approved `/mydata delete` wiped the warn points at once. Nothing removed the kept warn later. Root cause: "kept" was written for the delete but not for the step that strips the person from what is left, and a row kept "until it ends" had no one to end it. *Avoid:* every step of a person-level delete uses the same keep condition (`CASE_KEEP` and the same live test in `ANONYMIZE`); a row kept until it ends names what removes it: `persondata::sweep_kept` runs hourly from the scheduler and finishes done delete requests for rows made before the request, never later ones: an ended warn, a handled report or appeal, a closed ticket. It reads every done request, with no time window (a window of one warn life would leave a warn that a restored backup brings back); migration 4040 adds the indexes by person it needs. Tickets lose the person only when closed, and the "Not NSFW" rows are the server's.

**A first draft of the data delete removed the person's dashboard 2FA, open items and the newest case.**
With the authenticator row gone, whoever holds the Discord account could enrol a new one by DM code; deleting the newest case let its number be given to another member. Root cause: the delete list came from "every table with the user id", not from what each row is for. *Avoid:* a person-level delete (`core::persondata`) never deletes a credential, an open item (report, appeal, ticket), a running timed action or the row a number sequence is read from; those are kept or lose the person (`ANONYMIZE`). An export leaves out other people's ids and text that can name them (report reasons, which servers reported a raider).

**PRIVACY.md said staff see what their Discord permissions allow.**
Only permits give access to Brim data; Discord permissions give none. *Avoid:* the notice uses the same words as the code's rules ("permit", "Discord permission"), and is read again when access rules change.

**One server whose purge failed stopped the purge of every server after it.**
`db::purge_left` used `?` in its loop, so a lock timeout on one server kept the others' data. *Avoid:* a loop over independent items logs a failed one and goes on.

**Case and ticket numbers took the config lock.**
`cases::create` and `tickets::claim_number` locked `pg_advisory_xact_lock(guild_id)`, the same key as the config saves (`settings::locked`, dashboard `store.rs`), so they queued behind each other, and a numbering call inside a config transaction would deadlock. *Avoid:* the bare guild id is only the config lock; every other lock uses its own key, `hashtextextended('name:' || id, 0)`.

**Removed Raider List entries and their evidence were never deleted.**
`expire` deleted rejected and old pending entries but not `removed` ones, so evidence (reporter ids and notes) stayed for good, while PRIVACY.md said evidence goes with its entry. *Avoid:* every status has an end; a removed entry goes after 30 days once no server has a list action left to lift (the lift reads the row).

**PRIVACY.md promised retention the code does not do.**
The Message Builder row said an unused avatar goes "after 1 day", but `msghooks::gc` runs only when that server uploads or deletes; the Yes/No row said 10 seconds where `confirm.rs` deletes rows older than 70 seconds. *Avoid:* a retention line names the trigger and the age the DELETE uses (read the query, not the constant's name).

**PRIVACY.md missed tables and said message text is never stored.**
Reports (300 characters of the message), appeals, raid log, staff lists, sticky roles, lock updates, Message Builder, MCP and update records had no row; `verify_ips` (salted IP hashes, 30 days) had none; `guild_owners` said "deleted on leave" (it is the 30-day purge); optional third parties (Cloudflare, the AI connector, off-site dumps) were not named. *Avoid:* a new table with user ids, user text or anything about a user gets its row in PRIVACY.md (what, why, how long), and a new outside service its line under "Optional services", in the same change.

**A 5-second job scanned the whole cases table.**
`jobs::expire_cases` runs on every scheduler tick (5 s) with no index for `active AND expires_at < now`. *Avoid:* a job that runs often gets a partial index that matches its WHERE (migration 4004, `cases_expiring`).

**Tables with personal data had no cleanup.**
Expired `dash_session` rows (with the Discord access token) and every `action_log` row stayed forever, while PRIVACY.md promised sessions expire and did not list `action_log`. *Avoid:* a new table that stores user ids gets a retention line in PRIVACY.md and, if time-limited, a DELETE in the hourly list in `welcome::purge_left`. Sessions go when expired, `action_log` after 90 days (owner rule), except Brim's own `quarantine` rows of a live quarantine, which `joingate::missed` reads to spot rejoins. An action older than 90 days can no longer be undone from the dashboard.

**Two PRs used the same migration number.**
Git merges them without a conflict, then sqlx fails every test with "duplicate key _sqlx_migrations_pkey". Two merged PRs that each added `4049_*.sql` also stopped every start: a fresh database failed on the second insert into `_sqlx_migrations`, and a database that had one refused to start ("previously applied but has been modified"). *Avoid:* parallel work gets its own number range; the coordinator gives each builder its number; before merging several PRs and after rebasing on main, `ls crates/core/migrations` and look for duplicate prefixes. A test fails on two files with one number (`db::tests::migration_numbers_are_unique`).

**Old migrations are frozen.**
sqlx stores a checksum, so editing an applied migration breaks every existing database. *Avoid:* never edit an old migration, not even a comment. Write a new one.

**A column that replaces another goes stale after a rollback.**
The new `embeds.message` replaces `embed`, and the new code still writes `embed` so the previous image works after a rollback. But the previous image edits only `embed`, so after a roll forward the readers took the old `message` and the edit was lost. *Avoid:* a trigger clears the new column when an update changes only the old one (`embeds_stale_message`), and readers fall back to the old column (`embeds::MSG`). Drop the trigger with the old column.

**A default change must not overwrite user choices.**
*Avoid:* a migration that changes a default only moves rows that still hold the old default (600 → 60). Test it from an empty DB and from the old schema with data.

**A new "last activity" column backfilled from an old time makes a new idle rule act at once.**
Backfilling `last_activity_at` from `opened_at` would have let auto-close shut every old open ticket when a server first turned it on, though staff wrote in them yesterday. *Avoid:* when a column starts tracking something not tracked before, backfill live rows with `now` (unknown counts as fresh), and only finished rows with the old time.

**A new migration file was not picked up.**
`sqlx::migrate!` embeds the migrations at compile time, and adding a file does not make cargo rebuild `brim-core`; tests fail with "relation mcp_... does not exist". *Avoid:* after adding a migration, `touch crates/core/src/db.rs` before testing (CI builds clean). The same happens after `git merge` brings in a changed `RaidCfg`: touch `crates/automod/src/join.rs`. If a test fails right after a merge on code you did not touch, touch the changed crate's file and run it again before you debug.

**A row was found by its id alone, without its server.**
Many statements read or changed a row only by a global id (ticket channel, appeal, report, sticky, message rule, webhook, slowmode channel, raid code, confirm nonce). Every id came from a server-scoped step, so nothing leaked, but one later change (an unchecked id from a button, job payload or event) would let one server touch another's row. Root cause: the server was checked once, earlier and often in another function. *Avoid:* a statement keyed by an id that arrives from outside the function (parameter, job payload, button id, event) also says `guild_id = $n`; pass the server down (event `guild_id`, the job's `guild_id`, the handler's path). Not needed when the same function just read, locked or inserted that row with its server, or for sweeps over all servers (retention, the job queue, the message-rule tick).

**Any database session can NOTIFY, also a read-only one.**
Postgres has no grant for NOTIFY, and `default_transaction_read_only` does not stop it, so the MCP role (or any other) could send `config_changed` and make the bot redo each guild's save work (rule sync, ticket category, Raider List scan). *Avoid:* the listener always drops the cached copy (cheap; a purge notice names no version), but runs the save work only for a version that is saved and newer than the last it handled (seeded at start). Compare version numbers, not `created_at` (the transaction's start, so a later version can carry an earlier time). Treat a notice as a hint to read the database, never as the change itself. A new role that must not write rows gets no INSERT grant; a channel it must not use needs a check on the listening side.

- **A person's data deletion rule that lived only in the code.** The proofs and edit history of a case the deletion keeps (the newest, a running timed action) were deleted by two statements in `persondata::ANONYMIZE`. An older image (after a rollback) runs its own list, which does not know the new tables, so the member's message copy stayed. *Avoid:* a table that hangs on another table's row gets its deletion rule in the migration (ON DELETE CASCADE, or a trigger such as `case_forget_person`), so every image obeys it.

- **The copy trigger for an old column only added.** The trigger that copies `cases.proof` written by an older image into `case_proofs` fired only for a new value, so a proof the older image cleared or replaced came back after the next update. *Avoid:* a trigger that mirrors an old column handles replace and clear as well as set, and has a test for each.

- **The dashboard's database role could write what only the bot may set.** The role had INSERT and UPDATE on every table. SQL run as the dashboard could set `case_proofs.verified` (the bot's own copy of a member's message), change `reports.content` (the bot copies it as verified proof when a moderator acts), point a case at another member (`cases.user_id`, `kind`), and rewrite history and log rows. *Avoid:* a table the bot writes and the dashboard only reads, marks or adds lines to is narrowed in `db::set_dashboard_role`: revoke table-level INSERT and UPDATE and grant only the columns the dashboard's routes change (`cases`: reason, active, proof; `reports`: status, handled_by, handled_at; `case_proofs`: INSERT of the staff columns), and write the staff statement with only those columns. Before narrowing, grep every dashboard and core statement on the table, row locks too: `SELECT ... FOR UPDATE` needs an UPDATE right on at least one column (the proof removal locked a `case_proofs` row and would have failed with "permission denied"). `dashboard_role_has_rows_only` connects as the role, checks each refusal by its error code (42501) and runs what the dashboard does do. The dashboard's unit tests and the browser test connect as the owner, so they do not see a missing right: run the browser test once with the dashboard connected as `tommybot_dashboard` after a grant change.

**Role names written into SQL broke with the rename.**
Migrations 4035 and 4043 compared `current_user` with the literal `'tommybot_dashboard'`, and every MCP grant named `tommybot_mcp`, so a server on the Brim names (`brim_dashboard`, `brim_mcp`) would have lost the dashboard's row limits and the MCP role all its views. Root cause: the role name was a constant in SQL, the code and the compose file at once. *Avoid:* the code uses the Brim names only, and `db::connect` stops at start on a login under the old names (before any migration or role change), the bot grants the MCP views at start (`set_mcp_password`), and SQL that must know the dashboard's role names both (migration 4056). A new check on the dashboard's role in SQL names both names.

**An update could not be undone with its migrations, and a restore could half drop the database.**
The updater took no dump before the new image ran its migrations, so a rollback restored only the old images (not, for example, the column migration 3989 dropped). The DEPLOY.md restore piped into psql with no stop on error and no transaction, after the dump's DROPs. With a pinned tag the update's `up -d` kept the old container, whose restart count failed the health check. *Avoid:* the updater dumps with the server's own `pg_dump` (a newer pg_dump writes settings an older server refuses) into `./pre-update`, after the pull and the same-version check, so a run that changes nothing never rotates out the dump from before a migration. It stops before any restart when `/backups` is not a mount (new image, old compose file), when free space is under twice the database, or when the dump fails or passes its timeout (run inside the container, so it stops pg_dump itself). A restore checks the file (`gunzip -t`), drops and makes `public` again, and runs in `--single-transaction` with `ON_ERROR_STOP=1`; the bot starts only after it succeeded (`&&`). Every `up -d` the updater health checks uses `--force-recreate`.

- **A restore brought back deleted servers and revoked grants, and dumps left the server readable.** A restore replaced the whole database with the dump, so every server purged and every Extra Owner, Trusted Admin, permit holder, rescue key, dashboard 2FA and MCP token removed after the dump came back; the off-site copy was a plain gzip; its rclone image was pinned by tag only; the same rclone key could delete every off-site copy. *Avoid:* a grant or server removal leaves an `erasure_log` line (migration 4035, deferred constraint triggers, so a delete-and-insert in one transaction such as a permits save logs nothing), and `scripts/restore.sh` carries the live log into the restored database and calls `restore_erasures`. A new table that holds a grant gets the trigger in that migration's list. Every daily dump, the 7 local copies too (the updater's `pre-update` dumps are not), is age-encrypted to `BACKUP_AGE_RECIPIENT` and the private key never sits on the server, so anything unattended that reads a dump (the monthly restore test) runs on the plain dump inside `backup.sh` before it is encrypted; the backup key has no delete right and the bucket's object lock keeps copies 30 days; images that scripts run come from `docker-compose.yml`, pinned by digest when they get a credential, so Dependabot updates them.
