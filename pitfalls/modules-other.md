# Pitfalls: Other modules

Index and rules: [PITFALLS.md](../PITFALLS.md).

**A cleanup of Brim's webhooks knew only one of their users.**
`message_webhooks` held only Message Builder webhooks, so the 30-day sweep (`msghooks::sweep`) and the dashboard `forget_unused` deleted a webhook no saved message used, which would take a feed's webhook too.
*Avoid:* every query that deletes rows of `message_webhooks` (or the webhooks) also keeps a channel that a feed posts in (`not exists (select 1 from feeds ...)`). A new user of that table adds itself to both queries.

**A timed thread lock never ended.**
`lock_marked` queued an `unlock` job for timed server locks but not thread locks, so `t!lock 1h` in a thread stayed locked. *Avoid:* the thread branch queues the same `unlock` job with its `lock` kind, and a thread lock or unlock first drops older timers of that thread (`forget_timers`), so an old timer cannot lift a newer lock. The dashboard's "unlock all" does not delete every `unlock` job: it does not lift threads, so their timers stay, and the bot drops the timer of each lock it lifts.

**An invite diff per join picked a code by luck.**
`used_invite` fetched invites in each join's own task, so fetches could finish in either order and the older list overwrote the newer; it had no baseline after a restart, took the first grown code in HashMap order, guessed a vanished code as used and read a missing `uses` as 0. Root cause: a diff of shared state in parallel tasks, with a guess where data was unsure.
*Avoid:* events that must be diffed in order go to one actor per guild before `tokio::spawn` (`invites::observe` in `main.rs`), and an unsure match is stored as unknown (`invites::resolve`). A join arriving within 1 s after a fetch may already be in that list, so it joins the batch and the list is read again (up to 5 rounds); dropping the batch made every busy server and raid unknown and emptied `raid_log.invite_code`. A 403 on the list waits 10 minutes before joins ask again (403s count towards Discord's invalid request limit, which blocks the whole bot); GuildCreate seeds are spread over 10 s. A vanished code counts as its last use only when it was one use short of its limit; expired or event-deleted codes count as no use. A guild's actor checks it still owns the guild before each event, so a GuildDelete and quick GuildCreate never run two writers. No other state is diffed from REST in per-event tasks.

**A feed item without an id got a new random id at every read.**
The feed parser makes a random UUID for an RSS item with no `<guid>`, so the seen list never matched and the item was posted at every check. *Avoid:* `feed::parse` sets its own id (the item's first link, else its title); a test checks that an item with no guid has its link as its id.

**A fetch of an address staff typed is a request into the internal network.**
A plain client would fetch `https://169.254.169.254/` or a name that resolves to 10.x. *Avoid:* `feed::client` resolves through `PublicOnly` (each DNS answer checked by `is_public`), has no proxy (a proxy resolves the name itself, past that check), allows https on port 443 only, no IP literals and no user name in the address, checks every redirect hop with the same rules (`feed::safe`, at most 3), and stops at 10 s and 2 MB. Errors name the cause in plain words, never the inner address.

**A feed poller lost, doubled and stuck items.**
The poller saved the ETag before it handled the feeds, so a failed post was hidden by the next 304; a database write after Discord took the post failed the post, so the item went out again; a 400 from Discord broke the feed and the same item failed at every Check now; Check now on a paused feed posted; a good check never turned a broken feed on; a click during a check was wiped. *Avoid:* save conditional-request headers only when every feed on that address finished; bookkeeping after an outside side effect (a post, a DM) never fails that action; remember (skip) an item Discord refuses with 400 and still break the feed; a paused feed only does a test post; clear a request flag only if it is still the value the run answered. `is_public` also refuses `::/96`, site-local `fec0::/10`, `64:ff9b:1::/48` and Teredo `2001::/32`. Automod must not trust every message from a Brim webhook (anyone with Manage Webhooks can read its token and post past automod): it skips only the message ids Brim got back from its own sends (`feeds::sent_by_us`, which waits up to 5 s while a send in that channel is under way) and checks every other post and every edit.

- **One flag held "staff switched it off" and "waits for its open time".** The open job set `forms.open` on again at `opens_at`, also for a form staff had switched off later. *Avoid:* a job that turns a thing on checks that a person did not turn it off; `forms::update` drops `opens_at` when the form is saved off.

**A schedule edit kept `waiting_once`.**
The dashboard save reset `due_messages` and `issue` but not `waiting_once`, so after a "once" run waited out a pause, the first run of the new schedule was skipped with a wrong reason. *Avoid:* a save resets every run-state column the bot's enable path resets.

**A public endpoint takes GitHub and GitLab events from the whole internet.**
`POST /hooks/feed/<id>` needs no login. *Avoid:* only the address limit comes before the signature (a per-feed limit there lets anyone without the secret use up a feed's turns, and GitHub does not retry a refused delivery), the per-feed limit after it. Body stops at 1 MB; the signature is checked over the raw body before anything is parsed (GitHub: HMAC-SHA256 with `verify_slice`; GitLab: the token, compared in constant time). Unknown, paused or stopped feeds and a wrong or missing signature all answer a bare 404, so nobody learns which feeds exist. The secret is 32 random bytes, never in a list, log or error, shown once (add and "Make new secret", which kills the old one at once). A repeated delivery id, or the same signed body under a new id (the signature does not cover the id), is ignored for 7 days (`feed_events` unique keys). The bot posts queued events every 5 s, but a failure for now counts once a minute, so a short Discord outage does not stop the feed after 25 s. GitLab's confidential issues and notes never post. Event text is untrusted: the same checks as RSS items (scam, NSFW, the server's invite, link and word filters), and only the ping role is allowed as mention. GitHub's default webhook content type is a form: refused with a 400 saying to pick application/json, after the signature.

- **Saving a schedule vouched for text nobody checked.** The first build stamped the message as saved by the Trusted Admin on every rule save, so after a rollback an Editor's text (saved by the older image) got back the pings and webhook a Trusted Admin had set. *Avoid:* a schedule that is turned on vouches only for the version the page showed (`seen` = `embeds::VERSION`, refused on a mismatch or unsaved changes) and never for a save by an older image (`saved_at <> updated_at`); a rule that is off vouches for nothing.

- **A far date crashed the next-run math.** `NaiveDate` parses a year like `+262142`, and `local + Duration` panics on overflow, reachable by any Viewer through the preview route. *Avoid:* limit typed dates to a sane range when parsing, and use `checked_add_signed` in time math on user input.

- **The shortest repeat held per line, not per rule.** Ten daily times one minute apart, or "every 15" plus "every 16", passed the 15-minute minimum. *Avoid:* check the whole rule (`msgsched::too_close` over its next 400 runs) at save; the runner also skips a clock run less than 15 minutes after the last one (`last_clock`).

- **A restore sent a schedule at once.** Relinking a remade channel set `next_at = now`, which matched no line, so the runner picked any recent "once" line and could send it a second time. *Avoid:* a rule switched back on gets its real next time (`msgsched::next_of`); a "once" run is matched loosely only while marked as waiting out a pause (`waiting_once`).

- **A send-time check done only at save.** The schedule's channel was checked against log, ticket, verification and appeal channels only when saved; a later config change made the runner post there. *Avoid:* a check that guards a delayed action runs again right before the action.

- **A trigger answered a message automod removed.** Trigger answers were queued before `automod::on_message` ran, and the dashboard woke at once (NOTIFY), so a spam message with a trigger word got an answer before automod deleted it. *Avoid:* the Message Builder hook runs after automod in `events.rs`; the dashboard checks the message, member, timeout and quarantine again before it answers; a reply uses `fail_if_not_exists: true`.

- **A trigger answer skipped the rollback check that schedules have.** Schedules refuse a message an older Brim saved after a rollback (no rights check there), but trigger answers sent it. *Avoid:* every automated send (schedule, trigger, sticky) calls `msgrules::trusted` before it sends.

- **A sticky's repost pinged again each time.** `send_copy` forced no pings only for trigger answers, so a sticky with @everyone pinged on every repost. *Avoid:* every send that repeats by itself without a person pressing Send (trigger answers, sticky reposts) uses `allowed_mentions: {"parse": []}`.

- **A sticky's own new webhook counted as another bot.** The bot's cached list of Brim webhooks did not know a webhook made by the first send, so the copy it posted moved the sticky down again, in a loop, until the bot streak paused it. *Avoid:* a cache that decides "is this our own post" falls back to the database for an id it does not know (`message_webhooks`), and Brim's own user id never counts.

- **Two reposts of one channel mixed the sticky order.** Two dashboards during an update could repost one channel at once. *Avoid:* a repost holds `pg_try_advisory_lock` per channel on its own connection (released at the end, or with the connection if the process dies); a run that finds it taken goes back in the queue. A run caused only by bots reposts from the first sticky that follows bots and every one after it, so the order holds.

- **A sticky copy that could not be deleted was forgotten.** Moving or switching off a sticky cleared its stored copy id before the delete, so a failed delete left a copy nobody tracked. *Avoid:* a failed delete of a copy Brim posted is shown on the sticky (or in the answer) with "delete it by hand"; Brim only deletes copies by the id it stored.

**A feed address had to be the feed file itself.** Staff paste a site's normal address, and the add failed with "this is not an RSS or Atom feed". *Avoid:* `feed::find` reads the page and takes the feed its `<link rel="alternate">` names. The found address goes through `check_url` and the same guarded client as a typed one (public names only, https on 443, redirect, time and size limits), one hop only.

**GitHub's public list of events leaves out most of each event.** A push in `/repos/<repo>/events` has no commits, and a pull request has no title, link or author. *Avoid:* `feedfollow::body` reads each part again from its own `url` (only `https://api.github.com/`), and a push from the compare API, so `feedhooks::github_post` gets the body the webhook sends. The list says `merged` and `created` where the webhook says `closed` and `submitted`. The hourly limit (60 without `GITHUB_TOKEN`) does not count toward stopping a feed, and an unchanged list (304) costs nothing.

**A feed log line showed "Feed: GitHub (``)".** A webhook feed stores no address (GitHub or GitLab calls Brim), and its repository name came only with the first event that posts, after the "Feed Connected" line was queued; `feed_label` printed the empty address in a code span. *Avoid:* take the name from every signed delivery, the ping too (`feedhooks::take`), and from the pasted link when the feed is added (`repo_of`, `gitlab_path`); `label_of` leaves out an empty address, and one equal to the name. The poster name of posts stays GitHub or GitLab. Test: `a_label_never_shows_an_empty_address`.

**Check now said nothing, and a new feed posted nothing to test with.** The first check only remembers items, and Check now on a webhook feed did nothing. *Avoid:* Send latest posts the newest item (website, YouTube) or the newest event of a switched-on kind (GitHub, followed or webhook: the public events list, at most 5 events read), even one posted before, under a new delivery key. One at a time per feed (refused while one waits), not counted as a failed check. GitLab webhook feeds and private repositories say how to test instead (GitLab's Test button, GitHub's Recent Deliveries > Redeliver).

## A module switch must reach every reader of its parts
- The `modules` section holds the master switches of Server Joins, Messages and Logging (a missing switch is on). `GuildCfg::parse` applies them: Server Joins off turns Join Gate, Join Raid (with voice raids), Verification and the Raider List off in memory; Logging off makes `LogConfig::target` drop event logs. Stored part settings stay as they are.
- Readers of raw config were missed: the Raider List SQL queries, the dashboard web captcha, the Overview health list, and the standard channel set gate (`config_gate`), which would hide channels from @everyone while no verification ran. A part write that turned the module on also fired on a save of a part that was already on.
- *Avoid:* code that reads a part's `enabled` from raw JSON or SQL also reads `modules.<module>` (`brim_core::sections::module_of`). A write turns the module on only when it turns the part on from off, and then needs the `modules` bar (Trusted Admin with 2FA).

- **A winner role was taken away while a later win still held it.** A member who won the same winner role in two giveaways lost it when the first role time ended, and a second win while they still had the role queued no removal (the role counted as "had before"). *Avoid:* a due role removal skips while another removal for the same member and role waits in the future (`giveaways::role_off_waits`), and a win for a member who has the role adds its own removal when one waits. The member keeps the role until the latest role end time. The running job is due, so it never counts itself; a test that calls the job must make its row due first.

## Giveaway card pictures

**The giveaway cards show their facts as fields.** The default running and ended messages keep Hosted by, Sponsored by and the requirements as lines under the title, and Ends, Entries and Winners as inline fields (the ended card adds a full-width Result field, `Ends` reads just "Ended", and `{ga_winner_count}` is the number asked for). `drop_blank_fields` drops a field with an empty value. *Avoid:* a new fact needs its own field, never a line that can be empty next to a label. A server that saved its own copy keeps it; only the default changed. The place under the title is kept free for a host's own text later.
