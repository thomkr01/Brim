# Pitfalls: CI, build and release

Index and rules: [PITFALLS.md](../PITFALLS.md).

**Hourly log files had no size cap.**
A storm of errors could grow one hour's file to gigabytes on the volume Postgres shares. *Avoid:* `log::Capped` stops each hourly file at 100 MB with one notice line (stdout, capped by Docker, still has every line); 24 files keep the total bounded.

**Parallel worktrees shared one target and one DB.**
Cargo mixed crates from different worktrees, one branch's migration broke the others' tests, and four targets (about 7 GB each) filled the disk. *Avoid:* one `CARGO_TARGET_DIR` and one database per worktree (`su postgres -c "createdb X"`; `createdb -h localhost` hangs on a password prompt). Delete finished targets.

**Every push to a PR branch ran the whole CI twice.**
`ci.yml` had `push:` with no branch filter plus `pull_request:`, so each commit on a PR branch started every job (check, supply-chain, dashboard-ui, e2e, about 20 minutes) once per trigger. *Avoid:* `push` is limited to `branches: [main]` (the Images workflow still follows main's CI run); the PR gets its four required checks from `pull_request` under the same job names. A new workflow with both triggers needs the same filter. A branch with no PR gets no CI.

**The updater trusted the digests in a queued row.**
Only the dashboard checked GitHub's signed build record before it queued an `update_runs` row, and the dashboard's database role can insert such a row. A dashboard or database break-in could make the updater (the one container with the Docker socket) install any image in the repository. Root cause: a check by the writer of a request was trusted by its reader. *Avoid:* the side that acts checks again itself: `updater.sh` `attested` asks GitHub for the record of each digest and matches image name, digest, repository, workflow and `main` in SQL (psql is the only JSON tool there; the answer goes in with `\set` from a file). It fails closed: no answer or no record installs nothing. `ATTEST_URL` exists only for the e2e test's stub. The updater image changes only with the server command, so a change to `updater.sh` needs that command (the Update page warns).

**The hardening block covered only the two services that hold the bot token.**
`x-hardening` (`cap_drop: [ALL]`, `no-new-privileges`) was added to bot and dashboard only, so the MCP server, Postgres and the tunnel kept Docker's default capabilities. *Avoid:* every new service gets `*hardening`. Postgres needs `CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID` back for its entrypoint (without `DAC_OVERRIDE` it cannot read its own data folder at start). The updater gets only `no-new-privileges`: its Docker socket is root on the host anyway, and dropping capabilities could break the dump into a `./pre-update` owned by another user. A change to `docker-compose.yml` reaches the server only with the server command.

**A compose secret from `.env` cannot go into a `read_only` container.**
Compose copies a secret with `environment:` into the container at start and refuses a read-only one ("`file` is the sole supported option"). A `file:` secret is a bind mount, which the updater cannot recreate: it runs compose with the project at `/project`, a path the host does not have. *Avoid:* the bot token is an `environment:` secret and the bot and dashboard are not `read_only` (they drop all capabilities instead). Try a compose change on a real Docker daemon (`dockerd` runs in the cloud container) before you write it into DEPLOY.md. A variable set in the shell wins over `.env`, also for secrets.

**The Update page showed an older build as the newest.**
GitHub's `status=success` filter on the Images runs list left out a finished green run for over 15 minutes (the unfiltered list had it), so the page could neither show nor install the new build. *Avoid:* never trust GitHub's `status=` filter for something that must be current: list the runs unfiltered and check `conclusion == "success"` in our code (`update::runs_to_builds`, at most the 10 GHCR keeps). When the page is up to date on a commit the list does not have yet, "Newest" shows the running commit, never an older one.

**A failed cleanup of old image versions blocked every new image.**
The `delete-package-versions` step in each image job failed with "delete version API failed. Package not found" after it had deleted some old versions (most likely a child manifest GHCR had already removed with its index, left from builds before `provenance: false`). The updater job failed, the matrix cancelled the other three, `latest` was skipped, and the Update button had nothing new for hours. *Avoid:* housekeeping steps in the Images workflow run with `continue-on-error: true`; only build, push, attest and the `latest` move may fail a run. After a merge, check the Images run's jobs, not only that `latest` has not moved yet.

**A Postgres healthcheck passed before Postgres was up.**
On a fresh volume the postgres image first runs a temporary server that listens only on its socket, runs the init scripts, then stops it and starts the real one. `pg_isready` over the socket passed on the temporary server, so the next `psql` hit the gap. *Avoid:* every Postgres healthcheck (CI services, `docker-compose.yml`, e2e compose files) uses `pg_isready -h 127.0.0.1`; the temporary server does not listen on TCP.

**The approved-build Update had four holes.**
(1) An attestation looked up by digest alone also matched the same bytes copied into another package (the updater's image under `tommybot-bot`). (2) A stopped MCP container (`ps -a`) was started by an update and failed its health check, so every update rolled back. (3) A build whose dashboard still queued untargeted runs could be installed, and then no update from the page worked again. (4) The Images `gate` used a job-level `if`, so a run whose jobs were all skipped (a failed CI, or a fork's pull request from a branch named main) could count as a successful build in the dashboard's list. *Avoid:* `update::attests` reads the in-toto statement: subject name `ghcr.io/thomkr01/tommybot-<img>` with the digest, and the workflow `images.yml` on `refs/heads/main` of this repository (under its old name `thomkr01/TommyBot` or new name `thomkr01/Brim`, exact strings: GitHub records the name as spelled at build time). The updater adds mcp only when it runs (`ps -q --status running`), and refuses a dashboard image without `org.brim.update=digest` or `org.tommybot.update=digest` (images carry both, since an updater from before the rename reads only the old one). Workflow conditions that decide what counts as published are steps that cancel the run, never a job-level `if`. The updater checks `target_sha` and digests by regex in SQL (Postgres `$` is end of string; `grep -x` matches any line). An old updater's heartbeat keeps a stale `sha`, so read it only with a fresh `sha_at`.

**Every move of main became an installable build.**
Each push to `main` built four images (about 35 minutes) and the Update page offered each one: many half-step versions, no named version. *Avoid:* only a release is built and offered: a tag `vMAJOR.MINOR.PATCH` on a commit of `main`. Keep these rules when you change it. (1) `images.yml` stays a `workflow_run` of CI (filter `branches: ['v[0-9]*']`; for a tag push the CI run's `head_branch` is the tag name). A `workflow_run` run always uses the file as it is on `main`, so its signed build record names `images.yml` on `refs/heads/main`, which `update::attests` and `updater.sh` ask for. A `push: tags` trigger would run the tagged commit's own copy, which a branch commit can change. (2) The gate checks, as steps that cancel the run: CI passed on a push of this repository by its owner, and its `e2e` job passed (e2e runs for tags, on request and on a push that changed the dashboard or the browser test; a skipped job counts as passed, so the gate reads the job's own conclusion) (write access alone could tag an old commit as the highest); the tag is `v` plus three numbers; the tag (peeled for an annotated tag) names the commit CI checked; and `compare/<sha>...<main's sha>` is `ahead` or `identical` (main's sha from `ls-remote refs/heads/main`, never the name `main`: a tag named `main` would win). (3) `latest` moves only when the release is higher (`sort -V`) than the version label of the current `:latest`, so a re-run or a late older release never moves it back; it is not compared with the tags, since a higher tag that never built would hold it back for good. It is copied from the `:<version>` tag, not `:<sha>`, which two releases on one commit share. The package cleanup keeps 15 versions, more than the 10 releases listed, since a re-run adds a version. (4) The release goes into the image as the label `org.opencontainers.image.version`, part of the signed digest; the updater refuses an image without a release label, so an attested build of `main` from before releases is not installed. (5) The dashboard lists only runs titled `Release <version> at <sha>`, sorted by version, and looks up digests by the version tag, since two releases on one commit share the sha tag. (6) `image-cache.yml` builds the release while CI runs on the tag, only to fill the build cache: no push, no login, no attestation, only `contents: read`. It checks the parts of the gate known before CI ends (owner, tag, on main), so the shared cache holds only the owner's code from main; Images still runs its whole gate before it publishes. An updater or Update page from before this does not know releases: the server command is needed once, after the first release is out.

**The Update button kept installing an older version.** (also: two image builds could finish out of order)
CI runs finish out of order, so the oldest commit's run finished last. The `images` concurrency group runs one at a time in the order CI *finished*, and a waiting run is replaced by the next one, so the old commit was built last and moved `:latest` back, and the Update button could install it on a database a newer migration had already changed. The Update page read the newest successful Images run's `head_sha`, which for a `workflow_run` run is main's tip when it was queued, not the commit it built: it showed the newest commit as published, and each update pulled the old image and said "Updated". *Avoid:* the Images `gate` job builds only when its commit is still main's tip, and otherwise cancels its own run (cancelled, not skipped, since a skipped job counts as success). Each image builds only its `:<sha>` tag, in its own concurrency group, so a newer commit's build cancels an older one. The `latest` job checks the tip again and then moves all four `:latest` tags together, in a group that is never cancelled, so the images never point at different commits. The run title is `Release <version> at <sha>`, and `update::published` reads the release and commit from it. The updater refuses a download that is the version already running. Never read the built commit from a `workflow_run` run's `head_sha`. An older commit's `:<sha>` tag may never be built; that is fine, since the updater's rollback uses its local `:rollback` tag.

**Images were pulled by a moving tag.**
`rust:1-bookworm`, `debian:bookworm-slim`, `docker:28-cli` and the backup script's `rclone/rclone` (`latest`) changed under the same name, so two builds or backups of one commit could run different code. *Avoid:* name an exact version that is at least two weeks old (`rclone/rclone:1.75.2`). Postgres keeps its major tag (`postgres:16`): an exact minor pin can be older than the one a server already runs, and the `-alpine` variant would change the collation library under the data volume. The rclone pin is moved by hand.

**Dependabot would offer a Postgres major upgrade.**
The docker-compose ecosystem proposes the newest `postgres` tag, so a merged bump plus `docker compose up -d` starts Postgres 18 on the version-16 data volume, which refuses to start. *Avoid:* the docker-compose entry ignores `postgres` `version-update:semver-major`; a major upgrade is a planned pg_upgrade.

**Images were published for commits that failed CI.**
`images.yml` ran on every push to main on its own, so a commit that failed clippy or tests became `:latest` and the Update page offered it. "Keep 3 versions" also counted the untagged attestation manifests, leaving fewer real builds to roll back to. *Avoid:* `images.yml` runs on `workflow_run` of CI on main and publishes only when that run was a push and succeeded, from its `head_sha`. It stays a separate workflow, and keeps its name, since deployed dashboards read `images.yml` runs (`update::LATEST_URL`). A job-level concurrency group on the matrix needs `${{ matrix.target }}` in its name: one shared group makes the 4 legs cancel each other. The package cleanup keeps 10 versions.

**CI ran unpinned upstream code with the default token scope.**
`pipx install graphifyy` and `npm i playwright` took the newest release on every run, and only `images.yml` set `permissions:`. *Avoid:* pin every installed tool to an exact version, and give each workflow `permissions: contents: read` (a job that pushes images asks for `packages: write` itself).

**The UI build took new dependency versions without a commit.**
The UI crate's `Cargo.lock` was gitignored and the Dockerfile ran `cargo generate-lockfile`, so a bad upstream patch release could change or break the dashboard. `cloudflared:latest` had the same problem. *Avoid:* `crates/dashboard/ui/Cargo.lock` is committed; the Dockerfile runs `cargo fetch --locked`, CI runs the UI checks `--locked`, and the release build is `--locked`. Third-party images in compose name a version. After a UI dependency change, commit the new lockfile.

**An update could stay "running" forever.**
`updater.sh` has no `set -e` (its loop must survive), so when Postgres was briefly unreachable while `finish` ran, the row stayed `running`, the dashboard polled forever and hid "Update now" until the updater restarted. *Avoid:* runs happen one at a time inside the loop, so the loop fails any row still `running` every 30 s with an error that says the end could not be recorded.

**The backup was world-readable and ran `.env` as shell code.**
`backup.sh` wrote the dump (2FA secrets, session tokens) with mode 644, sourced `.env` (a value with spaces, `&` or `$(` broke the script or ran code), left `*.tmp` files after a failed dump, and `rclone delete` removed every file older than 30 days on the remote, not only dumps. *Avoid:* `umask 077`; read only `BACKUP_DIR`, `RCLONE_REMOTE` and `RCLONE_CONFIG_DIR` from `.env` as text; a trap removes the temp file; the remote delete has `--include '*.sql.gz'`.

**GitHub Actions were pinned by tag.**
A `uses:` tag (`@v7`, `@stable`) can be moved by its owner to other code; `images.yml` can push the images the updater installs. *Avoid:* `uses:` names a full commit SHA with the tag as a comment (Dependabot updates both). `dtolnay/rust-toolchain` then needs `toolchain: stable`, since it reads the toolchain from its ref name.

**Docs and config said what the code does not do.**
Cargo.toml named a licence with no LICENSE file, compose did not pass `PHISHING_LIST_URL`, `NSFW_LIST_URL` and `NSFW_THREADS`, `METRICS_ADDR` did nothing under Docker, the CHANGELOG named Postgres 18 for the database, an unused workspace dependency stayed, and the invite feature carried the name of another Discord bot (now Invite Tracking). *Avoid:* a new env variable goes into `.env.example` and, if the container reads it, `docker-compose.yml`; check a feature name against existing bot products first.

**Trunk's prebuilt wasm-bindgen needs a newer glibc.**
On the arm64 VPS `trunk build` failed with `GLIBC_2.38 not found`. *Avoid:* the Dockerfile builds `wasm-bindgen-cli` itself at the version the UI lockfile resolves to. Don't hardcode the version: read it from the `wasm-bindgen` entry of `crates/dashboard/ui/Cargo.lock`, before the UI code is copied in, so the build cache keeps this step.

**containerd deletes an untagged image.**
Rollback by image id failed because the old image was already gone. *Avoid:* the updater keeps the previous version under a `:rollback` tag.

**A `git pull` in the old folder would start the bot on an empty database.**
With `name: brim` in docker-compose.yml, a server set up before the rename (`~/tommybot`, project `tommybot`) that pulls the new file gets new, empty volumes `brim_*`: the bot would start in every server with no settings, permits or whitelist. The Update page also told such a server to run `git pull`. *Avoid:* the compose file needs `BRIM_NAMES=1` in `.env` (`x-names`), so the old folder refuses to start (`git checkout HEAD@{1}` goes back); the bot and the dashboard also stop at start under the old names, so no Update page runs there. The move itself copies the volume and renames database and roles in the copy, so the old volumes stay as the way back.

**The updater does not update itself.**
*Avoid:* a change to `docker-compose.yml` or the updater needs `git pull && docker compose up -d` on the VPS once.

**No logs without `RUST_LOG=info`.**
The bot prints nothing useful at the default level. *Avoid:* `live.sh` and compose set it.

**A new RustSec advisory turns the `audit` job red.**
*Avoid:* fix with `cargo update -p <crate>`. A new dependency can also pull a crate back to an older, vulnerable version (tract 0.21 pinned `time` below 0.3.42): after adding a dependency, diff `Cargo.lock` for downgrades. Ignore an advisory in `.cargo/audit.toml` only with a reason, as for RUSTSEC-2023-0071 (rsa only via the unused sqlx-mysql).

**Kept image tags could not be pulled.**
Each build pushed an index plus an untagged attestation manifest (3 package versions), and the cleanup keeps the newest 10 versions by date, so it deleted the image manifest under a tag it kept: `tommybot-bot:0d89861` returned 404 for its image while the tag still showed. *Avoid:* `images.yml` builds with `provenance: false` (one manifest, one version per build), the signed provenance goes to GitHub's attestation store (`attest-build-provenance`, not pushed to the package), and `imagetools create --prefer-index=false` so `:latest` is the same manifest as the sha tag. Before relying on an old tag, pull it or HEAD its manifest, not only the tag list.

**The patched twilight-model was outside every check.**
`vendor/twilight-model` is a path crate, so Cargo.lock has no checksum for it and cargo audit skips it; nothing showed whether its bytes were still the upstream release plus our one change. *Avoid:* `scripts/check-vendor.sh` (CI supply-chain job) rebuilds it from the crates.io release in `vendor/twilight-model.lock` plus `vendor/twilight-model.patch` and fails on any other difference, and CI runs `cargo audit -f vendor/twilight-model.lock`. On a twilight upgrade, update both files. A cargo audit that ran only when Cargo files changed, in its own workflow, did not stop an image either: it is a CI job, and Images publish only after CI passed.

**DEPLOY.md named a menu that does not exist.**
It said **MCP** in the top bar; the link is **MCP tokens** in the account menu. *Avoid:* when a guide names a button or menu, check its label and place in `crates/dashboard/ui/src/main.rs` (header) or the page itself. After a rename, grep every .md, CHANGELOG and README included, for the old label (a rename missed "new MCP page" in CHANGELOG.md).

**A rollback reported success without checking the old version.**
After a failed update the updater restarted the old images and wrote "running again" without a health check, so an old binary crash-looping on a newer migration was reported as fine. *Avoid:* the rollback recreates the containers (`--force-recreate`, so the restart count starts at 0), waits on the same `settled` check as the update and reports `failed` when the old version does not start. `tests/e2e/updater.sh` covers it with a marker file standing in for the migration. The old version must also run on the newer schema and config: `db::connect` sets `set_ignore_missing(true)` (so migrations must stay additive: never drop or rename what an older binary reads), and a key or enum value an older binary does not know drops only that entry (`brim_logging::lenient::{map, list}` on anti-nuke `limits`, logging `routes`/`events`/custom `events`, Raider List `categories`, Discord AutoMod `bot_actions`), never the whole section (anti-nuke off). A section that still fails falls back to defaults and DMs the owner once a day (`reply::fallback_alert`). A DM alone was missed with DMs closed, while the dashboard kept showing the section on: the alert also posts to the config-changes (or fallback) log channel, read from the raw config since `logging` may be the failed section, only when @everyone cannot read that channel (`events::public_with`, the log path's check without a config read); it posts nothing when `lockdown` (the main roles that check needs) is itself unreadable, and only to a channel of that server. The dashboard names such sections (`api::unread_sections`) in a red Overview row, a banner on the page and an off Quick Systems switch. *Avoid:* every enum-keyed map or enum list in a config section uses the lenient readers; a single enum field still fails its section, which is then announced. Writes still refuse such an entry (`sections::unreadable_entry` in the dashboard's `validate` and the bot's `check_section`), so only data a newer version wrote is ever skipped. That check first looked at the whole section, and the UI sends the stored section back, so after a downgrade every save of a section holding a newer entry was refused; it also checked only keys, so a bad value under a known key (`limits.Ban.enabled = "no"`, a route that is no id) was saved and then silently dropped; and `lenient::map` over the AutoMod `actions` dropped a whole rule for one unknown action. *Avoid:* `unreadable_entry(section, new, stored)` checks keys and values, and refuses only an entry that is not stored as it is (the rule `limits::check` uses with `old`); list items count as stored when the stored list holds them. A map of lists uses `lenient::map_of_lists`, which drops one item, not the entry.

**Each release compiled every Rust library again.**
The builder stage started with `COPY . .`, so any code change threw away the layer with the compiled libraries, and each image build took 8 to 10 minutes. *Avoid:* the Dockerfile copies only the manifests, the lock file and `vendor/` first, builds the libraries against empty stand-in crates, and then deletes every `brim*` artifact before the real code is copied, so no stand-in output can reach an image. A new workspace crate needs its own `COPY crates/<name>/Cargo.toml` line and a stand-in in that step; without it the build stops with a manifest error.

**The early image build ran beside the real one and saved nothing.**
CI on the tag ended in 7 minutes, the Image cache builds in 8 to 11.5, so Images started while the cache was still empty and compiled everything again. *Avoid:* each Images build job first waits (at most 20 minutes, and only waits) for the Image cache build job of the same release and target to end. The gate decides before that step; the wait never changes what is published.

- **Cloud env vars are read at session start.** A variable added during a session needs a new session.

**The updater image was the whole Postgres image, and Postgres ran with 100-connection defaults.**
The updater only needs `psql`: its image was 594 MB (amd64) instead of 183 MB. Postgres had `shared_buffers` 128 MB and `max_connections` 100 for a small database. *Avoid:* the updater copies `psql` and its libraries out of the pinned Postgres image onto plain Alpine of the same release (no package install; the `pgclient` stage in `Dockerfile`); a new `psql` library dependency shows as `not found` in `ldd /usr/local/bin/psql` inside the image, so check that after a Postgres image bump. `max_connections=40` in `docker-compose.yml` must stay above the worst case of all pools plus listeners (bot 10+2, dashboard 10+2, MCP 3, updater, dumps, admin about 33): add a new pool to the comment and the number when a service or a pool grows, or connections wait for the 30 s acquire timeout.

- **The backup scripts were not executable.** `backup.sh` and `restore-test.sh` had mode 644, so the crontab lines in DEPLOY.md (`~/tommybot/scripts/backup.sh`) failed with "Permission denied" and no dump was made. *Avoid:* a script DEPLOY.md runs by its path is committed with mode 755 (`git ls-files -s scripts` shows 100755).

- **The restore test left a plain copy of the database behind, and leaked rows into its log.** `restore-test.sh` removed its Postgres container with `docker rm -f`, but the image's data folder is an anonymous volume, so every run left the restored database (2FA secrets, session tokens, deleted data) unencrypted under `/var/lib/docker/volumes`. Its psql errors went to the log with DETAIL and CONTEXT lines, which quote rows. A typo in `BACKUP_AGE_RECIPIENT` made `age` fail inside the dump pipe, so no copy at all was made. *Avoid:* a throwaway container that holds data is removed with `docker rm -fv`; a log gets only psql's ERROR line; a key is checked (`age -r KEY < /dev/null`) before the dump, and a bad key falls back to the plain copy with a message.

- **One Discord 502 left the emoji set half replaced.** `tools/emojis.mjs upload --replace` deleted an emoji, then created it, and retried only 429. One 502 on a create stopped the run (and printed the whole HTML page) after some emojis were new and one was deleted. *Avoid:* every Discord call in a tool that changes many things retries 429 (with `retry_after`), 502, 503, 504 and network errors with a backoff, and prints a short error line, not the body. Draw the new image first, then delete, then create. A failure of one item must not stop the run: count replaced, created and failed, and print the exact rerun command for the failed names. Not tested against Discord with an error.

## An identity value from a failed lookup went into a commit

**A commit author email held an error text.** The email was read from a lookup that failed, and the failure text was stored as the value. It showed in the author and committer of a pushed commit and pointed to a tool. *Avoid:* set the author name and email as fixed literal values in the repo config, never from a command or an API call. Before every push, print `git log --format='%an <%ae> | %cn <%ce>'` for each commit to be pushed and read it. A wrong value in a pushed commit is not fixed by a new push: the commit stays public on its branch until the branch is deleted.
