# Pitfalls: Permits and levels

Index and rules: [PITFALLS.md](../PITFALLS.md).

**Enforce permits stopped at the first role it could not remove.**
The loop used `?` on each removal, so one 5xx left the other dangerous roles on with no log. *Avoid:* a loop over independent items logs a failed one and goes on; the log names what was not removed (`outcome`).

**The report Delete button skipped immunity, and chat showed settings panels to every permit.**
`reports::act` deleted the reported message of an Owner, TA or any permit holder, while `purge` of one member refuses them; every failure said "it may be gone". `settings::try_run` showed `Op::Show` panels (for example the anti-nuke caps) to anyone with a permit, while the dashboard needs `dashboard_view`. *Avoid:* a second way to do the same thing runs the same check as the main way: the Delete button runs `permits::check` on the author and maps errors with `http_err::gone_any` and `why`; a settings panel needs Dashboard Access or Dashboard Edit, as the dashboard does.

**Commands, joins and the dashboard skipped immunity for the member they acted on.**
`note remove ID` (without `@user`), `note modify`, a note sweep by author and `purge N @member` had no target, so `permits::check` never ran: a moderator could rewrite notes about themselves or an Owner, wipe the Owner's notes, or purge an Owner's messages. The dashboard's case edit and note edit, delete and sweep had no check at all. Verification's `on_join` and `deadline` never asked `is_immune`, so "quarantine on join" stripped a rejoining EO or TA, and the time limit kicked them. *Avoid:* every action on a member's record or messages finds that member first (the note's or case's `user_id`) and refuses self and an immune member unless the actor is immune (`modcmds::run`, `records::subject_guard`). `purge N @member` goes through `ModCmd::target` and `permits::check` like ban, so it refuses self and every permit holder; only the role order check is skipped. An automatic action on a joiner asks `is_immune` first; a failed read keeps the action at join (contain first) and retries the job at the deadline. Web mode releases an EO who is still in a join quarantine instead of refusing them.

**An Extra Owner was asked about as if it were less than the owner.**
Rule: an Extra Owner is the same as the physical owner and can do all the owner can, and is fully immune, except two things: only the physical owner adds or removes Extra Owners, and only the physical owner holds the rescue key. *Avoid:* a new owner feature uses `Level::Owner` (owner or Extra Owner) with 2FA for writes; use `api::is_discord_owner` only for the Extra Owner list, the rescue key and the other physical-owner things that already use it (handover Keep, purge). Ask owner decision only for a new physical-owner-only case.

**A verify permit could not verify a join-quarantined member by hand.**
With quarantine on join, the hold took back every role a held joiner got from someone without the quarantine whitelist, also the verification role a `verify` permit gave, and `verify::given` left it to the hold. *Avoid:* `hold`'s `on_join` branch calls `verify::grant` (the same path as the button: roles set, join quarantine row deleted) when a verification role is among the added roles and `given::may_verify` says yes (a person, not a bot, with `verify` or `quarantine`, or Owner, EO, TA). `given::hold_takes_it` returns false for such an actor on a join quarantine, so the two places agree. Any other role is still taken back.

**A listed bot kept user trust at runtime.**
GuildCreate removes bots from the EO, TA and quarantine whitelist lists, but until then (or after a failed check) `permits::resolve` and the hold still read them as listed. *Avoid:* `resolve` takes `bot` and skips the EO and TA tables for a bot (`App::level` passes `member.user.bot`), and `App::quarantine_listed` ignores a bot on the quarantine whitelist. The bot's role permits still count. Callers without a member at hand pass `false`; none of them grants trust to the actor.

**Discord can hand out a permit role by itself.**
Onboarding answers, linked roles and server subscription or purchase roles are given by Discord, with no actor in the audit log for the take-back guard to judge. A permit on such a role is a permit for anyone. *Avoid:* `api::permit_roles_ok` refuses newly added permit roles with tags `guild_connections`, `subscription_listing_id` or `available_for_purchase`, or listed in `GET /guilds/{id}/onboarding` prompt options (404 is no Onboarding; any other error refuses). A bot's own role (`bot_id`) stays allowed. At runtime `App::level` drops linked and subscription roles (`GuildInfo::unpermittable`) when the guild info is cached; Onboarding roles are not marked in the role tags, so they are caught at save only.

**The slash form of the general commands skipped two gates.**
`general::slash` checked only the permit, so `/about`, `/info`, `/invites` and the rest answered with "Use slash commands" off and had no cooldown for members without a permit, unlike the prefix form and the moderation slash commands.
*Avoid:* when a command has a prefix and a slash entry, give both the same gates (`use_slash` with the Owner/Extra Owner exception, `App::cooled_down` for no permit). Moderation slash already checks `use_slash`; tickets have their own staff gate.

**A permit sync gave a role to a member quarantined during the run.**
`permit_sync::roles` read the quarantine list once, then made one REST call per change for minutes. *Avoid:* right before each give, check the quarantine again and skip the member as held; after a give, check again and take the role back if a quarantine began during the call (its saved roles miss it). A long loop of REST calls re-reads any state a guard depends on.

**The first permit migration ran one query per member under the config lock.**
`migrate_members` ran a SELECT per member inside `settings::locked`, so on a big server every config save waited. *Avoid:* read the permit roles once and query only members who hold one. Keep work under `settings::locked` small.

**A role's Discord permissions made its members staff.**
Automod, activity heat and auto slowmode exempted anyone whose roles had Manage Messages, Administrator and the like (`App::staff_by_perms`, `slowmode::exempt`), during a Role lock by the saved permissions too. A raider given such a role before a panic stayed exempt for the whole lock; anyone with Manage Roles could hand out exemptions. Two sources of trust: permits and Discord permission bits.
*Avoid:* use our permits, not Discord permissions (owner decision). Exemptions, staff status and immunity come only from permits, whitelists and Owner/Extra Owner/Trusted Admin (`App::whitelisted`). Discord permissions only judge whether a role or channel is dangerous or visible. A failed permit lookup counts the message (`slowmode::exempt`): lookups 429 during a raid, and failing open exempted every raider. `misc.staff_only_permitted` has no effect now: still parsed so old configs load, values kept, hidden from the dashboard.

**A transferred server kept its old owner's trust.**
Ban Sync groups servers by Discord owner, so a server transferred to you joined your group with sharing on and could ban people in all your servers; the DM said it had left its group. Its Extra Owners and Trusted Admins (set by the old owner) kept full control. An owner change only moved the server between groups; it never asked whether the new owner wants what came with it.
*Avoid:*
- On an owner change (`bansync::on_owner`, GuildCreate and GuildUpdate) switch `ban_sync.enabled` off and remove EO/TA in one transaction with the `guild_owners` update and a config version, store what was removed (`owner_handovers`, migration 3920), and let only the new Discord owner keep it (Overview row "Ownership changed", `ops::keep_staff`). Keeping never turns Ban Sync on; the new owner does that with 2FA, and it then groups with their own servers.
- The dashboard memoizes the Discord owner for 30 s, so the old owner could still switch Ban Sync on or add himself as Extra Owner: `api::is_discord_owner` (used by every owner-only write and `level_of`) also refuses when `guild_owners` names someone else or the user is `owner_handovers.old_owner`.
- EO/TA were not all: permits the old owner set stayed on (his alt with an owner, full-immunity or dashboard-edit permit kept power); the card gave back all staff with one click and showed only counts; a rollback to a version from before the change wrote old EO/TA, permit roles and `ban_sync.enabled = true` back; `keep_staff` took row locks before the config lock (reverse of `on_owner`: deadlock); `on_removed` deleted the `guild_owners` row, so an owner change while the bot was out looked like a first sight. Fix: `on_owner` also deletes the roles of permits with `owner`/`dashboard_edit` or the `all` whitelist and stores them (`owner_handovers.paused_roles`, migration 3921), names the weaker permits that stayed on (`other_permits`, listed by the card and the Ban Sync page: `ops::weaker_permits`), and records a handover row on every owner change. Overview shows one row per paused person or role (name, id, previous owner marked), each with its own Keep, plus Dismiss. `api::rollback` keeps EO, TA, the roles of strong permits and Ban Sync off for a version older than `owner_handovers.at` and says so (`held`). Every dashboard writer of the permit tables takes the config lock first (`store::write_permits`, `keep_staff`, `claim_key`). `guild_owners` rows stay when the bot leaves; groups skip servers in `guild_left`; the next GuildCreate compares with the kept owner.
- The pause list named only `owner`, `dashboard_edit` and `all`, so permits with `antinuke`, `quarantine` or a `wl_*` flag, and the `antinuke.quarantine_whitelist` user ids, kept their exemptions; the rollback hold-back looked at the old version alone, so a permit made weak before the change got its guarded perms back. Fix: one rule in core, `permits::guarded`: every permit is guarded except perms outside `GUARDED_PERMS` with only `WEAK_FLAGS` (filter and report flags), so a new flag is guarded by default; `on_owner` and the dashboard's rollback both use it. `on_owner` clears the quarantine whitelist into `owner_handovers.quarantine_whitelist` (migration 3923), kept per person on Overview. A rollback never makes a role guarded again: a permit guarded in the old version keeps its current roles when guarded now, keeps its current perms when weak now, and comes back without roles when gone.
- The Ban Sync copy cancel ran after the commit, so a failure left the old group's copies pending and the retry found the owner recorded and did nothing: the cancel is in the transaction; after the commit only cache drops and best-effort DMs run.
- A failed `on_owner` was not retried, so the new owner had no Owner level until the next guild event: events call `bansync::owner_seen`, which queues `owner_check` on failure (reads the owner from Discord, retries on the job lease). The dashboard checks the memoized owner against a Discord answer at most 2 s old (`Discord::guild_owner_fresh`; a lookup error counts as not the owner): when Discord confirms the user but `guild_owners` still names the previous owner, the user keeps Owner level and a retry is queued, but owner-only writes (Ban Sync, Extra Owners, Keep, purge) wait until the bot has paused the previous owner's staff.
- A retry dropped after repeated failures was queued again on every dashboard request and filled the log: `owner_state` queues at most one `owner_check` per server and hour (per dashboard process). While that reset waited, the real owner could not remove the previous owner's Extra Owners: `put_permits` allows an Extra Owners change that only removes people when Discord confirms the user (`owner_state == Some(false)`), never one that adds.

- **An Admin-only check let every trusted admin through a permit-gated page.** `api::staff` and `access::page`'s `has` treat Admin as holding every permit, which is wrong for a permit meant to be owner-granted (View Mod Stats). *Avoid:* such a permit gets its own check (`access::mod_stats`) placed before `has`. `page_access` fetches permit perms for trusted admins too, and `keep_exemptions` stops non-owners from changing who holds it on save, rollback and import.

- **An empty list switched an authorization rule off.** "Only owners may hide a channel from staff" compared against the staff roles. A server without roles on the Admins and Moderators permits had none, so nothing counted as hidden and anyone could do it. *Avoid:* decide what an empty list means for the rule (here: every newly limited channel hides it from staff) and say in the refusal how to fix it.

- **A bot path had a lower bar than its dashboard twin.** `t!backups load` and `clear` needed only the Custom backups permit while the dashboard asked Admin + 2FA, and `load` ran during a lock (it put back the locked permissions). The dashboard's `backups` section and `lockdown.main_roles` were Editor level although they steer anti-nuke's revert, panic's restore and what the monitors guard. *Avoid:* a change that steers anti-nuke takes anti-nuke's bar (Owner/EO + fresh 2FA) on every path: the bot command (`commands::backup_cmd`), the bot settings panel (`main_roles` while a monitor is on), `put_section`, rollback and import (`api::main_roles_bar`). A restore refuses during a lock or panic in `backup::load`, which the dashboard's job goes through too. Deleting one backup is a clear done in steps (ten deletes empty the store), so `t!backups delete`, `/backups delete` and the dashboard's delete have the same bar, and they and `clear` refuse during a lock or panic (`backup::locked_or_panic`, `recovery::busy`). The Backups settings form is read-only below Owner.

**A second way to change something had a weaker check than the main way.**
Root cause: a rule was put on the path that was built first, not on the state it protects. Cases: (1) Chat config edits (`t!` settings rows, `t!logging`, `t!pingrole`) took any typed channel or role id, while the dashboard's `check_ids` refuses ids of other servers. (2) The hold whitelist flag `quarantine` on a permit equals the Owner-only quarantine whitelist, but `antinuke_exempt` and the Permits page lock left it out, so a Trusted Admin could grant it. (3) Backup create needed only Editor and the backups permit, worked during a lock or panic, and deleted backups past Max Images, while backup delete needs Owner or Extra Owner, 2FA and no lock or panic: ten creates were a clear. *Avoid:* when you add or review a path that changes some state, list every other path to the same state (dashboard, chat, slash, MCP, jobs) and give it the same check. Fixes: chat `resolve`, the two ticket commands and `t!whitelist` check ids against this server (removing takes an id as given); `quarantine` is in `antinuke_exempt` and the UI `owner_only`; backup create is Owner or Extra Owner (no 2FA) on the dashboard and in chat; `backup::save` refuses every backup during a lock, panic or nuke (also when the queued job runs, and checked after its snapshot, since panic can start during the reads); only automatic backups delete the oldest, and they skip a lock (its overwrites would become the restore source); a rollback runs `check_ids` and `check_held_roles` on every section it changes. MCP writes and Auto Setup need no change.

- **`false` passed for a known bot flag.** Callers that had the member passed `bot = false` to `permits::resolve`, so a bot still listed as TA got TA trust. *Avoid:* pass `member.user.bot` wherever the member is known; `false` only where only an id is known, with a comment.

- **A role carried a permit, so whoever handed out the role handed out the permit.** Manage Roles, a reaction-role bot or a level bot could give anyone a permit, and every guard (View Mod Stats) had to judge the giver. *Avoid:* a permit belongs to a Discord user id (`permit_members`, one permit per person); its roles are Brim's to give. `permit_sync` (GuildCreate, job `permit_sync` after a dashboard save) pages every member, and only after a complete paging: moves role holders to ids once per guild (`migrate_members`), forgets listed people who are gone, gives listed members their permit's roles and takes permit roles from everyone else, nobody punished (never managed, Discord-given or above-the-bot roles, never a quarantined member). Live, `guard_permit_roles` takes back a permit role given to anyone not listed, whoever gave it (Owner, EO and TA too), and `guard_permit_removal` gives a listed member's role back. A leaver loses permit, EO and TA (`permit_sync::on_leave`). Until a guild is migrated (`permits::members_migrated`) every lookup and guard reads the roles as before; new code that reads permits goes through `permits::top_permit`/`member_roles`, never `permit_roles` alone.

- **A permit by id outlived the quarantine and the leave.** When roles carried permits, a quarantine (strips roles) and a leave took the permit with them. By user id, a quarantined holder and a user no longer in the server still resolved to their permit in `top_permit`, `App::level` and the dashboard's `permit_perms`. *Avoid:* `permits::top_permit` gives no permit to a user with a `quarantines` row (both paths); `App::level` and `permit_perms` give nothing to a non-member (a fetch error stays an error, see "guild_member errors"), as `level_of` does for EO/TA; a dashboard save refuses a new permit member who is not in the server. When trust moves from a role to an id, list every way losing the role used to remove the trust and keep each one.

- **A missing key wiped data.** `write_permits` read a custom permit without `members` as "no members", so an old UI tab or older MCP client that saved a permit cleared everyone listed. *Avoid:* a new list field on a saved object keeps its stored value when the key is missing or `null`; only an explicit list, `[]` too, changes it.

- **A leaver's level was gone before the audit entry asked for it.** A kick or ban outside Brim is judged by the victim's level, but MemberRemove can run `permits::forget_member` before the MemberKick or MemberBanAdd audit entry comes in, and `App::level` gives a non-member nothing, so every kicked permit holder read as "no permit". *Avoid:* `permit_sync::on_leave` keeps the level a listed leaver held for 10 minutes (`permit_sync::left_level`, in memory) before it forgets them; `antinuke::guard_rank` reads that, else `permits::resolve` by id, and the live level only for a timeout. When code deletes trust on an event, check every later reader that judges the same event.

- **A leave and a later ban were read as one event.** `left_level` kept a leaver's level for 10 minutes, so a member who left by themselves and was banned by id later looked like a kicked or banned permit holder, and the actor was punished. *Avoid:* keep the leave time (wall clock) with the level; a kick or ban entry uses it only when the entry's snowflake time is not more than 5 seconds after the leave.

- **Security checks warned about a state the permit rules intend.** After permits went per Discord user ID, "Staff permit members" still warned when nobody was listed in the Admins or Moderators permit, but people are added only when needed. "Automod whitelist" read only the Whitelist page lists and told the owner to add "staff roles", although staff skip automod through their permit (Owner, EO and TA always; Admins and Moderators by the `automod` whitelist flag Auto Setup gives them). The wizard setup score had the same two points, and its notes said Discord permissions whitelist a member and left out the whitelisted permits. *Avoid:* when a trust rule changes, search the security score (`security.rs`), the wizard score and texts (`wizard.rs`) and the Overview links (`pages.rs`) for checks built on the old rule. A check about staff reads the permits, never the Whitelist page lists or roles.

- **A rollback's save kept a permission stamp it did not earn.** `saved_level` said a Trusted Admin saved the message, but the previous image's save changes the text without touching that column, so an Editor's text could ping after the roll forward. *Avoid:* a stamp that grants something is valid only together with a marker the older image cannot keep in step (`saved_at = updated_at`); any write by older code then voids it.

- **A role alone gave a permit before a guild's member migration.** `permits::top_permit` read `permit_roles` (a role holder had the permit) for every guild without a `permit_members_migrated` row, and four more readers had the same "unmigrated" branch (`antinuke::held_staff`, `raiders::not_collectable`, `automod::word_exempt_roles`, the Overview handover card). *Avoid:* a permit belongs to user ids only (`permit_members`); `top_permit` and `resolve` take no roles, and `permit_roles` is only what the bot hands to listed members (and what guards and pings read). A new reader of "who holds a permit" reads `permit_members`, never a role. Kept on purpose: `migrate_members` still converts a guild's role holders to listed members once, at the first sync (GuildCreate), so a server loses nothing; the ownership handover in an unmigrated guild still deletes the strong permits' role rows, so the migration cannot give them back later (`owner::on_owner`). `enforce_permits` waits in a guild whose first permit sync has not run (nobody is listed yet, so taking roles then would lose the staff for good). Until that sync, staff who hold a permit role and are not Owner/EO/TA resolve to no permit (anti-nuke whitelist, held-staff check and the raider list see them as members); the sync is queued at GuildCreate and retried. Not done: some functions still carry a `roles` argument that nothing reads (`App::cached_level`, `raiders::collect`, `joingate::immune_by_roles`); removing it is a separate cleanup. Tests that gave a permit through a role now list the user in `permit_members`; `permits_resolve_levels` asserts a user listed nowhere has none.

- **Permit role rows outlived their Discord role.** Admins and Moderators each listed an old and a new role id, the old pair deleted. Auto Setup and the Overview Fix never make permit roles; a person deleting one by hand, or a restore that was not relinked, leaves the row. *Avoid:* do not drop the row when the role is deleted, because an anti-nuke restore makes the role again with a new id and `relink` needs the old row to point it there. `deadroles::sweep` (hourly, in `welcome::purge_left`) starts `permit_roles.missing_since` (migration 4049) when it sees the role missing, clears it when the role is back, and drops the row after `DEAD_ROLE_DAYS` (7, one constant). Readers skip missing roles at once (`tickets::live_roles`, also the `ticket config` view). A saved permits copy from the dashboard rewrites the rows and so restarts the clock (a server that saves permits every week never drops a dead row; harmless, readers skip it). `relink` clears `missing_since` when it points a row at the restored role, or a sweep that read the roles just before the restore could drop the fixed row. A backup loaded more than 7 days after the role was deleted finds no row to relink: the permit has no role until staff set one. Not done: stored config lists (`tickets.ping_roles`, panel `ping_roles`, feed `ping_role`) keep a dead id until edited, readers skip it; `level_roles` rows are not swept (the owner sync would have to make the role again first).

- **A plan runs with the rights of who saved it last.** Like message schedules, the runner reads the saver's permit (`giveaways`, or Trusted Admin and up) before each run and stops the plan with the reason when it is gone; an unreadable level only skips the pass. A template and a plan never keep an entry code (only a hash is stored, salted with the giveaway id): a giveaway made from them has none, and the form asks for a new one.

## The optional Staff role

- **A rollback would have turned the Staff role off with no channel steps.** `store::write_levels` deleted every `level_roles` row and wrote back only Trusted Admin and Owner, so a rollback or Auto Setup run dropped the `staff` row, and Brim took the role from everyone while its channel overwrites stayed. *Avoid:* only `staff_role.rs` writes the `staff` row (on, off, and the Overview Fix); `write_levels` keeps it, and the rollback's owner check compares the levels without it. A new level that has steps of its own gets its own route, not a key in `permits.levels`.

- **A permit's rank decides who gets the Staff role, but a rank change queued no sync.** `store::held` compared names, roles and members only. *Avoid:* the rank is in `held`. When a new reader depends on a permit field, check that a change to that field queues `permit_sync`.

- **An existing role picked as the Staff role goes to every staff member.** A role with Administrator, a main role or one Discord hands out would give that to all staff, or Brim would take a main role from every member. *Avoid:* `staff_role::unfit` refuses @everyone, managed roles, roles at or above Brim's top role, roles with a dangerous permission, roles Discord hands out, and a role another setting uses (`channels::used_by`, the alert and ping lists left out).

- **Do not replace the permit role overwrites with the Staff role.** A deleted Staff role (a nuke action) would lock every staff member out of the logs during the attack. *Avoid:* the Staff role opens a Staff channel next to the permit roles (`Ctx::staff_role` in Channel Setup, `all_staff_roles` for the Logs and Staff categories), never an Admins or Owner channel. Off takes its overwrites first, then the row, then the role, so no step closes a channel to staff.

- **The Staff role is no member list group.** `all_staff_roles` holds it (security score, anti-nuke Mention @everyone rule); the hoist pass and its Overview row read `grouped_staff_roles`, which leaves it out.

- **Off locked staff out where only the Staff role opened a channel.** Members can hold a permit by user ID with no permit role, so the delete left no role with View. *Avoid:* off gives View to the live permit staff roles first, and refuses when the role opens a channel and no such role exists. Off takes the draft lock alone, and Auto Setup holds it shared over its channel steps, so neither writes the Staff role's overwrites while the other runs.

- **A picked role could carry rights.** Only dangerous permissions were refused, so Move or Mute Members went to every staff member. *Avoid:* `unfit` refuses any permission that @everyone does not have.

- **A setting could have Brim give a level role to every member.** The quarantine role, main roles and verification roles took any role, so the Staff, Trusted Admin or Owner role could go to members, and `permit_sync` then took it back: a fight, or staff access for a moment. *Avoid:* `api::given_roles` names the roles a section gives; a save, rollback (also one that brings back a level role) or import that adds a level role there is refused, the bot's settings command refuses it too (`reply.settings.staff_only_role`), and a value saved before shows as the Overview row `level_role_given`. Ids are read as text or number (`api::id_text`), as the bot reads both. A new setting that gives a role goes into `given_roles` and the settings command list.

- **Picking an existing role took it from its members with no word.** The next sync takes the Staff role from everyone who is not staff. *Avoid:* the switch asks first with the live count (`GET /staff-role?pick=`, members who hold it and are not staff).
