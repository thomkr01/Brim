# Pitfalls: Anti-nuke guards

Index and rules: [PITFALLS.md](../PITFALLS.md).

**A Trusted Admin could give a quarantined nuker their roles back.**
The quarantine hold exempted every level that `whitelisted("quarantine")` accepts, and Owner, Extra Owner and Trusted Admin accept every flag. `unquarantine` let any immune level release a member whose saved roles hold a permit or dangerous permissions. *Avoid:* the hold asks `hold_exempt`: Owner, Extra Owner, a permit with the `quarantine` flag or the quarantine whitelist; a Trusted Admin only for a join quarantine (an unverified joiner). Their change is undone; they stay immune to punishment (the nuke run logs them). `unquarantine` of staff needs Owner or Extra Owner. A level-wide `whitelisted` is never the right check for a bar narrower than "immune". No dashboard or MCP route releases a quarantine.

**A taken-over guard job kept its lease, heat panic ignored immunity, and the rank guard stopped silently on an unread owner or victim.**
A live run reused a pending `nuke_revert` job as it was, so a job a failed run left leased (heavy lease, 900 s) retried 15 minutes late. With a failed whitelist lookup, `count_at` added heat and called `panic::note_heat` for an immune actor. A retry that contained a nuker opened no case. `guard_rank` used `?` on the owner and the victim's level. *Avoid:* the takeover is one `UPDATE .. SET run_at = now + 120 s, locked_until = NULL .. RETURNING id` (safe: a job runs only under the run claim); `count_at` asks `is_immune` before heat panic (immune: no panic; unread: counts); the late containment opens a case and names it; any unread level in `guard_rank` undoes as if the victim were the owner and the actor had no level, and logs. Discord logs say only "not saved"; the database error goes to tracing. `first_in` prunes past 10 000 keys.

**A nuke run reverted and reported an immune actor, a late containment was silent, and each unread run kept its own guard job.**
An Owner, Extra Owner or Trusted Admin reaches a nuke run only when a whitelist lookup failed, but a level read of Ok(true) still undid their work, opened a quarantine case and counted towards panic. `REPORTED` took "stopped" only from a run that reports, so a retry that contained the actor sent no log and left "left free" set, and a second nuke in the hour was not reported. Each live run queued its own `nuke_revert` job, and an unread error ended the run before later actions were reverted. *Avoid:* `nuke_run` reads the level once per run: immune ends the run with one log and no revert, case or panic count; unread reverts, opens no quarantine case (`UNREAD`), and fails at the end (`LevelUnread`) after the revert-only passes. A non-reporting run that stops the actor logs it and sets `mark_stopped`. A run takes over a pending `nuke_revert` job of the same actor. The case line says "not saved" or "none" instead of a case 0, and `quarantine_actor` sends its log when the case insert fails.

**A live nuke run quarantined an immune member whose level could not be read, and a rank breach with an unread level was left in place.**
`count_audit` counts an action when the whitelist lookup fails, but the live run then contained without asking the level, so a Discord 5xx made an Owner, Extra Owner or Trusted Admin a quarantine target. `resume_nuke` folded the level into `contain = false`, which `revert_and_report` reads as "contained earlier", so the report said "Quarantined" and hid channels from a free actor. `guard_rank` returned on an unread actor level, so a ban of a permit holder stayed with no log. *Avoid:* the Contain step asks `is_immune` itself on every run: Ok(false) contains; Ok(true) and Err contain nobody and say why; Err fails the run so the `nuke_revert` guard job asks again. `guard_rank` undoes as for the lowest level and logs "their level could not be read". `voice_nuke::apply` counts as `count_audit` does (no `?` on the whitelist lookup).

**A failed case insert dropped the nuke report, and a nuker the bot could not contain got a case per action.**
`report` used `?` on `open_case` and `record_nuke` before the log and the owner DM. The live path had no `reported` check, so each run against an uncontainable nuker opened a case and a full report. *Avoid:* the case and the record are best effort (the log says what was not saved); a live run reports only when the last report in the hour did not leave the actor free (`reported_free`), so a released nuker who nukes again is reported again.

**A nuke retry quarantined a member made immune since, and a config failure reported a member as contained while a role it could not take kept them armed.**
`resume_nuke` contained whenever the actor was free, without asking their level, and `strip_dangerous` only looked at dangerous roles below the bot. *Avoid:* a retry contains only when `is_immune` answers Ok(false) (an unread level does not punish, and the next retry asks again); the config-failure strip reports success only when no dangerous role is left at all, including roles above the bot and managed ones.

**A failed level lookup quarantined whoever deleted the verification channel.**
`verify::deleted::on_audit` read a failed owner or level lookup as `Level::None`, so a Discord 5xx made the owner, an Extra Owner or a Trusted Admin who deleted the channel a quarantine target. *Avoid:* the D12b rule: an unread level means make the channel again and punish nobody (`Deleter::Unread`), and the alert says the level could not be read. No other `unwrap_or(Level::None)` is left in the bot.

**A channel overwrite gave dangerous permissions past the grant guard.**
After role grants were guarded for everyone, a non-immune member (or a bot with the `antinuke` whitelist flag) could still give a staff role or a single member Manage Messages, Manage Channels or Administrator-like rights in a channel: the overwrite guard watched only @everyone and the main roles, only with `monitor_channel_perms` on, and exempted the whitelist flag. Root cause: the same rule was built once per Discord object (role, member, overwrite) and only the role half was moved to `is_immune`. *Avoid:* `ChannelOverwriteCreate`/`Update` are grants in `guard_perms`: any role or member overwrite (`options.type` "0"/"1", member ones undone with `PermissionOverwriteType::Member`) that gains a `DANGEROUS_PERMS` allow bit is undone unless `is_immune`, always on, with the live re-read and the current denies kept. `strict_mode`, `strict_member_roles` and `monitor_channel_perms` were removed (serde ignores the keys in old configs and exports; `AntinukeCfg` has no `deny_unknown_fields`). Brim's own entries (Channel Setup, lockdown, panic, backup restore and the dashboard, same bot token) are skipped by `actor == app.me` in `on_audit_as`. Also: a failed undo is logged as failed, not as undone; a looping MemberRoleUpdate take-back (a reaction-role bot) is logged through `take_back_log_due`; a dangerous role that also carries a permit is handled only by `guard_perms`; an unreadable lock state falls back to the live roles and then takes the roles back unpunished; a replayed RoleCreate removes only the dangerous bits the role still holds; BotAdd reads the bot's role a second time before it gives up. Other overwrite paths already covered: `hold_overwrite` (quarantined members, quarantine whitelist, may act on the same entry), `guard_lock` (lock snapshots), `verify::given` (verified channel access).

**Dangerous grants were guarded only behind strict mode and the whitelist flag.**
`guard_perms` undid a role created with Administrator (or another `DANGEROUS_PERMS` bit), a role given one, or a member given such a role only with `strict_mode` or `strict_member_roles` on (both off by default), and a permit with the `antinuke` whitelist flag (a bot's too) exempted the actor. A bot added with Administrator on its own role was not checked at all. Root cause: a rule from "trust comes from Brim, never from Discord rights" was built as an opt-in toggle with the module's general whitelist. *Avoid:* RoleCreate, RoleUpdate, MemberRoleUpdate and BotAdd grants are always guarded and exempt only `is_immune` (Owner, Extra Owner, Trusted Admin); a failed lookup undoes without punishment. A bot's own role is judged once, on the BotAdd entry with the adder as actor: the RoleCreate of a role with `tags.bot_id` is skipped (Discord's docs do not say whom that entry names), and a MemberRoleUpdate never judges a managed role. The toggles were removed later (see the entry above). `guard_permit_roles`, the join gate bot filter and the hold already ask `is_immune`/the quarantine whitelist; the vanity guard keeps its toggle and whitelist on purpose.

**A DB error before or in a nuke run skipped containment, the report or the retry.**
`quarantine_and_revert` queued its guard job and read `still_contained` with `?`, so a DB error left the nuker free. A failed `revert_actor` returned with `?`, skipping report and panic, and the guard job was deleted anyway. *Avoid:* a failed guard write runs without a guard; `still_contained` returns a bool and a failed read counts as not contained. An unreadable config in `revert_and_report` and `quarantine_as` runs the defaults (auto quarantine on, no Quarantine role, so roles are cleared) and logs the error to Anti Nuke; the run is then done (no retry for the config error alone). Without the config the Quarantine role is unknown and counts as "other", so `row_flags` keeps the row: no `released` (saved roles stay) and the row's `on_join`. A member who already has a quarantine row keeps their roles then (owner decision; stripping would take the Quarantine role that holds them); revert and report still run. Such a member still loses every role with dangerous permissions (`strip_dangerous`: a row can outlive a release by hand) and counts as quarantined only while at most one non-managed role is left. A retry does only what is left: `resume_nuke` contains whenever `still_contained` is false, and reports and runs panic only when no run reported yet; `mark_reported` (in memory and as `reported` on the guard job) runs right after every report step. `revert_actor` reads the deleted-object rows before any inverse runs, so a failed read cannot leave run inverses unmarked. A failed final `UPDATE action_log` is a warning; its rows stay in memory (`UNMARKED`), are skipped by the next revert and marked with it, so no deleted channel or role is recreated twice. Accepted (owner decision): when the `reported` mark cannot be saved and the bot restarts, the retry reports a second time. A failed revert logs, reports with an empty summary plus a failure log, counts towards panic, and returns the error at the end; the guard job is finished only on `Ok`, so it reruns the revert.

**A failed `action_log` insert skipped the anti-nuke count.**
`count_at` returned on the insert error before `on_actions_at`. *Avoid:* log the insert error and keep counting; only that action's revert row and its count after a restart (`seed_windows`) are lost.

**A switch checked in only one of two call sites.**
`on_audit` calls the quarantine hold from two places. Kicks, bans and timeouts checked `quarantine_hold`, role changes did not, so staff were quarantined with the switch off.
*Avoid:* when a feature has a switch, grep every caller of its entry point and check the switch in each, or check it once inside the function. `hold` checks it inside, after the join-quarantine branch: an unverified joiner's role change is always undone (that punishes nobody); only the punishment follows the switch.

**A join quarantine counted as a nuke target.**
Verification's "quarantine on join" writes a quarantine row with no saved roles. The quarantine hold treated it like an anti-nuke quarantine, so an autorole bot giving a joiner its role was quarantined and lost its role permissions on every join.
*Avoid:* the hold undoes the role change on a join quarantine but punishes nobody. Code that reads `quarantines` must tell the two kinds apart, by the `on_join` column (next entry).
The same happened on a rejoin into a real quarantine: `requarantine_rejoin` put the quarantine back and the autorole bot's role, a second later, made the hold quarantine the bot. A bot's role change within 60 s of a rejoin's quarantine is undone without punishment (`note_rejoin`, in memory: after a restart the bot is punished as before, which fails safe); a human doing the same is still quarantined. The join branch also undid with `?`, so a Discord error skipped `guard_perms` for that entry and left the role on silently: `undo_role_change` tries once more after 2 s, then posts "Could not take back roles" in the anti-nuke log, and never punishes.
*Avoid:* a step whose failure must not stop the rest of an audit handler does not use `?`; retry or report it where it fails.

**A failed log must not stop protection.** (#100, #133)
The timeout DM went out before the timeout worked, and a failed anti-nuke report stopped panic mode.
*Avoid:* fixed order Contain → Revert → Report → Panic. Logs and DMs are side effects; their failure never skips the next protective step.
Same mistake found in Join Raid (a failed raid log or report job skipped the lockdown and every punishment, and one raider who had left stopped the punish loop), in automod (the mention-lock log and lock came before the strike, the timeout log before the strike-cap lock) and in `warn_actions`. A loop that punishes several members logs a failure and goes on with the next.
`voice_nuke::apply` broke it with `?`: the audit deltas were already stored as seen, so one actor's failed whitelist read or count dropped every later actor's delta for good. Root cause: `?` inside a loop whose input was already marked done. It logs per actor and goes on.
Join Gate: a refused gate punishment (403 on kick) ended `on_join`, so the join raid check never ran for that joiner. Gate punishments log and go on.
`panic::note`: a failed heat panic log returned `Err` after heat panic was on, and automod (`automod.rs` twice), `activity::heat_up` and anti-nuke's heat path passed it on with `?`, so the strike, timeout or `on_actions` count that tripped it never ran. The panic report and lockdown logs in `panic::start` did the same and ended the nuke run that called it. Those logs only warn, and every heat caller goes through `panic::note_heat`, which logs a failure and returns. Also `catch::on_message` (a failed log handed a caught message on to automod as uncaught) and `verify::deadline` (a failed log failed the job, which would punish again); both warn. `native_action`'s Report log was left: its caller already logs per action and goes on.

**Heat lives in memory.** (#111, accepted)
A restart resets running heat. Strikes and timeouts survive. This was left as is on purpose.

**A permit without its own limit had none.**
Auto Setup gives Admins and Moderators ban and kick without limits, and anti-nuke skips the bot's own audit entries, so a hacked mod could mass-ban with `t!ban id1 id2 …` where the same account in Discord's UI would be quarantined at the anti-nuke limit. A breach of a permit limit quarantined them but left the bans already made.
*Avoid:* `permits::command_limit` falls back to anti-nuke's limit for the same action (`commands::nuke_fallback`: ban, kick and timeout, one less, as a permit limit trips past its value and anti-nuke at it; only with anti-nuke on). Under that fallback bans and kicks share one rate limit key (`commands::limit_key`), as they share anti-nuke's card (per-action keys let a mod do the limit in bans and again in kicks). On a breach `gated` quarantines and runs `antinuke::revert_breach` (the actor's last hour, case bans included). Every staff command goes through `gated`; the dashboard's own rate limit is D24.

**A nuker under every limit, or with quarantine off, never reached panic.**
Anti-nuke heat at 100 % only counted towards panic, which needs 3 distinct accounts, so one nuker spreading actions over several cards below each limit was never stopped; and Quarantine On Limit off dropped the Panic step with the quarantine. Root cause: one switch or signal fed only the step next to it.
*Avoid:* 100 % anti-nuke heat contains and reverts like a limit (`antinuke::breach`), and `nuke_plan(false)` still ends with Panic. When a switch turns one step off, check the steps after it still run.

**A category exemption covered anyone who moved a channel there.**
Ticket categories and panic's Whitelisted Categories exempted every channel create and delete in them, for any actor, so a nuker moved channels in and deleted them uncounted and never recreated. The panic list was only documented as "left unlocked by panic". Root cause: an exemption meant for one kind of actor (ticket bots) was keyed only on the place.
*Avoid:* an exemption names who it is for: ticket categories exempt only a bot (`antinuke::is_bot`, a failed lookup counts), never a channel that moved in from outside in the last hour (`App::note_category` before the first await of the gateway task, `moved_in`), and panic's list is panic-only. No other module reads `whitelisted_categories`.

**Manage Roles handed out a whitelist.**
Anyone with Manage Roles could give themselves a role that carries a permit (and its anti-nuke whitelist), then nuke uncounted. Root cause: who may hand out a permit's role was left to Discord's hierarchy.
*Avoid:* giving a member a permit role is a guarded action (`antinuke::guard_permit_roles`): the role is taken back and the actor quarantined unless Owner, Extra Owner or Trusted Admin. Runs with anti-nuke on, after `guard_perms`, also for a self-grant. Only a guarded permit counts (owner decision): every permit except the weak ones in `permits::WEAK_PERMS` and `WEAK_WHITELIST` (cases, notes, mod stats, reports, tickets; word, link and report immunity; automod immunity is guarded). Reaction-role, level and autorole bots hand the weak ones out, so they are only logged. List the weak ones, never the strong ones: listing the strong ones missed the per-action `wl_*` flags (the original D16 attack), revert, backups, appeals and `lock_*`. A new permit is then guarded by default.

**A failed whitelist lookup dropped the action.**
`on_audit` used `app.whitelisted(..)?`, so a 5xx or timeout returned before the action was logged or counted: a nuke during a Discord hiccup was never stopped or reverted. An error in the exemption check was handled as "exempt".
*Avoid:* on a protection path a failed exemption check means "not exempt" for counting. The instant tripwires (`guard_perms`, the hold) still stop on the error, as #97 asks for staff. During a nuke the level is reused for 5 s (`App::whitelisted`), cleared on every member update or leave before the event's first await; a lookup that raced a clear is not kept (as D66).

**The unauthorized-bot filter let a bot in when the audit lookup failed.**
A bot whose adder could not be read (5xx, 429, entry not written yet), or whose adder's immunity check failed, counted as authorised. "Unknown" was read as "allowed" on a protection path.
*Avoid:* `welcome::bot_adder_retry` retries once after 1.5 s (each try bounded to 3 s); Join Gate blocks the bot when that fails too, finds no entry, or the adder's level cannot be read. The mock Discord answers `audit-logs` (`Mock::audit`, `fail_audit`).

**A new delete type was not watched.**
Deleting threads and forum posts (audit type 112) was not an anti-nuke action. *Avoid:* the "Thread & forum post deletions" card (`Action::ThreadDelete`, opt-in, nothing to restore). A new action needs the enum, `ALL`, `watched`, the dashboard's `NUKE_CARDS` and the UI's `NUKE_WORDS`.

**A lost gateway session lost its audit entries.**
Discord replays missed events only on a resume. After a new session (`Ready`) the audit entries made in the gap never arrived, so a nuke during a reconnect was never counted. *Avoid:* `welcome::saw_audit` keeps the newest audit id per guild; `on_ready` runs anti-nuke on the entries after it (`catch_up_audit`). The last handled id is saved in `audit_seen`, loaded before the gateway (`load_audit_seen`), so the first `Ready` after a restart reads entries made while the bot was down too.
A replay is not a live event:
(1) A replayed entry counts at its own time (snowflake), never now (`antinuke::replay_age`, `AntiNuke::on_actions_at`, `action_log.created_at` backdated, no heat); older than the hour window it is not counted; a burst in the gap still trips.
(2) No gateway event, so its category comes from the channel or the latest backup (`replayed_parent`); a ticket made and closed in the gap is counted.
(3) Take the start point in the gateway loop before the `Ready` task is spawned (`note_ready`); a second `Ready` keeps the older start; take the floor before `on_ready`'s first await.
(4) Live and catch-up bring the same entries: `saw_audit` returns whether an entry is new (last 1000 ids per guild); both run anti-nuke only then. The dedupe ring (2500) must exceed a whole catch-up plus the live entries meanwhile.
(5) Page back with `before` (newest first) up to 1000 entries; past that, or when every retry fails, the Anti Nuke log says the gap was not checked (the gap is unpinned).
(6) Batch the `audit_seen` write every 2 s (`done_audit`, `flush_audit`): an UPSERT on one row per guild in the event path serialised a nuke's entries on its row lock.
(7) "Replayed" is a flag from the catch-up (`antinuke::on_replayed`), never inferred from the host clock (a clock an hour fast made live entries too old to count).
(8) A replayed entry re-judges every window that holds it, with the live entries already counted after it (`on_actions_at`): a nuke split across a reconnect tripped nothing.
(9) Past the hour window an entry is still logged with `counted` 0 (revertable); the Anti Nuke log says how many were not counted.
(10) The saved id never passes an entry still being handled (`audit_inflight`, left when its `InFlight` guard drops, also on panic; a 30 min expiry only bounds a leak) or a gap whose catch-up has not succeeded (`audit_pinned`); `action_log.audit_id` lets a catch-up skip entries counted before a crash lost the batched id.
(11) Record every handled entry in `audit_handled` (tripwires, lock set-backs, voice and exempt entries too; not when anti-nuke is off or for the bot's own entries; pruned after a day); a catch-up skips them and every `action_log.audit_id`: replaying a tripwire entry from before a restart took back a role an Owner had since re-granted.
(12) Replayed tripwire entries have no age limit, on purpose: `guard_perms`, `guard_permit_roles` and the holds judge a grant still in force, so an old one is undone and punished like a new one; only counting has the hour window.

**A config read error skipped an audit entry's guards and count.**
`on_audit_as` used `app.cfg(..)?`, and the cache is empty after each save, `relink` and a listener reconnect. The entry was marked handled with no count and no `action_log` row. *Avoid:* `App::cfg_or_last` falls back to the last config loaded (kept through `forget`, set only by a read that is not stale), else after one retry returns Err with the defaults: the guards undo with nobody punished, the action is saved with `counted` 0 (`log_uncounted`) so `/revert` can undo it, and staff are told. The nuke run and its later passes use the same fallback.

- **A loop breaker failed open.** After 5 reverts in 10 minutes for one (guild, actor, member), `fight_stopped` and `permit_fight_stopped` stopped every revert, so the bot that fought Brim won. *Avoid:* a breaker on a security revert slows it down (here at most one revert a minute, `FIGHT_SLOW`), never stops it; the alert stays once per window.
