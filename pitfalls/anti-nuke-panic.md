# Pitfalls: Anti-nuke panic mode

Index and rules: [PITFALLS.md](../PITFALLS.md).

**Panic mode started by a Trusted Admin loaded the latest backup.**
A direct load needs Owner or Extra Owner (`t!backups load`, the dashboard `load`), but the dashboard's panic start needs only Admin, and panic's `LoadLatestBackup` step loaded whatever the trip settings said. *Avoid:* the `panic_start` job carries `by`; `panic::start` takes it, and `may_restore` reads that member's level when the job runs: Owner or Extra Owner loads; anyone else (or an unread level, or an old job without `by`) skips the load with a report line that says why. A trip (no person) loads as set up. A second way to reach an action asks the bar of the first, also through a queued job.

**Mass role removal from members was not counted by anti-nuke.**
`watched` had no action for a `MemberRoleUpdate` that takes roles. *Avoid:* `Action::RoleRemove` (opt-in card, heat 15 as a timeout) counts by heat only (`heat_only`: left out of `watched`, so it never trips a minute or hour cap) and is undone by `Inverse::AddRoles`, which adds each role back one by one (`RestoreRoles` replaces the whole list and would drop roles given since). A new action needs `watched`, `inverse`, `undo`, `undo_text`, `run_inverse`, the dashboard's `run_inverse`, `NUKE_CARDS` and the coverage note.

**A failed panic end log retried the end, and start dropped a dashboard end.**
`panic::end` returned the end log's result, so a refused log made the job retry and write the saved category overwrites again. `end_payload` replaced the whole payload (losing `ended_by`) and pushed `run_at` 60 s ahead, delaying a dashboard end during start. The backup step read the config with `?` after the locks were taken. *Avoid:* the end log is best effort. `end_payload` keeps `ended_by` and leaves `run_at` alone when set (`ends_later` handles the early end). A failed config read in the backup step reports `Backup::Failed` and goes on.

**Anti-nuke tripped once per event, not once per nuke.**
Past the limit every audit entry returned `Quarantine`, each in its own task, so a 20-channel nuke started about 16 quarantine-and-revert runs. They read the same unreverted rows, so the backup recreated the same deleted channel several times (the copy has a new id, so the next run still saw the original as missing) and opened as many cases and owner alerts.
*Avoid:* one run per (guild, actor) (`App::nuke_runs`). A later event only logs its row and asks the running run to revert once more; the run frees its claim in the same step that finds nothing new, so no action falls between two runs. The `nuke_revert` guard job is due after 120 s and a run under rate limits can take longer: the scheduler skips a guard whose run is alive, and the job path takes the same claim. An actor an earlier run already quarantined only gets the revert, no second case or alert. `panic::start` undoes its claim and category exemptions when its `panic_end` job cannot be saved (else mod commands stay locked with nothing to end them), and checks and inserts `panic_runs` in one step (else a second start saves the already exempted overwrites as the old ones).

**Panic's "lockdown" let everyone keep writing.**
Panic locked with `LockKind::Role` only, which strips dangerous perms (Mention @everyone and the like) and never Send Messages, so @everyone wrote everywhere and the Whitelisted Categories exemption changed nothing. The exemption also gave @everyone Send by removing a Send deny the category already had (a read-only category opened), and only ever wrote the @everyone overwrite, also when the lock silences other main roles. Root cause: the step was named "lock the server" but used the lock that covers only roles; nothing tested what members could still do.
*Avoid:* panic takes two locks, `Role` and `Server` (main roles, or @everyone, lose `SILENCE` and voice when the lockdown voice option is on), each with its own overlap check, so a lock staff made first leaves the other part to panic. `panic_end` keeps one owner flag per lock (`locked`, `locked_server`), written before the lock, again after it (a staff unlock in between cleared it), and cleared when no lock was saved (a crash between lock and flag left everyone muted for good); a new panic does not start while an old `panic_end` job still waits for its retry, or its replace drops the claim on the old locks; `lockdown::forget_timers` clears the one whose lock staff lifted, and `panic::end` reads the flags from the job as it is now and tries both unlocks. A whitelisted category gets, per main role, an allow for exactly the bits the server lock takes from that role (`panic::taken`), never a bit the role lock takes too (Mention @everyone), never a bit the category already allows or denies the role, and for a role other than @everyone never a bit another role's overwrite denies there (a role allow beats every role deny, so a Muted role would write; the Quarantine role's deny is left out for a role quarantine takes, never for a managed role, which quarantine keeps). Each exemption is saved in the job before it is put; if panic's server lock was not made, the categories close again at once. A category id from another server is refused. A combined lock (`Mixed`, `All`) takes the parts no active lock covers (`LockKind::rest`), so a join raid during panic still locks joins. `t!unlock <kind>` checks the permits of every active lock it lifts, not only of the kind typed (`unlock` lifts every overlapping lock, a combined one too), and `t!lock` names what it took. A part a lock from before panic held when panic started is marked in `panic_end` (`waits_role`, `waits_server`), and panic takes it once an unlock lifts a lock overlapping it (its timer ran, or staff lifted it), once only, and then owns it (`panic::held` before `lockdown::unlock`, `panic::relock` with the lifted kinds after). An owner flag alone could not tell "a lock from before panic" from "staff lifted panic's own lock", so every unlock re-muted the server. Not while `start` runs (`PanicRun::starting`, a per-start token so an old start's guard never clears a newer one); a relock that panic's end missed is lifted again at once (`unlock_now`). A failed relock keeps waiting (unless panic's own lock holds the part already, so two relocks at once leave no stale wait), and the end of `start` takes a waited part whose lock ran out while it ran (`catch_up_waits`, after `start` marks itself done, so nothing falls between them). Relock and catch-up share `take_waited`, which lifts again a lock that an end of panic missed. Panic marks a lock as its own inside the guild's lock mutex, right after the save (`lockdown::lock_marked`), so a second take or an unlock always sees the mark. Cleanups that lift "panic's own" lock after an early end know it by its saved time (`store::lock_created`), not by its kind: the end may have lifted it and staff made a new lock of the same kind. `relink_roles` rewrites a snapshot with `store::update_lock`, which keeps its state and age. A role a restore made again under an active lock is locked like the old one and its snapshot entries move to the new id (`lockdown::relink_roles`, after `relink` in both restore paths), or it was the one main role still writing. Entries are saved before the PATCH, and a role in two locks gets one PATCH with what both take (one PATCH per lock from the same read gave the first lock's bits back). An early end from the dashboard that ran, or is running, while `start` took its locks is caught at the end of `start` (`panic::ends_later`), which lifts its own locks (only a lock of exactly its kind still active, so a staff `All` stays) and closes the categories. Not covered: the lock's time is read a few ms after the save, outside the guild's lock mutex, so an end plus a new staff lock of the same kind in those ms can still be mistaken for panic's; a failed time read leaves panic's lock after an early end (fails toward locked); a part whose lock failed with nothing holding it waits for an unlock that may not come. A role with Send that is not a main role keeps writing, as with `t!lock` (owner decision); a non-synced child channel of a whitelisted category stays locked; a crash after the flag but before the lock lets panic's end lift a server lock staff made later.

**During a Role lock the stripped permissions were read as the real ones.**
A Role lock saves each role's permissions and strips them, so sticky roles, verification, `strict_member_roles` and "enforce permits" saw a stripped Admin role as harmless; when the lock ended the member held Administrator.
*Avoid:* a check that judges a role dangerous reads `lockdown::unlocked_info` (live permissions OR the active locks' saved ones): `sticky` (3 places), `verify::grant`, `antinuke::guard_perms`, `enforce_permits`, `events::public`. Active locks are kept in memory (`lockdown::active_locks`, also read by `guard_lock`), forgotten on every lock write in `lockdown.rs`: these checks run per join and per audit entry. `info` shows live permissions on purpose; `setup` checks the bot's own role (never locked).

**Staff could take a lock apart one channel at a time.**
During an active lock, deleting a locked overwrite, removing its deny or giving a stripped role its permissions back went unwatched (overwrite changes are not a watched action, a role's permission change counted only as a rename), and nothing reapplied the lock. *Avoid:* `antinuke::guard_lock` checks every role update and overwrite update or delete against the active locks' snapshots (`role_perms`, `channel_denies`, `prior`): the change is set back from the audit entry, logged, and counted on the Channel Updates or Role Updates card (when on). An Owner, Extra Owner or Trusted Admin is only logged. Every check in `on_audit` runs whatever an earlier one returned and the first error is returned at the end (`keep`): a `?` on `guard_perms` or `hold_overwrite` skipped the set-back, and one on the kick/ban hold skipped the count (D21).

**A staff button skipped the panic lock and the rate limit.**
The Raider List alert's Allow button wrote the allow straight away, while Ban, Kick and Quarantine go through `commands::apply`/`modcmds::run`, which call `gated`. During panic mode's mod lock, or past the rate limit, a hacked staff account could still let listed raiders in.
*Avoid:* every button or command that acts for staff calls `commands::gated` with the permit it acts under before it changes anything, also when it only lifts or allows.

**A failed side step skipped the protection after it.**
`guard_perms` undid the change with `?` before quarantining, so when the undo failed (role above the bot, a 403) the actor was not quarantined; the hold did the same. The nuke report sent its log with `?` before the owner DM, so a nuker who hid the log channel from the bot also kept the owner from hearing of the nuke.
*Avoid:* an undo, a log or any other side step logs its error and lets the protection (contain, alert) run. Same pattern in `panic.rs` `start` and the other `?` under D13: fixed by g2a (see the `panic::note` D13 note above).

**A failed step returned before the next protective one.**
A failed strike timeout returned before the strike-cap lockdown, and a failed case did the same. Native rule actions and reaction or thread heat timeouts failed with only a trace line. *Avoid:* as in "A failed log must not stop protection": keep the error, run the remaining protective steps, return it last, and report a failed action with `action_failed`. Every path that records a strike runs `automod::strike_cap_lock` (messages, reactions, threads, and a warn threshold's timeout). `filter_action` stops after a failed ban, but nothing protective follows there.

**A judgement on role permissions read the live roles during a role lock.**
A role lock strips permissions from roles, so a saved Administrator role looked harmless and `t!verify` could free it. *Avoid:* judge a role by its unlocked permissions (`lockdown::unlocked_role_perms`, the oldest lock snapshot wins over the live role). The rejoin grace for an autorole bot covers any number of bot changes in its 60 s, but only roles with no dangerous permission and no permit, read live (a failed lookup or a role Discord does not list counts as not plain; the cached guild info missed a role created a moment before); anything else quarantines the bot as before. A single-use grace brought back the false positive for a second autorole or level bot.

**A lock could run for years.**
No upper bound on lock duration (`999999d`). *Avoid:* `lock_marked` caps the duration at 30 days (`MAX_LOCK_SECS`).

**Dashboard mod actions skipped panic mode's mod command lock.**
Appeal deny, dismiss and deny + blacklist, case edits, note add, edit, delete and sweep, and report dismiss and reopen ran during the lock, while their bot twins go through `commands::gated`. Only the appeal accept checked it. *Avoid:* every dashboard route whose bot twin runs `gated` calls `appeals::mod_lock_guard` (Owner, Extra Owner and Trusted Admin pass). The command rate limit of `gated` is still not mirrored (no dashboard rate limits yet).

**"Delete server data" deleted what a lock, panic mode or quarantine gives back.**
`purge_guild` empties `lock_snapshots`, `quarantines.saved_roles`, the `panic_end` and revert jobs, and `guild_owners`, while the bot stays in the server. *Avoid:* `api::purge` refuses while any `lock_snapshots` row exists (also one that is unlocking), while `recovery::no_backup_now` is true, or while a staff or automatic quarantine (not `on_join`) exists. It writes the checked owner back into `guild_owners`, so the next transfer still runs the D47 reset.

**Lockdown Apply Fix applied fixes the user never saw.**
`fix` ran every automatic fix the check found at click time, so a role or channel change after the page loaded could add a role-permission change nobody reviewed. *Avoid:* the page sends the ids of the automatic fixes it showed (`shown`). `chosen` refuses with 409 when the check now finds a different set.

- **The lockdown check looked only at main-role overwrites.** An allow on @everyone, another role or a member beats the lock too. *Avoid:* `tshoot` reports every overwrite that allows writing, except bots' managed roles, the bot itself and ticket channels. Only main-role and @everyone ones get the automatic fix, since a staff channel's allow is often on purpose. Apply Fix once took the write allow off @everyone in every channel, which closes a channel everyone is meant to write in, and the bot cannot undo it. So an @everyone allow beside set main roles is listed with its fix marked `opt_in`, and Apply Fix runs it only for the ids the user ticked (`picked`). Main-role allows are fixed as before, and with no main roles set @everyone is the main role.

- **A dashboard action skipped panic mode's mod command lock.** Accepting an appeal unbanned during panic mode while the bot refused `t!unban`, and the dashboard's own Discord client bypassed the `commands::gated` rate limit. *Avoid:* a dashboard path that does what a mod command does checks the lock (`appeals::mod_lock`, from the pending `panic_end` job; only owners, Extra Owners and Trusted Admins pass) and runs as a bot job through the command's own code, not a copy. The accept is the bot job `appeal_accept` -> `appeals::accept_job`, which runs the log button's `decide` (permit, panic lock, rate limit (a breach quarantines), lift, undo, verdict). The dashboard keeps its checks only to answer early, and a refusal is posted in the appeal log. `panic::start` saves the job (without unlock) before its slow category calls, rewrites its payload after each opened category (`end_payload`) so a crash leaves a job that closes what was opened, and deletes it when the start is undone.

- **A push that made roles read the quarantine role as above the bot.** The Roles tab renumbers every role after the draft, new ones included, but the safety check used Brim's live position, so with one new role the quarantine role right below the bot read as above it and every such push was refused. *Avoid:* check a renumbered role list with the bot position read from that same list (`roles::bot_top`), never `Live::bot_pos`.

- **A role edit during a lock gave Send Messages back.** The Roles tab may set Send Messages; during a lock or panic mode that is the lock's, and Brim's own audit entries are not put back. *Avoid:* any editor that writes Send (channel overwrites or role permissions) reads `Ctx.locked` first (`roles::editable`).

- **"Load the latest backup after Panic mode" had no switch of its own.** Panic mode loaded a backup whenever backups and their restore were on, and the restore switch also steers Anti Nuke's own put-back of a nuker's deletes, so an owner could not keep one and turn off the other. *Avoid:* `panic.load_backup` (default on, the old behaviour) gates only the panic step (`panic.rs`, `PanicStep::LoadLatestBackup`); `revert_actor` keeps reading `backups.restore`. The panic report shows the same "Backup System is disabled" text for both.
