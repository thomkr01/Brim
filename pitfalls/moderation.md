# Pitfalls: Moderation

Index and rules: [PITFALLS.md](../PITFALLS.md).

**A case's `active` flag was changed with a weaker permit than the effect it has.**
`closecase`, `opencase` (and the dashboard and MCP case edit) set `cases.active` with only the `cases` perm, which `timeout`, `kick` and `ban` also imply. On a warn case that flag is the warn points (`cases::warn_points`), so a member without the `warn` perm could remove or restore a warn. Root cause: the flag was treated as bookkeeping, but one kind of case reads it as the punishment. *Avoid:* an action never needs less than the permit perm of its effect. `ModCmd::CaseSet` on a warn case also asks `actor.has("warn")`; the dashboard `case_edit` refuses a change of `active` on a warn case inside the update (`c.kind <> 'warn' or c.active = $5 or $6`), so check and write see the same row. The text of a warn case stays editable with `cases`. Also: "Left While Timed Out" in the user info reply read `expires_at` (only a warn case has it); it reads `created_at + duration_s` and no later `untimeout` case.

**An undo of an old case lifted a punishment the case did not make.**
A ban row in the dashboard's revert list (and an undo button on an old mod log) unbans whoever is banned now, also when another moderator banned them again later. Root cause: the stored inverse names the member, not the punishment. *Avoid:* an undo that starts from a case asks `cases::not_current` first: its ban or timeout ran out, a later case banned, timed out, quarantined or released the member, or the quarantine row is newer than the case. `undo::press` refuses with that reason and lifts nothing. The dashboard revert leaves such a row under "Skipped" (as for a server renamed again), also when a later `action_log` row bans or unbans the member (anti-nuke's ban rows have no case). The typed `unban`, `untimeout` and `unquarantine` name a member and lift what the member has now, on purpose. A ban made by hand in Discord opens no case, so only the run-out check can catch it.

**A failed temp ban kept its unban job, and a softban's failed unban left a lasting ban.**
The temp ban queued its `unban` job before `create_ban` and left it when Discord refused the ban, so the job could later lift a ban made by hand. A softban ran `delete_ban(..)?`, so an outage on the unban returned an error with no case and kept the member banned. *Avoid:* a job queued before an action is finished when Discord refused the action (a 4xx, `http_err::refused`; after an outage the ban may stand, so its unban stays) (`unban_job` in `apply_dm`); a second step of an action that already happened is queued as a job on failure, never dropped with `?`.

**A failed confirmed command left "Working on it..." on screen.**
An error from `guild_info`, `cfg` or `Pending::run` returned through `?`, so nothing replaced that line. *Avoid:* `handle_confirm` catches every error of the run and an empty result and writes "The command did not finish: <reason>" in its place.

**A second Yes press showed "This interaction failed".**
`confirm::handle_confirm` acknowledged Yes with `DeferredUpdateMessage`, which changes nothing on screen, so during a slow run (`t!purge 100`) the question and its buttons stayed and the moderator pressed again. That press found the row taken, was treated as "expired" and tried to rewrite the question to "Timed out, nothing was done." while the first run was busy and the purge deleted that very message. *Avoid:* the first answer is an `UpdateMessage` that removes the buttons and shows what runs ("Purging messages..."); a press that finds no row gets an ephemeral reason from the command's snowflake age in milliseconds (`gone_text`: already answered, or timed out after 10 s) and never touches the message. A late press leaves the row, so the expiry job closes the question. One handler serves every caller (ban, kick, timeout, warn by id, hackban, unban, quarantine, purge, note sweep, closeall, slash and prefix).

**A purge's result went to a message the purge deleted.**
After a confirmed `t!purge` the result edited the question, which was among the newest messages and so deleted; the mod log had no channel, filter or skipped count. *Avoid:* a purge posts its own note in the channel (`modcmds::post_briefly`, removed after 10 s), sets `Applied::posted` so no reply repeats it, and its mod log entry adds Channel, Deleted, Not deleted (older than 14 days), Filter and time (`purge_log`). `t!purge N` and `/purge` count N messages from before the command (`ModCmd::Purge::before`: the command message or interaction id); the command message (`own`, real message ids only) goes in the batch, uncounted and best effort, and the question is deleted after the note. When the mod log and the Message Delete Bulk log share a channel, the bulk embed is held back and its file goes under the case (`purge::on_bulk`, one entry); a bulk delete is matched to its purge by message id, so two purges in one channel keep their own files, and a failed purge sends what it held. In different channels both stay. A refused purge says "I lack Manage Messages or Read Message History", not the role-order text of `http_err::why`.

**`t!tshoot` reset anti-nuke and automod heat.**
Anyone with a permit could clear `nuke_heat`, `heat`, `pings` and `mentions` for the whole server, so mixed actions never reached the heat trip. *Avoid:* a cache reset clears caches only (`invalidate_guild`, `forget_cfg`); detection state is never reset by a command.

**A message menu purge skipped "Use slash commands" and Confirm.**
`slash::run` sent message context menus to `reports::message_menu`, which called `modcmds::run` before the `use_slash` check and without `ask`. *Avoid:* a menu builds the same `Cmd` as its slash command (`Cmd::Ext`) and takes the same path; only user menus skip Confirm.

**A softban of an id that was already banned unbanned it.**
A softban is a ban and an unban, with no check that the target is in the server. *Avoid:* `apply_dm` refuses a softban of someone who is not a member ("use ban").

**A timeout with the server default length had no duration in its case and mod log.**
Only the DM got the default; case and log got the typed `?t`, which was None. *Avoid:* `apply_dm` sets `duration_s` to the real timeout length once, for the DM, case and log.

**A command with no valid target said it succeeded.**
`t!warn @role` resolved no member and still replied "All members were warned!". *Avoid:* the shared target loop in `commands.rs` returns early with no targets and asks for a member when no name failed (a failed name was already answered). It is the one loop every mod command uses.

**An automatic timeout shortened a longer one.**
Automod, warn thresholds, Join Gate and heat panic set `communication_disabled_until` to now plus their own length, so a 5-minute strike timeout replaced a 7-day staff timeout, and a long timeout's renewal lost to the next spam message. Root cause: "time out for X" was written as "the timeout ends in X", whatever ran before.
*Avoid:* every automatic timeout goes through `commands::timeout`, which reads the member first and leaves a timeout that ends later (`outlasts`); a failed read times out as before. A mod's own `/timeout` still sets exactly what they typed, shorter too.

**For bans the bot makes on staff's behalf, the audit actor is the bot, so checks must use the case moderator.**
A `t!ban` or dashboard ban uses the bot's token, so the audit entry names the bot, never the hacked moderator. Ban Sync's check (hold 60 s, drop if anti-nuke contained the actor) could never fire for staff commands.
*Avoid:* when the actor is the bot, take the moderator from the matching case (`cases.mod_id`, written by `apply_dm` within seconds) and check that person. With no case (automatic ban), stop only for a nuke case or the quarantine of someone whose permit can ban, kick or quarantine since the ban. Any quarantine at all is too wide: Join Gate and verification quarantine raiders on join, so raiders could switch sharing off by getting quarantined. Store the moderator with anything that acts later (`ban_sync_links.mod_id`). `antinuke::on_audit` skips the bot's own entries on purpose (`commands::gated` permit rate limit covers staff commands); `verify::deleted::on_audit` treats the bot as actor only for its own deletes.

**The dashboard acts as the bot.**
A dashboard unban (accepted appeal, revert) uses the bot's token, so the audit entry names the bot. The Raider List read it as its own lift and did not record that staff let the user back in, so the next removal or join acted on them again. Same cause as "the audit actor is the bot".
*Avoid:* when the dashboard lifts something the bot may have done, record the staff choice in the same transaction (`brim_core::raiders::allow` in `appeals::accept_appeal` and `ops::revert`). On the bot side, take a bot-made unban's moderator from the newest unban case or action-log row by someone other than the bot in the last 5 minutes (`raiders::on_unban`). Ban Sync `on_unban` takes any actor on purpose; anti-nuke skips the bot's own entries; MCP has no unban tool.

**Any moderator could purge a log channel.**
`purge` needs only a timeout, kick or ban permit and ran in any channel, so staff could erase the logs of what they did.
*Avoid:* every purge entry (prefix, slash, context menu, report button) goes through the `ModCmd::Purge` arm, which refuses a channel in `GuildCfg::log_channels` (logging routes, appeals channel, ticket log) for everyone, Owner included.
- A deleted log channel is made again by `protected::log_channel_deleted` and the deleter logged; `forget_log_channel` runs only when no new one was made. The copy takes the newest backup's overwrites (not the deleted channel's: a nuker's grant would return, a deleted role makes Discord refuse), drops gone roles and members, and is locked.
- `backup::recreate` skips a channel with a copy (`protected::copy_of`) and moves the copy into the made-again category (else the anti-nuke revert makes a second channel). A copy whose config swap changed nothing (a restore came first) is deleted. `/appeals/channel` must be in `KEEP_FIELDS`, or a restore deletes the appeals channel. The revert waits on a pending marker while a copy is being made.
- Messages deleted by hand in a log channel are reported (`protected::on_audit`). Discord cannot stop the server owner or an Administrator, and folds later deletes by one person into the first audit entry. The deleter lookup skips the bot's own entries (else it finds the bot's relock first). The report Delete button refuses a reported log message.
- Log channels are locked (`security::LOG_LOCK`, `lock_overwrites`): @everyone is denied Manage Messages and Manage Channels there (that takes a role's grant away in the channel) and only Brim's member overwrite allows them. The bot's allow goes first and counts on its own (else the bot locks itself out). The bot relocks on every ChannelUpdate and at GuildCreate (`protected::lock`, `lock_all`). Overview flags an unlocked one with a Lock fix; Auto Setup makes log categories and #ticket-logs locked; Channel Setup pushes a changed log channel locked. A restore or revert that makes a log channel from an unlocked image has no event to lock it: `protected::lock_guild` runs after both. Each relock PUT fires a ChannelUpdate that relocked from a stale payload: lock one at a time, read from the live channel. Every flip sends an owner DM (one per channel per 10 minutes).
- Known limit: a holder of Manage Roles (only Owner/EO/TA) can remove the @everyone deny and act in the second before the bot relocks. Denying Manage Roles too was left out: the bot would need that allow itself, which Discord may refuse.

- **A proof read after the ban found nothing.** A punishment typed as a reply stored the replied message as verified proof but read it after the ban, and the ban deletes the member's last messages (7 days by default). *Avoid:* read what a punishment is about before it runs (`proof::replied` in `confirm::Pending::run`); store it after the case exists.

**Two clicks could decide one appeal twice.**
`appeals::decide` read the appeal row without a lock and opened its transaction later, so two staff both passed "still open". Its timeout end read the member with `let Ok(..)`, so a Discord error looked like "no timeout". *Avoid:* the transaction starts first and the row is read `FOR UPDATE`; read the member with `http_err::member`.

**An early timeout lift could lose the member's main roles.**
`timeout_roles::on_member_update` deleted the `restore_main_roles` job (DELETE ... RETURNING) then called `restore`; a Discord error left no job and no roles. *Avoid:* when a claim deletes the job first, a failed run queues the payload again. (The scheduler path keeps the row until the run succeeds.)

**A second ban keeps the first ban's reason, so a reason cannot prove who owns a ban.**
Ban Sync laid a copy over a shorter local temp ban and took the ban's reason as proof the copy was its own. Discord keeps the first reason and writes no audit entry when a banned user is banned again, so the copy still read as the temp ban: the source's lift called it "banned again by hand" and left it (the temp ban became permanent), and a retry skipped it as "already banned". A staff ban over a plain copy looked like the copy too. Root cause: ownership read from a field Discord does not overwrite.
*Avoid:* a copy laid over a local temp ban records the reason Discord shows and the temp ban's end on its row before the ban (`over_reason`, `temp_end`, migration 3902), and `bansync::owned` counts that ban as the copy once the temp ban's unban job is gone, at `lift`, `banned_by_us` and the copy's retry. A lift before `temp_end` keeps the ban and queues its unban at the old end (then drops the copy's own unban job); after it, the copy is unbanned as usual (option B, pending the owner's answer). A staff ban over a done copy also leaves the old reason, so `owned` first asks `hand_ban_since`: a ban or tempban case by someone other than the bot newer than the row's `done_at` means banned again by hand, for plain copies too (a Discord-app ban cannot be made on an already banned user, and an unban first lifts the row). `temp_end` counts leased unban jobs, a copy fails and retries while the temp ban's unban is due or running (`temp_ending`), and the lift's new unban job, the drop of the copy's job and the row mark run in one transaction. Ban here goes through `banned_by_us`; nothing else reads a copy's ban reason. The copy path deletes the temp ban's unban job itself with `?` before the row becomes banned (`drop_temp_job` in `finish_ban`), since the ban's own `forget_jobs` is best effort and a leftover job would disown the copy and lift it at the old end.

**Ban Sync's hourly cap was counted outside the row's transaction.**
`share_job` and `import_job` each counted the users shared in the last hour, then wrote rows; a share and an owner-started import at once both saw room and passed the 30 per hour cap.
*Avoid:* `offer` counts and writes in one transaction under `pg_advisory_xact_lock(hashtextextended('ban_sync_cap:' || source, 0))`, and says whether it hit the cap. Send the rest stays outside the cap on purpose (owner's choice). See "A count checked a cap, then a second statement inserted" (#183).

**Parsed words lost their typed form or their limit.**
`note remove 12345m` was read as a duration and `012345` as 12345, so those note ids could not be removed. `sanitize` could cure a 32-character name to more than 32 (㎏ -> kg), which Discord refuses. `COMMAND -h` sent a help embed with no cooldown for members without a permit. *Avoid:* an id that is free text takes the raw word (`modcmds::word_after`); cut a cured name to 32 characters after curing; every reply path for members without a permit passes `cooled_down`.

**A huge duration wrapped negative.**
`duration::parse` took any i64, so `/ban duration:106751991167300d` made `now + d` wrap and the ban ended at once. *Avoid:* the shared parser caps every duration at a year (`duration::MAX_SECS`, the filter action duration's cap; the 28-day timeout cap would refuse the renewed long timeouts), and `too_long` lets each caller say so (`duration::TOO_LONG`) instead of reading the word as a name. A lock keeps its own 30-day cap. Refusals also name the missing permit ("you lack the lockdown permit"), and the ticket blacklist refuses role and channel mentions (`user_ids`).

**`info` showed a member's moderation details to everyone.**
`user_info` printed cases, notes and flags for any caller. *Avoid:* for a caller with no permit asking about someone else, show only account age, "In Server" and the join date.

**A warn whose auto action failed said nothing.**
`apply_dm` dropped the error from `apply_warn_actions`, so the reply said the warn worked while the timeout or kick never happened. *Avoid:* log the error and add "Warn saved, but the auto action failed" to the reply.

**`/warn` gave 1 point, the chat command the server's base points.**
The slash parser filled a missing `points` with 1, while `t!warn`, confirmations, reports and automod use `misc.warn_base_points` (default 5). *Avoid:* an optional value that has a server setting stays `None` until the call site reads the setting.

**Saving a note without a change was stored as an edit.**
`notes::edit` always wrote a `note_edits` row and both callers logged a Modify, so Save twice gave a "x → x" history line and a log. *Avoid:* an edit that changes nothing writes nothing (`old.text <> $3` in the SQL) and the callers skip the log when `old == text`.

**Reopening or dismissing a report on the dashboard erased its action.**
`report_status` set `action = null` and cleared `handled_by` with no trace. *Avoid:* an `actioned` report keeps its action and handler (the route refuses it). A dismiss or reopen writes a `mod_actions` row (`report_dismiss`, `report_reopen`).

- **Editing or deleting a case left no trace.** Anyone with Manage Cases could rewrite or close a case and a trusted admin could delete one, with no record of who did it, so a staff member could hide their own history. `case_delete` also answered OK for a case that did not exist. *Avoid:* a change that can erase moderation history writes an append-only row (`cases::record`, kind `case_edit`/`case_delete`) in the same transaction, and a delete of nothing answers 404. Other erasing routes already keep history (`note_edits`, `handled_by`/`decided_by`; Revert Center and purge are logged).

- **The same rule written twice drifts.** The dashboard's Report button had its own copy of the bot's report checks and missed some: permit holders, a quarantined moderator's saved roles, a server that opted out, and putting a rejected entry back to pending. The permit rule drifted the same way: the bot used the member's highest-ranked permit only, the dashboard the union of all their permits. *Avoid:* a rule both processes enforce lives once in `brim_core` (`raiders::report`, `raiders::not_collectable`, `raiders::allow`); each side only looks up what only it can reach (Discord) and passes it in. Both sides read `permits::top_permit` (ties: the oldest permit). The appeal rules live only in the dashboard.

- **Writing into Discord JSON by position panicked after the decision was saved.** Appeals `close_log` added the Decision field with `embeds[0]["fields"].as_array_mut`. `v[0]` panics when `v` is not an array or is empty, and `v["k"]` write panics when `v` is a string, number, bool or array. A log message with no embed panicked after `decide` had committed, so the member never got the verdict DM. The UI embed editor's `set_at` also panicked on a stored `"image": "url"` and now replaces a non-object parent with `{}`. The Decision field could pass Discord's 1024 limit, which made Discord refuse the edit and left the buttons on the log. *Avoid:* to change JSON from outside (Discord replies, stored documents, user input), use `get_mut(i)` / `as_object_mut` / `entry(..)` and do nothing on a wrong shape (reading with `v["x"]` never panics). Side work like `close_log` must not stop what comes after it. The dashboard and the bot's button path cut the Decision field to 1024 and skip a 26th field.

- **A command word can mean two commands, so a reply frame found by word alone hit the wrong one.** `r` is unquarantine for moderators and reply in a ticket; `c` is purge and close. Ticket aliases are not in `general::CMDS`, so the lookup fell to the moderation aliases and a ticket error was framed as `cmd.purge`. *Avoid:* `reply::command_key` takes the sender's family (`mod_first`): moderation senders use `prefix::alias`, ticket senders `ticket_alias`, general senders `general::lookup`; a test holds `r`/`c` for both. A frame goes on the first embed only. A reply over 5500 characters in total is sent as built (Discord counts all embeds together). A result that edits an earlier message (lock) must be framed too. Confirm questions stay unframed, so a frame without `{text}` cannot hide what is being confirmed. Check every `create_message`/`update_response` that answers a command.

- **A per-command setting must hold at every way into the command.** Ways in: prefix form with aliases (some only in `prefix::alias`, such as `slock`), short ticket words (`r`, `c`, `s`), a slash form whose subcommand can be another command (`/ban remove` is unban; the Commands page listed it under ban, so unban had no slash form), right-click entries (Kick, "Purge 100 From Here"). A gate on one of them lets "who may use it" or "off" be passed through another. *Avoid:* `cmdcfg::prefix` (in `events`, before every prefix handler) and `cmdcfg::slash` (in `slash::handle`, before `run`) resolve every word and menu to its catalog command with `cmdcfg::canonical`; a new way into a command goes through one of the two. The gate only refuses; the command's own permit check still runs after it. Safety commands (`core::cmdcfg::SAFETY`) ignore off, narrowing and cooldown at save (`problem`) and at read (`of`), so a rollback or import cannot lock staff out. A server alias never replaces a built-in word (`cmdcfg::RESERVED`, which holds every word `commands::KNOWN` dispatches; `verifysetup` is in no catalog row). A sibling word that runs another command (`hackban`, `warns`, `cases modify`, `info -server`) also answers to that command's settings (`cmdcfg::also`). A button that runs a command (Warn, Timeout, Kick, Ban on a report; Ban, Kick, Quarantine on a Raider List alert; the undo buttons under a case) calls `cmdcfg::button`. `whitelist` in a ticket is unblock. A new word, sub-form or button that runs a command gets a row in one of these. The cooldown map stops taking entries when full of running cooldowns, so members without a permit cannot grow it.

- **A log that needs the old value needs stored member data, and stored member data has five ways out that are easy to miss.** Discord's member update carries only the new username, display name and avatar, so `profile_log` keeps the last seen ones in `profile_snapshot` (migration 4044). *Avoid:* wire a new table with member data, in the same PR, to all of: (1) written only while the feature that needs it is on (`profile_log::routed`); (2) deleted when the member leaves (`on_leave`); (3) a retention delete in `retention::sweep` (here a fixed 90 days with no setting, owner rule; a per-server limit would be a `RetentionCfg` field with a `delete_for` arm and a `limits::FIXED` range); (4) `persondata::PLACES`, so `/mydata` shows and deletes it and the dashboard counts it; (5) the dashboard role: a REVOKE in `db::set_dashboard_role`, the `dashboard_role_limit` trigger in the migration, and both lists in `dashboard_role_has_rows_only`. Also `PRIVACY.md`, the `/mydata delete` DM text and `T::cleanup`. `purge_guild` needs nothing: it finds every `guild_id` column. Never use `dashboard_role_limit` for DELETE: it returns NEW, which is NULL there, so the trigger would cancel every role's deletes. Show a member's name in a code block (`Log::diff`), never as plain embed text (a display name can hold a masked link). The read of the old row takes `FOR UPDATE` (events run in their own tasks; two updates at once would both log). The first sight of a member only stores, so the whole member list is read once a day, after a restart and within the hour after the logs are turned on (`profile_log::sweep`, last in the hourly loop, one request per 1,000 members in sequence): a quiet member's first change is then logged, a missed leave is deleted (only after a complete paging), and the 90 days count from `seen_at`. A sweep over every server takes `only` for its test, as `retention::sweep` does (else a test touches other tests' rows). Known limits: a change made while the bot was offline only updates the row, with no log; a server that turned the logs on less than an hour ago has no old values yet; the old avatar picture works only while Discord still serves that hash.

- **The Moderation switch forced each moderation command off.** That also blocked the Raider List alert buttons (Server Joins) and the commands that lift an Anti Nuke or Auto Mod punishment (unban, untimeout, unwarn, the Undo buttons). *Avoid:* the Moderation switch is one check in the command gates (`cmdcfg::module_off`), with a kept list (`KEPT` plus `SAFETY`). A button of another module uses `cmdcfg::button_settings`, which skips that check.

- **The appeal page could show what the punishment DM hid.** A case reason of the bot's own (an automod filter, the Join Gate minimum account age) is left out of the DM when the owner hides it. Showing "the newest case reason" on the appeal page would tell a raider the gate's rule. The server name went to anyone who knew the id. *Avoid:* the page shows only staff cases' reasons (`mod_id` is not the bot) and the server only to someone punished there. A Discord log message that more than one path edits (member additions, staff questions, the decision) is edited one at a time (`appeals::patch_log`); an addition checks the appeal is still open, or it writes back an old copy without the Decision field.

- **A purge without a member was logged as a case against the moderator.** A purge of a channel and a slowmode stored the moderator as the case's `user_id`, because the case needs a number there. The mod log showed the moderator as Target, their case list and count held the purge, and they could not change their own purge case ("it is about you"). *Avoid:* a case without a member stores `user_id = 0` (the value a data deletion uses for "no person"); `cases::create` then logs no `target_id`. Every place that shows or filters a case's member uses the one rule in `brim_core::cases`: `target()` in code, `TARGET` and `HAS_TARGET` in SQL. They also cover older rows (`user_id = mod_id`; a self-target is refused, so that pair always means no target). Used in: the mod log (`Target: None`), `t!cases`, the report member view, the dashboard Cases list, case page, edit guard and case delete log, and the MCP `cases`, `case` and case edit preview. A dashboard staff action on such a case records no target. Other kinds with no member (lock, lockdown) open no case.
