# Pitfalls: Dashboard server: saves and requests

Index and rules: [PITFALLS.md](../PITFALLS.md).

**A data request whose job was dropped stayed "approved" for good.**
`datareq::run_job` returned an error when the bot owner was unknown (the Discord application lookup at start failed), and any other failing try errored too. After the last attempt the scheduler dropped the job, the row stayed `approved` without a job, `/mydata` refused a new request ("already asked") and the dashboard answers only `pending` ones. *Avoid:* a status row that waits for one job goes back to a state a person can act on when that job is dropped: an unknown bot owner (it cannot become known in this run) reopens the request at once instead of retrying, and the scheduler's give-up branch calls `datareq::gave_up`, which puts an undone request back to `pending` (test: `datareq::tests::gave_up_reopens`). Checked and fine: `auto_slowmode` (entry above), `raider_lift` (logs for a by-hand fix), `appeal_accept` (the appeal stays open; a dropped job unblocks a new accept); the Raider List decisions change no row that the job must finish.

**A write to the permit tables without a config version came back with a rollback.**
`statics 10 ?remove` deleted a Trusted Admin straight from the table, and the rescue claim added an Extra Owner the same way. Every config version keeps a `permits` copy, so a rollback rewrote the removed TA, a Permits page opened before the removal saved it back (version check passed), and History's "Diff vs current" compared two stale copies. One piece of state in two places (tables and version copy), with writers updating only one.
*Avoid:* every write to `extra_owners`, `trusted_admins`, `permits` or `permit_roles` runs in a config-version transaction: the dashboard's `store::commit` and the bot's `settings::save` take the copy from the live tables (`permits::snapshot`), and a table-only change appends a version (`store::bump`, the bot's `locked` + `append`). Read permits you write back after any Discord call (Auto Setup). Take the config lock before the first permit-table write (`store::write_permits` does): the bot's TA edit locks first, so a dashboard path that wrote rows first and locked in `commit` deadlocked with it.

**A save after a Discord call lost the race to an unrelated save.**
`set_bot_actions` read the config, and after the AutoMod rule was made in Discord, committed with that version; any save in between answered 409 and the rule had no bot actions. *Avoid:* a config write that follows a side effect reads the version under the config lock in its own transaction (`store::locked`). Keep Discord calls outside that lock.

**A slot freed only by the next write locked the page.**
A profile change holds a `reserved` row so one runs at a time; a row left by a restart (an Update restarts the dashboard) was freed only when the next change came in, but the page greyed its buttons while any row was reserved, so none could. *Avoid:* free stale claims on every path that reads them (`profile::sweep` in both the page load and the write), and finish a claim with `where status = 'reserved'` so a late answer cannot overwrite what the sweep wrote.

**A new range clamped stored values the old code allowed, and the dashboard named the wrong used value.**
The first webhook multiplier range was 1-10, so a stored 0.5 (allowed by `heat_ok`) read as 1.0. `verification.time_limit_ms` and `filters.nsfw_threshold` are clamped on read but were not in `limits::CLAMPED_ON_READ`, so `stored_outside` showed a stored 5000 without "(used as 10000)". *Avoid:* a range's lower end is not above the lowest value the old validation took; a path clamped on read goes into `CLAMPED_ON_READ`.

**A stored prefix with a space fell back to `t!`.**
Reading any prefix that failed `prefix_ok` as `t!` broke a stored `"tb "`, which works (the bot strips it and splits the rest by whitespace); the API also refused it on every save of the section. *Avoid:* only a blank stored prefix reads as `t!`; `api::validate` checks the prefix only when it changed.

**Numbers that switched their feature off at 0 had no range, and one range was never checked.**
Verification time limit 0 kicked every joiner; strike expiry or reoffend window 0 reset every strike to 1; `auto_lockdown.strikes` 0 locked the server on anyone's first strike; `panic.duration_secs` above `i64::MAX` wrapped and ended panic at once; `warn_base_points` 0 made warns add nothing; a huge webhook multiplier tripped every webhook message. Import, MCP and the API took them, since `validate` only parses the type. `filters.nsfw_threshold` had a range only in `for_path`'s match arm, which the form shows but `check` never walks. *Avoid:* a number at a fixed path goes into `limits::FIXED` (save, import, MCP, prefix panel and `stored_outside` all use it), a float into `float_for_path` and `ranged_paths`; a value an old config can hold outside the range is also clamped on read (`VerifyCfg::time_limit_ms`, `HeatCfg::clamped`). `stored_outside` lists every section that has a range.

**An empty prefix made every message a command.**
The dashboard API, import and MCP saved `""` or `" !"`; with `""`, `strip_prefix` matched every message. *Avoid:* `sections::prefix_ok` (1-32 characters, no whitespace) in `api::validate` and the panel; `MiscCfg` reads a blank stored prefix as `t!`.

**The backups section had no range check.**
`max_images` had no upper bound (automatic backups have no other cleanup), and an `interval_hours` above `i32::MAX` wrapped negative, so a backup ran every tick. *Avoid:* `limits::FIXED` has `backups.max_images` (1-50) and `backups.interval_hours` (1-168), and `due` converts with `try_from` instead of `as i32`. A number a section saves gets a `FIXED` range.

**Limits drifted between places.**
The prefix panels, the dashboard and the save path each had their own bounds, and an out-of-range value was changed silently. *Avoid:* all bounds live in `core::limits` and are used everywhere. Refuse a value out of range with a message.

**Heat max and decay had no range outside the dashboard.**
Only the dashboard's `heat_ok` checked them, and it let decay 0 through. The `heat` prefix panel took any number (`4 1000` saved a decay of 10, so `(1 - 10)^t` made every heat NaN; `3 0` made every message trip), and the bot used the values as read. Decay 0 meant heat never cooled, so an auto slowmode channel was never calm. Panic mode's `heat_decay` had no range either. *Avoid:* `HEAT_MAX` and `HEAT_DECAY` live in `automod::heat` and go through `core::limits::float_for_path` (dashboard, import and MCP saves, the prefix panel's `Kind::Num` rows), and the bot clamps when it reads (`HeatCfg::clamped` in `AutomodCfg`'s deserializer, the panic decay in `add_heat`). A number the bot divides by, raises to a power or waits on gets a range in `limits` and a clamp on read.

**A zero quietly switched a protection off.**
Strike cap, multiplier, strike durations, mention lock count and window, the mention hour cap (0 stays allowed: any mention trips), panic window and heat trigger, Join Raid count, span and ID matches, ban purge days and warn points had ranges only in the prefix panels, so the dashboard, import and MCP could save `panic.window_secs = 0` or `mention_window_ms = 0` and the feature never fired. *Avoid:* the ranges live in `core::limits` (`FIXED`, `for_path`), the prefix panels use the same constants, and rollback runs the same `validate`, `limits::check` and `web_mode_error` as a save. `panic.executors` 0 stays "off" on purpose (its dashboard field says "(0 = off)"). Zeros stored before the limits stay as they are (no clamp on read); Overview's security score lists them (`limits::stored_outside`, row "Settings outside their range") so the owner sees which protection is off.

**The dashboard validated a section with a smaller type than the bot reads.**
`verification` was checked as `VerifyCfg`, but the bot parses `VerificationCfg` (also `channel`, `roles`), so a bad role id was saved and the bot read the whole section as default (off). *Avoid:* a section type both sides parse lives in `brim_core::sections` and the dashboard validates with that exact type.

**A range check refused a whole rollback.**
Rollback ran the save's `limits::check`, so one old value outside today's range (`joinraid.count` 800) blocked the rollback a cleanup after a hacked admin needs. *Avoid:* a rollback calls `limits::clamp` first (moves a number to the nearest end of its range, returns `section.path: old -> new`); the rollback logs and returns those (`clamped`, shown in the toast). Saves and imports still refuse, so a user typing a value learns the range. A non-number is still refused.

**A lower limit makes old values look broken.**
Auto slowmode's maximum dropped from 6 hours to 2 minutes. A server with an older 21600 got the Overview warning "Settings outside their range" (which says 0 switches the protection off), although the bot reads that card clamped and the value works at 120. *Avoid:* `limits::stored_outside` marks values the bot clamps on read (`CLAMPED_ON_READ`) with `(used as N)`. When a card gets a `clamped` on read, add its prefix there; when a range shrinks, check what Overview and the form say about older values.

- **An "on" default for a switch that acts on members would start removing roles unseen.** Config sections use `#[serde(default)]` with the struct's `Default`, so a new default reaches every saved config that lacks the key at the next bot start, and every server with no saved config (`GuildCfg::default`). For `misc.enforce_permits` that takes dangerous roles from staff without a permit, also on a just-added server. *Avoid:* the bot default stays off; "on by default" lives where a person confirms: the wizard card presets it on (`Card::preset`), Overview shows a row with a Fix while it is not saved on, and every save that turns it on asks first with the live list from `/enforce-permits` (`form::ask_enforce`). That list uses the bot's rule (`antinuke::enforce_permits`): not a bot, no level in `permits::holders`, a role below Brim that is not managed and holds `DANGEROUS_PERMS` with a Role lock's saved bits added. Use a migration for a default (as for `always_dm`, 2300; the verification fail action, 4000) only where the change cannot take something from members.

**The dashboard role's limits were gone after a rollback.**
`db::set_dashboard_role` narrows the role at every bot start, but an older bot image runs its own list (`GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES`, no revokes), so a rollback gave the role every row right again. Root cause: a limit that only the newest code sets does not survive older code; grants are state that every image rewrites. *Avoid:* a limit that must hold on every image lives in a migration (an older image runs no down step): migration 4043 `dashboard_role_limit` row triggers refuse (42501) for `current_user = 'tommybot_dashboard'` what the column grants refuse. A trigger checks values, not the columns a statement names (the #357 image names every `case_proofs` column with `verified = false`). A grant that leaves a column out also refuses a chosen value for it: the staff proof's `id` and `added_at` must be the defaults (a chosen `id` would take the sequence's next values and block the bot's verified proofs). A trigger function that guards a role sets `search_path = pg_catalog, pg_temp`, or the caller puts its own `pg_temp` operators in front of the check. The same holds for history and log lines (`case_edits`, `note_edits`, `mod_actions`, `raider_evidence`): "no UPDATE" alone still let the role DELETE a line and INSERT it again with the same id and any text or time. Append-only means INSERT on the named columns only (no `id`, no time) and no DELETE; a case's or note's delete removes its lines through the foreign key, which runs as the owner. A new dashboard write to one of these tables needs its column in BOTH the grant and the trigger's argument list; `dashboard_role_has_rows_only` grants everything back as an older image does and runs the refusals again against real rows (a row trigger does not fire for `WHERE false`).

**Only the browser checked the typed server name before a delete.**
`purge` checked Owner level, 2FA and the physical owner, but a direct call skipped the name PRIVACY.md promises. *Avoid:* a confirmation that the notice or the UI names (a typed name, a code) is also checked on the server, after the access checks so a refused user still gets 403.

**Dashboard twins of bot actions were weaker: appeal blacklist and pinging messages.**
The appeal blacklist add and remove routes needed only an Editor, with no `appeals` permit and no panic mod lock, while the bot's Deny + Blacklist button needs both. Send and Edit of a built message checked only the webhook case, so an Editor could send a Trusted Admin's @everyone message again and again. Appeal answers went into the staff log as raw markdown. *Avoid:* a route uses its bot twin's checks (`reviewer` and `mod_lock_guard`; the page access follows the route). Send and Edit refuse below Admin when the allowed mentions name anyone (`pings_members`: `parse`, `users` or `roles` not empty), the same bar as saving. User text in an embed goes through `msgvars::escape`.

**Error texts named the wrong cause, and two config log lines had no version.**
`users_only` told an owner to "try again" for an id Discord does not know (`Ok(None)`), a failed `/users/@me` at login showed raw JSON, and every 2FA setup DM failure said "allow DMs". The Discord AutoMod rule routes and the word migration committed a version but logged without it. A second tab turning Tickets on made a second category and log channel. *Avoid:* match each failure kind (404 user, Discord 403 on a DM, others) to its own text. A route that commits a version logs it (`audit_version`). A setup that makes Discord objects before its commit holds a try-lock (`tickets_setup:`) and reads the version again under it.

**The MCP DM showed `"pings": null` for a save that keeps @everyone.**
`Save.pings` reads a JSON null as missing (keep the stored pings), but the preview filled in the stored value only for a missing key. *Avoid:* the preview treats a null like a missing key wherever the route does. Check how serde reads `null` for each `Option` field the DM shows.

**An MCP change stuck in `running` kept its body.**
A restart between the claim and the final update left the row `running` with its body, and expired bodies were cleared only on the next MCP call. *Avoid:* `mcp::service` and the bot's hourly prune (`welcome::purge_left`) close `running` rows older than 15 minutes and expire pending ones, both with `body = null`.

- **Check access before you look at the body.** `put_section` and `import` validated the input before the level check, so someone without access learned the shape of a section from the error. *Avoid:* call `require` first, then validate.

- **A section struct without `#[serde(default)]` breaks the first save.** `RaidCfg` had required fields, so turning Join Raid on for a server that never saved it was refused ("missing field `suspicious_only`"). *Avoid:* a config struct with a `Default` impl gets `#[serde(default)]` on the struct.

- **A number field without a schema default must be optional in the config struct.** The form saves an emptied field as its default, or `null` without one. Join Raid's `id_margin_ms` is a plain `i64`, so emptying it made every save fail. `schema::tests::number_fields_without_default_accept_null` checks every field, and `one_field_alone_deserializes` checks every section loads with one field set. Stepping an optional field back to 0 empties it: Join Raid's ID flag at 0 would flag every joiner in a raid. *Avoid:* give a page whose main action is a write `need(level)` in `access::page`, or disable the button with `Access::rank`.

- **A missing `enabled` key was read as on.** Overview's switches guessed their own defaults and showed Anti Nuke and Join Raid on for a server that never saved them, while the bot, the security score and the pages read them as off. The settings pages ringed cards red only when `enabled` was literally `false`, so a never-switched-on system showed no "Not in use" ring. *Avoid:* read a missing switch as the bot does (the schema default, off for every system). Never keep a second copy of a default in the UI.

- **An action ran something other than what was reviewed.** Push ran the draft stored at that moment, which another editor (or a late save) could have changed after the preview. *Avoid:* every reply carries a version of what it shows (`updated_at`), the action sends it back, and a mismatch is refused with 409.

- **A filter meant for display also weakened the check.** Member overwrites were left out of the issue list so they would not make rows pulse, which also let a dangerous member overwrite through Push. *Avoid:* filter for display where it is shown. The list that decides keeps every row.

- **A picker's filter is not validation.** The UI left the quarantine and main roles out of the role picker, but the server took any role id, and the UI's own list still offered roles the server would refuse. *Avoid:* the server validates with the same rule (`Ctx::pickable`) and sends the allowed ids, and the UI offers only those.

- **A body extractor answers before the handler's own check.** The "not through the tunnel" check sat inside the handler, after `Json(..)`, so a request without a JSON body got 415 instead of 404 and the route showed it exists. *Avoid:* a check that must refuse before anything else is a `route_layer` middleware, not the first line of the handler.

- **The config-change log read the new config.** A save that cleared or moved `logging.config_changes` was announced only in the new channel, so clearing it hid itself. *Avoid:* a caller that saved a version passes it to `log_change`, which then also posts to that version's predecessor's channel. Events that saved nothing post to the current channel only, or moving the log would not stop them reaching the old one.

- **A server error said only "internal error".** Fix All showed "Staff cannot use their channels (internal error)"; the cause (Discord 404 on a permission overwrite) was only in the dashboard log, with nothing that tied that log line to the toast. **Rule:** `ApiError::Internal` answers "Server error, code XXXXXXXX. The cause is in the dashboard log." (a Discord cause `internal_text` recognises: its plain text plus " (code XXXXXXXX)") and logs the full cause with `error_id=XXXXXXXX` inside the request span (method, path, server id), so `logs_tail` (dashboard, contains the code) finds the line. The code is random per error and carries nothing internal. Errors with a cause the user can act on keep their own text (`BadRequest`, `Forbidden`, `TooMany`, `Busy`). A log field named `code=` after `?`/`&`, or a JSON `"code"`, is masked by `logs_tail`, so the field is `error_id`.

- **A dashboard change was recorded only in a Discord channel.** `log_change` posted the line to the config-changes log channel and kept nothing, so a server with no such channel (or a deleted one) had no record of who changed what. *Avoid:* `log_change` takes who made the change (`by`, 0 for Brim itself) and stores every line in `dashboard_audit` before it posts (migration 4031, 90 days, removed with the server's data). The dashboard role may insert but not update those rows. A new record of who did what is stored first and posted second.

**The dashboard had no script rule (Content-Security-Policy).**
Only `frame-ancestors` was set; the UI writes message previews and emoji as raw HTML, so one escape gap would run a script with the viewer's session. *Avoid:* every response gets `script-src 'self' 'wasm-unsafe-eval'` plus the hash of each inline script of the built `index.html` (`script_csp`, made at start). A server-made page (verify, raid report) gives its scripts a new nonce (`nonce_csp`) and has no inline event handler (`onclick=`): set the handler from the script. A new inline script in `index.html` needs nothing more; a new script host must go in the rule.

- **Numbers with no range at all.** `panic.executors`, `joinraid.active_ms` and `automod.heat.similarity_floor` took any value, so 999999999 executors or a similarity above 1 switched the feature off silently. *Avoid:* every number the bot acts on has a range in `core::limits` (`FIXED` or `float_for_path`, and `ranged_paths` for a new float); executors may be 0 (off). The bot clamps the similarity on read (`HeatCfg::clamped`), like heat max and decay. The heat weights (`heat::WEIGHTS`) go from 0 to the max heat in the same section (`limits::float_range`, clamped on read too; a negative weight cooled a spammer). A new weight goes in `WEIGHTS` and `weights_mut` (a test checks they match). A filter's "Action duration" (`filters.<key>.duration_secs`) is 0 (default) to 365 days (`FILTER_DURATION`).

- **A phase shipped without the plan's safety rules for it.** PR #229 went up without the plan's 4d.7 and 4d.8 rules (sends during panic, lockdown or a nuke case; no edits in log, ticket, verification or appeal channels; caps and banned categories for "+ New channel"), because the build read the phase line and not the safety sections. *Avoid:* before a phase PR, grep the plan's safety sections (4, 4b, 4c, 4d, 4e) for every route and feature the phase touches, and list each rule as built or deferred in the PR.

- **A global header layer overwrote a route's stricter header.** `SetResponseHeaderLayer::overriding` for Content-Security-Policy replaced the `sandbox` policy that `/media` sets. *Avoid:* global security headers use `if_not_present` when a route may set a stricter value of its own.

- **A JSON body that is not an object panicked a handler.** `spec["channels"] = ..` on a user-sent `Value` panics when it is a number or a string. *Avoid:* use `as_object_mut` (or a typed struct) before writing into JSON from a request.

- **A stored id was trusted at use because it was checked at save.** Log channels, the appeal channel, the dashboard's Lockdown Update post, the verification channel (anti-nuke invite back, verification retry invite), ticket categories and verification roles were checked to be in the server only when saved. An id saved before those checks (or written by another path) could post one server's logs or appeal answers into another server, make an invite there, or count another server's role as safe. *Avoid:* every send, invite, parent or role grant that uses a stored id checks at use that the object is in the same server: bot logs through `events::send` (error, no owner DM); dashboard logs through `Discord::post_log_with` (`private_channel_of`, which like the bot also refuses a channel a main role can read); invites and verification roles against `guild_info`; categories by the fetched channel's `guild_id`. A role or channel missing from the server's lists is not used.

- **The Update page showed no change lines because it only knew merge commits.** `update::changes` listed a pull request only from a two-parent "Merge pull request #N" commit, but main has used squash merges since #335 ("Title (#N)", one parent), so every list was empty ("Newest" showed a hash only, Install rows had no lines). *Avoid:* `update::commit_change` reads both forms; a build's lines come from one compare of the oldest to the newest build, split at each build's commit (`changes_per_build`), so the list costs one GitHub call per new pair. The oldest listed build has no lines (its base is not in the list). A finished update shows the lines of the installed build, not of every build it skipped. Same package: the Servers page takes `banner`, `owner` and `permissions` from Discord's `/users/@me/guilds` (no new scope), lists servers where the person may add the bot (owner, Manage Server or Administrator) as `addable`, and "Add to server" is `/auth/invite?guild_id=<digits>`, the existing invite with that server preselected (same scopes and permissions; a non-numeric id is ignored).

- **A switch showed on while the server ran it off.** The schema (`crates/dashboard/src/schema.rs`) gave `giveaways.enabled` the default `true`, but `GiveawaysCfg::default` is off (owner decision), so a server with no saved giveaways settings showed the switch on while Start stayed off. *Avoid:* the `default` of a schema field must equal the Rust `Default`; a test checks the giveaways switch, and every new `dv(.., true)` on an `enabled` field needs the same check against its Rust default.

**The Update page showed "Newest: Could not reach GitHub right now." and an empty release list after a release, with nothing in the log.** `update::get_json` turned every failure (no connection, the hourly limit of 60 unauthenticated calls per server address, a bad answer) into `None` with no log, and `builds` kept no list, so one failed refresh emptied the page. The limit is shared with the GitHub feeds and with the compare and pull request calls of one page load. *Avoid:* log a failed call (WARN with the url and reason) and send its reason to the page (`error`); name the limit with its reset time; keep the last good release list on a failed refresh, and do not retry a failed refresh for 30 s. `GITHUB_TOKEN` (public read only, already passed to the dashboard) is sent to api.github.com calls only, never to the registry. Every GitHub call of the dashboard is in `update.rs` (`get_json`, attestation check, which returns its own error) and `feedfollow.rs` (already names its limit).
