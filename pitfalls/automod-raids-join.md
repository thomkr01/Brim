# Pitfalls: Joins, verification and raids

Index and rules: [PITFALLS.md](../PITFALLS.md).

**Verify answered after the grant, and errors left no answer.**
Verify Start and the solved captcha ran `self_grant` (reads, a member PATCH in the busy member bucket, logs) before `create_response`, and every `?` went to `events::handle`, which only logs. During a raid, or for a member in another quarantine, Discord showed "This interaction failed". Same hidden reason: a failed ticket close always said "check that the bot can send files", and `note add` with closed DMs said only "Could not DM you" although the note was saved. *Avoid:* slow work after a click runs after a defer and edits the answer; a failure is mapped to text that names the cause (`verify::grant_failed`, the `send` refusal or `http_err::why`). A DM challenge waits at most `DM_WAIT`.

**"Quarantine on join" replaced the roles of members who were not held.**
`grant` replaced the role list when `quarantine_on_join` was on, so a never-quarantined joiner, an old member, or one just released by `t!verify` lost every role. *Avoid:* only `replace_roles` or a real join quarantine (`quarantine_kind == Some(true)`) replaces roles; otherwise roles are added.

**An unsaved verification channel was made again for every joiner.**
`adopt` only logged a refused save and posted the panel anyway, so `channel` stayed empty and each joiner made another channel, up to the cap in a raid. *Avoid:* `ensure_channel` deletes a channel it could not save, waits 10 minutes per server before it tries again, and tells the owner why.

**An unlock lifted invite and DM pauses the lock did not set.**
The unlock sent `pause_invites(None)`, which clears both pauses, so the owner's own 24 h pause (or one a Discord AutoMod rule set) ended with a 10-minute lock. *Avoid:* before a lock pauses invites, `plan_now` reads the guild's `incidents_data` into the snapshot's `prior_pauses`, and the unlock puts back each end still ahead (`set_pauses`). A failed read, or one slower than 2 s, does not stop the lock; that unlock lifts both, as before.

**The adder of an unauthorized bot got the harshest action of all the bot's filters.**
`adder_action` was the harshest action over every filter the bot matched, so a No Avatar ban banned the member who added it. *Avoid:* the adder gets the Unauthorized Bot filter's own action.

**One refused channel stopped hiding the rest from a quarantined member.**
`hide_channels` used `?` on each channel's deny, so a 404 (a channel deleted in the nuke) or a 403 left every later channel open. *Avoid:* the loop logs each failure and goes on, returns an error naming the failed channels at the end, and `hide_channels_best_effort` posts it to the Anti Nuke log. Containment first: when `deny_member` cannot save the member's own overwrite, the deny still goes on, and the log names that overwrite's allow and deny bits, since it will not come back on release.

**Automod, NSFW scan, invites and raiders: eight small gaps.**
"Not NSFW" was allowed "from now on", but the 30-day sweep (and the failed-punishment cleanup in `act`) deleted its `feedback = 'fp'` row, the only memory of it. A failed NSFW catch-up sweep marked the server swept and never retried, one unreadable config ended the pass for all servers, and the enabled-servers query read every stored config version. The raid detector redid the ID-farm analysis per joiner per bucket under a blocking mutex, with no cap on the window. `is_public` let 192.0.0.0/24, 198.18.0.0/15, 240.0.0.0/4, NAT64, 6to4 and 2001:db8::/32 through. Any non-Brim unban counted as staff allowing a raider, a bot's too. `LockKind::mask` always held View Channel, so unlocking a plain Server lock gave it back although only Blind takes it. The invite tracker credited a code that was one use short and also expired. *Avoid:* a row that is a user decision is exempt from every retention sweep and cleanup; a "done" set is filled only after the work succeeds; a trust record from an audit actor needs the actor's permit and a human check (`has("ban")` covers Owner, EO, TA); an unlock mask lists only what the lock took; a per-joiner analysis is computed per bucket and its window capped (`MAX_JOINS`). Not fixed: a code deleted by the invite-delete event while one use short still counts as a last use, since Discord sends that event for a last use too.

**A verified-member cache outlived the membership.**
`verify::given` remembered a verified member for 10 minutes, also across a leave and rejoin, so a bot's role grant to the rejoined unverified member was not taken back. *Avoid:* state about a member's stay is forgotten on `MemberRemove` (`given::forget_member`, before the event's first await).

**Leaving and rejoining ended a quarantine.**
The `quarantines` row survived a leave, but no join code read it, so a quarantined member who left and came back was a normal member again. (Timeouts survive a rejoin in Discord itself, strikes and warn points are stored per user, and join lock and join raid act on every join.)
*Avoid:* state that holds a member back must be re-applied on `MemberAdd`, not only while they stay. `antinuke::requarantine_rejoin` runs first in `joingate::on_join` and goes through `contain`, so a re-added bot loses its managed role's permissions too.
A rejoin while the bot was down sent no `MemberAdd`, so the member stayed free. *Avoid:* an event-driven re-apply needs a catch-up at startup. `joingate::requarantine_missed` runs at GuildCreate: a member with a row who joined after the row and after the bot's last `quarantine` record goes through `requarantine_rejoin`; one who joined before is the same membership (held, or released by hand as `still_contained` allows) and is left alone. It reads GuildCreate's member list when complete and one member per row otherwise.

**The post-join username filter punished immune staff.**
Join Gate's username filter checks names again after join (the "POST join" switch) and called `punish` without a level check, so an Extra Owner or Trusted Admin with a word-list nickname could be kicked or banned. At join time nobody is staff yet, so the gap showed only after join.
*Avoid:* every automatic action against a member who is already in the server checks `is_immune` or `whitelisted` first. The one deliberate exception is auto-dehoist (and Join Gate's Rename through `dehoist::rename`): it skips only the owner and Extra Owners, so Trusted Admins and mods are renamed too.
Join Raid had the same gap: when a raid triggers, it punishes every joiner it flagged in the window, and an earlier joiner may have been made staff since. The loop skips immune ids other than the joiner. A failed lookup punished anyway, so a Discord error could ban a Trusted Admin: it queues the `raid_punish` retry, which checks immunity again and fails (so it runs again) while the lookup still fails. *Avoid:* when an immunity check fails, wait and check again; never read an error as "not immune" before a removal. Voice raid checks members flagged earlier in the window the same way, and disconnects a member whose check failed at once: only the punishment waits for the retry.

**A download without a size cap could fill the bot's memory.**
Ticket and modmail relays copied attachments with `.bytes` then `to_vec` (twice the size in memory). `Sites::fetch` read the whole body when Content-Length was missing. The phishing/NSFW list refresh read any size and took an empty or garbled 200 as the new list, switching those filters off for 12 hours. Only the IP list reader capped and refused a shrunk list. An out-of-memory restart wipes in-memory protection state.
*Avoid:* read outside bodies through `sites::read_capped` (Content-Length and running total), with a cap above the real source size (NSFW list about 18 MB: domain lists 64 MB, IP lists 20 MB). A failed first load is logged as an error (the filter is off). Refuse a refreshed list that lost over half its entries unless the next refresh brings a non-empty count within 10% of it (`sites::ShrinkGuard`, shared with IP lists). A list that is on but empty is retried after 1, 5 and 15 minutes, not 12 hours (`sites::next_refresh`). Ticket files are copied up to Discord's 25 MB per message in total; the rest is linked, and the staff message holding it is kept. The NSFW scan fetch goes through `Sites::fetch`.

**A Raider List hit was invisible to Join Raid.**
`joingate::on_join` returned right after the list acted, so listed raiders never counted and a raid of partly listed accounts did not trigger.
*Avoid:* an early return on a protection path must not skip the counters of the next check. The hit counts (`RaidDetector::note(.., listed)`) and the raid skips whoever the list already punished.

**A command that can end a quarantine skipped every target check.**
`t!verify` ends a quarantine but `ModCmd::target` did not list it, so the release guard (staff saved in the quarantine go free only through an owner or TA), the hierarchy check and the self check never ran: the verify permit freed any quarantine, a nuking admin's too. The guard also looked only at permit roles, so a saved role with Administrator but no permit counted as a plain member. Per-command checks hang off `target`; a new member command must be added there by hand.
*Avoid:* every command that acts on a member returns it from `target`. `verify` ends only verification's join quarantine (`on_join`); any other needs the `quarantine` permit; saved roles holding `DANGEROUS_PERMS` count as staff. The dashboard revert skips Unquarantine, the Raider List releases only its own quarantines, verification buttons lift only `on_join`.

**A bot cannot change its own role, and a role between the bot and quarantine trips a check.**
Discord refuses any edit of the bot's highest role ("Missing Permissions", even with Administrator), so hoist and colour cannot go on it. A second role right under the bot would sit between the bot and the quarantine role, and Overview would warn "Quarantine role not right below the bot".
*Avoid:* the bot gets its own display role with no permissions (`sections::show_bot`), placed right under the quarantine role, not under the bot. Auto Setup sets the whole order below the bot in one move (`order_roles`): Quarantine, display role, staff, other roles, Member. A display role a member also holds is never reused (it sits above staff, who then could not moderate that member). Only a role the bot holds, with its name and no permissions, is reused; a made role the bot could not be given is deleted again, so a retry makes no second one. `channel_access` bot roles are managed roles only, so the display role gets no channel access.

**A captcha decoy could be drawn cut off at the image edge.**
Spread decoys were centred anywhere, so some were cut at an edge, and a test asserting a clear corner failed at random.
*Avoid:* keep every drawn shape whole inside the image (`captcha::glyph` clamps the turned box 1 px inside). A test of random output asserts only what holds for every draw, checked over many draws.

**A captcha answer could be guessed without limit.**
A wrong answer only said "Wrong answer" and kept the code alive until it expired, so a script could try many readings of one image. Also a real font draws `l` as a bar like `I`, and the answer ignores case, so `i`, `l`, `I`, `L`, `O`, `o`, `0` must stay out of the answer set.
*Avoid:* every answer check counts wrong answers per code and drops the code after `verify::MAX_TRIES` (3); the member presses Verify for a new image. When a font changes, check which characters look alike in it before they can be an answer. The image captcha and simple sum share one answer path (`app.captchas`, the code modal), so both get the limit; web verification uses Turnstile.

**A failed command reply or lookup skipped automod.**
The ticket relay and command steps before `automod::on_message` used `?`, so a 403 on the reply or a DB error in `commands::ignored` left `t!ban x <scam link>` unchecked. *Avoid:* the command block runs in its own `async` block whose error is only logged; automod always runs after it.

**A failed join lock read skipped the whole join.**
`lockdown::join_lock(..).await?` returned from `on_join` before raid counting, verification and the Join Gate, so a pool timeout in a raid let every joiner in unchecked. *Avoid:* an unread lock is logged and skips only the lock's kick or ban. Do not queue a retry: `raid_punish` does not read the lock again, so it would kick joiners when no lock is on. `on_join` returns only when `punish_or_retry` removed the joiner (a lock kick that did not remove them, by refusal or a retry due in 30 s, must not skip counting, holding and the gate).

**A raid's log, owner DM and lockdown came before its punishments, and punishments ran one at a time.**
`join_raid` awaited the trigger log, `alert_owner` (up to 3 s) and `lockdown::lock` (one Discord call per role or channel) before punishing the first wave, and each punishment awaited its DM. The mention spam lock did the same in automod. *Avoid:* punish first: the raid spawns the log, DM and lock task (not awaited) and punishes the flagged list at once (`join_all`); the lock must not wait for the whole first wave either. The mention spam lock runs in `automod::check` after the punishment, as auto slowmode does. An earlier flagged joiner's level is read from the roles of their join (`RaidDetector::set_roles`, a DB read), not by a member fetch per flagged joiner (they queue before the bans). A member update forgets those roles, so that member is fetched again; a TA or EO added by id is still seen, because the level is resolved again.

**A Join Gate, bot adder or Raider List ban refused by an outage was never retried.**
These paths called plain `punish`, so a 503 left the account in the server with nothing queued, and the gate counted it as removed (same as "A join lock's failed kick let the joiner stay"). *Avoid:* they use `punish_or_retry` (it takes the gate's `Detail`), and "removed" comes from its result. `queue_retry` keeps one pending `raid_punish` per (guild, user) with the harshest action, in its enqueue SQL (the join lock, Raider List, raid and gate could each queue one). A Raider List outage counts as "the list acted" (the raid and the gate skip the joiner); a refusal does not (the join goes on, verification holds them). The retry of a list kick or ban writes its case, `raider_actions.case_no` and mod log (`raiders::join::retried`), so staff can undo it.

**Verification fetched the joiner's level on every join.**
`verify::on_join` called `is_immune` (a member GET) though `on_join` had read the level from the join's roles: one extra GET per joiner in the bans' bucket. *Avoid:* `verify::on_join` takes the `immune` that `joiner_immune` read; unread (None) holds the member.

**Replayed voice audit entries counted at "now".**
`voice_nuke::note` counted through `antinuke::count`, so moves made during a gateway gap landed in the live window. *Avoid:* `note` takes `replayed` and counts through `count_at` with `replay_age`, as the other cards do.

**The join lock, join gate filters and raid punished an immune joiner, and a bot's adder was punished on an unread level.**
None of these join steps asked the joiner's level, so an Extra Owner or Trusted Admin who rejoined during a join lock was removed; a failed adder lookup counted as "not immune". *Avoid:* `on_join` reads the level once from the join's own roles (`joiner_immune`, no member fetch per join). Immune: every punishing join step is skipped. Unread: nothing punishes now, `hold_back` queues the `raid_punish` retry for a kick, ban or timeout (it reads the level again), and the rest of the join still runs (verification holds them; never return early on an unread level). A bot is never immune, so it is not read. The bot adder uses the same rule. The Raider List (`exempt` with `?`) and the post-join username filter (`is_immune` with `?`) already refuse on an unread level.

**A join lock's failed kick let the joiner stay, and skipped the re-quarantine.**
The join lock ran before `requarantine_rejoin` with plain `punish` and returned its error, so a 5xx left a quarantined nuker in with no role and no retry. *Avoid:* `on_join` re-quarantines first, then the join lock uses `punish_or_retry`. A security step that comes first in a handler must not return early before a step that contains.

**A Join Gate retry sent the punishment DM again.**
`punish` sends the DM before the action, and each `raid_punish` retry called `punish` (six DMs). *Avoid:* `punish` is `tell` then `act`; `punish_job` calls `act` only. The first try still DMs before a kick or ban Discord may refuse (not changed).

**A DB error at GuildCreate skipped the missed-rejoin quarantine.**
The `guild_left` delete and `owner_seen` used `?` before `requarantine_missed`, which queues its retry only once it starts. *Avoid:* in `on_guild_create` each step logs its error and the next one runs.

**Verification jobs treated any Discord error as "member left".**
`verify::deadline` and `verify::web_grant` began with `let Ok(member) = guild_member(..) else { return Ok() }`, so a 5xx or timeout ended the job: an unverified member never removed, or a web-verified member never given roles. *Avoid:* use `http_err::member`: `None` only for a member who is gone, an error (the job retries) otherwise. (`purge.rs` and `nsfw.rs` use the old form only for best-effort details.)

**A second heat panic replaced the first wave of raiders.**
`panic::note` inserted a fresh raider set and end time, releasing wave 1 early. *Avoid:* while heat panic is on, a new trip adds to the live set and keeps the later end.

**Membership was checked when roles were claimed, not when they were added.**
Sticky roles checked the member once, at the claim, then added roles later (a job a minute on, after verification, when a timeout ended). By then the member could have left and rejoined, been banned, quarantined or sent back to verification, and still got the old roles. Errors after the claim (a failed read, a refused add) dropped the claimed list, and a join where any step acted (even a Log hit) froze the row, so the next rejoin got roles from two memberships ago. `timeout_roles::restore` had the same gap and gave main roles back to a quarantined member.
*Avoid:* every delayed add carries the membership it was claimed for (`joined_at`) and checks again right before the add: same `joined_at`, setting on, no quarantine row, not pending (`sticky::due`). Do fallible reads before a claim, and put whatever a claim took and could not finish into a job. A ban leaves a tombstone row instead of deleting, so a late event of the old membership cannot write it back.

**"Nothing saved" was used to mean "join quarantine".**
The fix above told the kinds apart by an empty `saved_roles`. But a staff, Raider List or time-limit quarantine of a member with no roles also saves nothing, so such a member could verify out of it on the web page; and an autorole landing before the join quarantine filled the list, making it a real one: the joiner could never verify and the autorole bot was punished. Verification also lifted the join quarantine only while "quarantine on join" was on, so switching it off left members held with a stale row, and a rejoin then logged an anti-nuke "rejoined while quarantined" for a joiner who had only not verified.
*Avoid:* never infer a kind from what a field happens to hold; store it. `quarantines.on_join` (migration 3900) is set only by verification (`antinuke::Kind`), a real quarantine always wins over a join one (`on_join AND EXCLUDED.on_join`), and `self_grant`, `grant`, `hold` and `requarantine_rejoin` read the flag. `grant` ends a join quarantine whatever the setting is now, and a rejoin into a join quarantine counts as verifying for sticky roles. A join raid hit that keeps the member (Log, Warn, Timeout, Rename) drops their saved sticky roles (sticky-roles plan decision): kept pending, a raider got them back by verifying (web, staff `/verify`) or by leaving and rejoining. `restore_pending` reads the member's live timeout before it claims, because web verification and staff `/verify` work during a timeout, which holds the main roles. Rows from before the column with nothing saved were marked join, as they were treated until then. The time limit's Quarantine is still a join one only when the member had no roles, until an owner decision says whether verifying should lift it.

**A quarantine left channel access from overwrites.**
Quarantine swapped roles only. A member's own allow overwrite, or one for a managed role they keep (booster, a bot's role), still let them read and act (an allow beats the Quarantine role's deny); a new overwrite for a quarantined member was never checked. *Avoid:* after a real quarantine `contain` calls `hide_channels` (own step, after the role change and the `quarantines` row, so `save_row`/`restore_row` are untouched): in each channel that grants them access it adds a member overwrite denying those bits and saves the old one in `quarantine_overwrites`; `Inverse::Unquarantine` puts them back. `hold_overwrite` undoes a member overwrite that gives a quarantined member new access and quarantines the actor. A managed role's overwrite that later grants more (`hold_role_overwrite`) gets the same member deny for every really quarantined member who holds the role, without punishing the actor (staff set up booster channels). Join quarantines are left alone.
Access taken back works both ways: a lost deny is a grant like a new allow, so clearing the quarantine's own member deny or deleting that overwrite (`ChannelOverwriteDelete` goes to `hold_overwrite` too) is put back and punished; a managed role's lost deny gets the member deny. A "more access" check reads both the allow and the deny change. When the actor's quarantine whitelist cannot be read, both holds (and `guard_perms`, `guard_permit_roles`; `guard_lock` sets back without counting) undo the grant but quarantine nobody and say so in the Anti Nuke log (`hold_whitelisted`; owner decision, undo not punish): returning on the error left the member what they were given. In a nuke the hiding runs after the revert (`contain_with(.., false)` in `revert_and_report`) so it does not hold up recreating deleted channels.

**A quarantine row was read as "still contained".**
A nuke run decided "already quarantined, only revert the late entries" from the row alone. The row stays when a Quarantine Whitelist user gives the roles back by hand, with Quarantine Hold off, or when the hold's undo fails, so a nuker released and nuking again was only reverted: no new quarantine, case or owner alert. A later quarantine also kept the old saved roles (`ON CONFLICT DO NOTHING`), so a demoted mod got the old Mod role back on release.
*Avoid:* decide from Discord whether the stored state still holds. `still_contained` needs the row and the member holding only what `quarantine_roles` leaves (`held`), and for a bot its managed role cleared; a member who left falls back to the row; a failed read counts as not contained. A new real quarantine saves today's roles and restarts `created_at` only when the member holds a role quarantine would take and joined before the row was written (a rejoin with autoroles, a member with no roles, or one missing a recreated Quarantine role keeps the valid list). The failure undo (`restore_row`) is a compare-and-set on the row version `save_row` wrote (`xmin`, new on every write; `xmax = 0` tells an insert from an update), so a quarantine written meanwhile is never deleted or downgraded; a re-applied one (rejoin, sticky roles: `Kind::Again`) keeps the saved list, and a failed role change puts the old row back. `dehoist`, `timeout_roles`, `sticky::due`, `commands` and `info` still treat any row as held, which only holds back more.

**The quarantine overwrite hid the verification channel.**
`enforce_quarantine` (ChannelCreate and ChannelUpdate), `t!setup` step 5 and the dashboard's Auto Setup and score Fix denied the Quarantine role View Channel in every channel, the verification channel too. With "quarantine on join" a joiner could not see the Verify button and was kicked at the time limit. A ChannelCreate of a channel the bot just made can arrive before the bot saved it as the verification channel.
*Avoid:* the verification channel gets its own quarantine overwrite, not a skip: allow exactly View Channel and Read Message History (an extra allow such as Manage Messages breaks the shape), deny the rest of `QUARANTINE_DENY` plus Use Application Commands and Use External Apps (`brim_antinuke::verification_shape`). Skipping it left a real quarantine free to send, react, make threads and invites there, never repaired and hidden from the score; the channel id is an Editor setting. Every writer uses the shape: `ensure_channel`, the remake after a delete (replaces the copied quarantine overwrite), `t!setup` step 5, `enforce_quarantine` (also repairs a channel D55 already hit), the dashboard's Setup Channel, `quarantine_channels`, Channel Setup's push; the score checks for it. Setup Channel also puts the shape back once the channel is saved (`reshape_verification`): with verification off the bot denies a new unsaved channel, and nothing repaired it when verification was switched on later. A shaped channel that is not the saved one counts as a new verification channel only while verification is on and no live channel is saved (a saved id that 404s counts as none); `enforce_quarantine` takes `verify::CHANNEL_LOCK` only for that check, because the bot saves the channel it made under the lock and its ChannelCreate can come first.

**A raid outcome was assumed, not checked.**
`joingate::on_join` skipped the Join Gate and verification once the raid's action *would* remove the joiner, so a raid ban that Discord refused left the joiner in with no quarantine, and a raid set to Kick cancelled a Join Gate Ban, so the raider could rejoin at once. *Avoid:* decide on what a punishment did, not what it was meant to do: `punish_or_retry` returns whether the member was removed, and the gate still bans after a raid kick.

**A startup catch-up read one member per row.**
`requarantine_missed` did a member GET for each `quarantines` row at every GuildCreate, in the bucket that kicks and role edits share, and rows from members who left pile up. *Avoid:* read members in pages (`GET /guilds/{g}/members?limit=1000`, its own bucket), and put the check off while a raid or lock is on, in one `requarantine_missed` job per guild (`jobs::replace`; `enqueue` started a chain per GuildCreate) and for 30 minutes at most, then run anyway (a GuildCreate takes the first wait from the pending job, so a re-identify does not restart the 30 minutes; `lockdown::Deferred`). The job is in `jobs::HEAVY`: it pages members and would hold back unbans and raid retries in the serial light worker. A failed run queues the job too, and runs take a per-guild lock, so a restart's job next to GuildCreate never quarantines or logs one rejoin twice (the second run sees the first's action_log rows). Compare Discord's join time with a DB time only with a 30 s margin, since the two clocks differ.

**The Join Gate spammer card took the Rename action.**
`spammer` had no `no_rename`, and the test loop listed six filters, not seven. *Avoid:* every account filter except the username filter has `#[serde(deserialize_with = "no_rename")]`, and the test lists every filter.

**"Is this held member staff" always read no for a quarantined member.**
`top_permit` skips anyone in `quarantines`, so `resolve` gave no permit. A permit holder could release, or give roles to, quarantined staff whose permit came only from roles. *Avoid:* `antinuke::held_staff` reads the saved roles' permits (or the member's own permit rows once migrated) and dangerous permissions. `unquarantine`, the quarantine hold and the Raider List's release on removal all use it. Below Extra Owner, the hold's `quarantine` flag and whitelist spare the actor only for a held member who is not staff.

**A deleted main role made "Move to main roles" a dead end.**
The Security score fix refused to run with "a main role no longer exists" when one saved main role was deleted in Discord, without naming the role or a way forward. Saved role lists keep ids of deleted roles (nothing cleans them), and the fix required every id to exist. *Avoid:* skip saved roles that no longer exist and act on the rest. When none is left, say where to pick them again (Lockdown > Main roles). Other dashboard fixes and the lockdown plan already work from the live role list.

- **The in-Discord settings panel (`joingate 1a ?on`) saved the part on but left Server Joins off.** *Avoid:* both writers use `module_to_turn_on`; the panel asks for the same bar (Owner, Extra Owner or Trusted Admin with a fresh 2FA).
