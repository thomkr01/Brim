# Changelog

All notable changes to Brim (called TommyBot before 2026-11-20) are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). TommyBot has no version numbers yet, so changes are grouped by pull request under Unreleased. Changes before #134 are in the merged pull requests on GitHub.

## [Unreleased]

### Added
- Built-in tag `/tag dangerous-permissions` in every server: posts TommyBot's list of dangerous Discord permissions as an embed. The embed is an entry on the Bot messages page (Tags group), so a server can edit it; the list itself always comes from the bot. Migration 4045 lets a `/tag` run post an entry instead of a saved message.
- Commands page: per-command settings for a server (the ⋮ on each row, and "Edit several" for ticked rows), for the Owner and Extra Owners with their 2FA code: prefix form on or off, slash form on or off, up to 5 aliases, a narrower "who may use it" (never wider than the permit), delete the command message, delete the answer after 1 to 300 seconds, answer as a reply, and a cooldown of up to 3600 seconds per member. Stored in the new config section `commands` (no migration). Safety commands (`lock`, `unlock`, `unquarantine`, `anpanic`) cannot be turned off, narrowed or slowed. The slash forms of a command now sit on the command they run (`/ban remove` under unban).
- Cases (review): a case holds several proofs (links, short texts, files kept on the mod log), a **verified proof** marked with a check (a copy of the member's own message, stored when TommyBot punishes by itself, when staff act on a report, and when a moderator punishes in a reply to that message), and an **edit history** (old and new reason, open or closed, removed proofs, who and when). New command `proof CASE [PROOF]`. The dashboard's Cases page lists clean rows; a click opens the case page with details, proofs, history and Edit. Every edit and proof change posts a mod log entry. Only an owner, Extra Owner or Trusted Admin removes a verified proof. Verified proof is kept 1 year by default (Miscellaneous, "Verified proof kept for"); proofs and history go with their case, with the server's data and with a member's own deletion request. Migration 4037.
- Message Builder: schedules (post a saved message on a timetable), triggers (answer words in member messages, or every N messages) and sticky messages (always the last message in their channel), on the message's Automate tab (migrations 3986 to 3988).
- Bot Profile (dashboard, Tools): the server owner and Extra Owners can give TommyBot its own nickname, bio, avatar and banner in that server only. Changes go through Discord's own member profile (`PATCH /guilds/{id}/members/@me`), never the bot's global profile. Each change needs 2FA; Trusted Admins cannot make it. Images are PNG or JPEG within Discord's limits (avatar up to 8 MB and at least 128 x 128, banner up to 10 MB and at least 600 x 240; at most 16 megapixels), decoded and encoded again so EXIF and anything hidden in the file is dropped, and never stored: the history keeps who changed which field, when, the outcome and an image's SHA-256. One change runs at a time per server, at most 30 an hour. Migration 3950.
- Bot status: TommyBot's application owner can set its global status (online, idle, do not disturb, invisible) and an activity (playing, watching, listening, competing or a custom status) on the Update page, with 2FA. The bot applies it at once and again after every new gateway session. Discord has one presence per bot, so it is the same in every server. Migration 3951.
- Tickets 2.0 (owner decision 11-15): ticket panels beside DM tickets. Staff build panels on the dashboard's Tickets page (name, button color, emoji, category, up to 5 open per member, ping roles, greeting and up to 5 form questions) and publish them to a channel as buttons or a dropdown. A button opens a private ticket channel for the member with the answers; it works only on a message the dashboard posted, for a panel that is still on. The same blacklist, pause, raid, quarantine, filter and hourly limits as DM tickets apply; a member who may not open one is told before the form. A panel emoji must be one standard emoji. Migration 3932.
- Tickets: `claim`, `unclaim`, `reassign` (Owner, Extra Owner, Trusted Admin), `priority`, `ticketnote` and `ticketinfo`, and Claim and Close buttons in panel tickets. A note never reaches the member: a DM ticket keeps it in its channel, a panel ticket sends it to the ticket log. The transcript names notes, and in a panel ticket it names the member's messages User.
- Tickets: auto-close after a set number of hours without a message, one setting per server, off by default. A message just before the close stops it.
- Tickets: who did what to a ticket (open, claim, priority, note, close) is recorded without any message text. The dashboard lists open and closed tickets with paging and shows 30-day numbers: opened, closed, the median time to the first staff answer and tickets per panel.

### Changed
- Updates come only as releases (owner decision 11-21): images build only for a version tag `vMAJOR.MINOR.PATCH` on a commit of `main`, not for every push to `main`. The fast checks still run on every push; the slow e2e check runs on a release tag (and on request: Actions > CI > Run workflow), and a release gets images only when it passed. Its browser sweep and updater test now run at the same time. The Update page shows the running and the newest release by version, and **Older releases** lists the newest 10. `latest` is the highest release. The updater installs only images with a release version label. **Upgrade:** after the first release (`v1.0.0`) is built, run the server command once (`cd ~/brim && git pull && docker compose pull && docker compose up -d`), since the Update button does not replace the updater. DEPLOY.md section 4 says how to make a release.
- Rename to Brim, server names: compose project `brim`, database and owner role `brim`, roles `brim_dashboard` and `brim_mcp`, volumes `brim_pgdata` and `brim_logs`, images `ghcr.io/thomkr01/brim-*` (the old repository still publishes `tommybot-*` too), folder `~/brim`, backups in `~/brim-backups`, B2 bucket `brim-backups` in the guide, `BRIM_TAG` (old `TOMMYBOT_TAG` still read). The Update page and the updater use the new repository `thomkr01/Brim`. A server set up before the rename keeps its old names, repository and images with no change: role names, repository and image names follow the database user it logs in as, its Update page gives a command without `git pull`, and the new compose file refuses to start without `BRIM_NAMES=1` in `.env`. The bot also grants the MCP role its views at start (the migrations grant them only to the old name).
- Rename to Brim, app names: the bot's Prometheus metrics are `brim_*` (were `tommybot_*`), the MCP server calls itself `brim`, the Logging page's Brim tab is at `logging/brim/...` (old `logging/tommybot/...` links open it too), message kits export as `brim-messages` (kits exported as `tommybot-messages` still import), and the erasure functions use the flag `brim.erasing` (migration 4054).
- The bot is called Brim (owner decision 11-20): dashboard, default bot messages, docs and the design system. New setups make `#brim-logs`, "Brim messages" webhooks and "Brim" authenticator entries; existing channels, webhooks, codes and edited messages stay as they are. The Discord AutoMod rule "TommyBot keywords" is found and renamed to "Brim keywords" on its next sync. Repository, image, database, crate and env variable names are unchanged.
- One list of dangerous Discord permissions (owner decision 11-20), used by anti-nuke, the role lock, verification, quarantine, backup restore, the security score and the new tag. It adds View Audit Log, Mention @everyone, @here, and All Roles, Manage Nicknames, Manage Expressions, Manage Events, and Manage Threads and Posts to the 9 anti-nuke guarded before. Mention @everyone stays allowed on staff permit roles. Names follow Discord's current names (Timeout Members, Kick, Approve, and Reject Members).
- Dashboard: the Raider List (Settings and Matches) moved from the Moderation module to Server Joins, right after Join Raid, because the list is shared across servers and Join Raid feeds it. Same page keys and links, same access rules; nothing about how the list works changed (owner decision 11-19).
- The dashboard's database role is narrowed: with plain SQL it can no longer write a verified proof, change a report's text, change who a case is about or its kind, or rewrite history and log rows. It keeps the columns its pages change.
- Security (security review): the updater checks GitHub's signed build record of every image itself before it installs anything, instead of trusting the dashboard's request; this needs the server command once (`git pull && docker compose pull && docker compose up -d`), since the Update button does not replace the updater. Ending panic mode early and Raider List decisions are checked again when the bot runs them: an asker who lost the level (or is no longer the bot owner) is refused, and panic mode then keeps running until its timed end. Every dashboard change line is stored for 90 days, also on servers with no config-changes log channel (migration 4031). The MCP server, Postgres and the Cloudflare tunnel now run without Linux capabilities and with no privilege gain like the bot and dashboard (Postgres keeps the five its start needs); the updater gets no privilege gain only. These two changes need the same server command.
- Dashboard look (owner decision 11-18): the dashboard loads the TommyBot design system (`crates/dashboard/ui/design/`: tokens and `bundle.css`) and maps its colours onto it: flat dark slate, rust orange only for the main button and what is selected, yellow warnings, a lighter red, dark labels on status fills, rounder cards, fields and pill buttons, no blur, gradient frame or card shadows, sentence-case buttons and titles, and the spring lift and press on buttons. Dark slate only: the light/dark toggle is gone. Layouts and behaviour are unchanged.
- Phishing and NSFW domain lists: held in one compact set per list (`fst` crate) instead of one string per domain, and the allocator's freed memory is returned after each 12-hour refresh. The two lists used about 100 MB and grew to about 210 MB after a few refreshes; they now stay near 15 MB. Matching is unchanged (the host or any parent domain, same refused entries). A refresh builds the set in about 1.5 s on a worker thread.
- MCP access (owner decision 11-17, security review): the fixed `MCP_TOKEN` and `MCP_WRITE_TOKEN` are gone. An MCP client with a token logs in with a token from the dashboard's MCP tokens page (read and propose changes); an OAuth login only reads. Each read of a server is listed for its staff on the History page (90 days). The `nsfw_scans` tool is removed, and member ids and names are masked in log lines. The bot owner gets a security alert DM on each Raider List confirm or verify, each update and each MCP token change; DEPLOY.md section 9 covers a stolen Discord account. **Upgrade:** make a token on the MCP tokens page, set the token in the header of your client's MCP settings (DEPLOY.md 6.2), revoke the token that was in `.env` as `MCP_WRITE_TOKEN` (it can now also log in and read), then delete the `MCP_TOKEN` and `MCP_WRITE_TOKEN` lines from `.env`. An image from before this needs `MCP_TOKEN` back to start the MCP server. Migration 4021.
- Update page (owner decision 11-17, security review): Update installs exactly the build you approved. The dashboard looks up each image's digest for that build in GHCR and needs GitHub's signed build record for it; the updater pulls those digests only and refuses an image labelled as another build. The MCP server is updated with the bot and dashboard when it runs. **Published builds** lists the newest 10 builds to install, for example to go back. The page warns, with the command for the server, when the updater or `docker-compose.yml` changed since the server was last updated by hand. Needs the command on the server once (the updater must report its version). Migration 4014.
- Verification fails with Kick by default (owner decision 11-17). Migration 4000 moves every server whose newest config had Nothing to Kick, except Web verification, which keeps Nothing.
- Verification: a member who times out 3 times in 24 hours is banned for 7 days, and a server sends at most 20 retry invites an hour. Both counts survive a restart (migration 4002).
- The Owner level and the Trusted Admin list can each have a Discord role, which TommyBot gives to the people on the list by user id and takes from everyone else (migration 4003).
- Number settings that switched their feature off at 0 now have ranges, on the dashboard, in import, MCP and the prefix panels: verification time limit 10 seconds to 7 days (a stored value outside it is read as the nearest end), strike expiry and reoffend window 1 second to 365 days, auto lockdown strikes 1 to 100, NSFW threshold 50 to 99, panic duration 10 seconds to 1 day, warn base points 1 to 1000, and the webhook heat multiplier 0 to 10 (a stored value above 10 is read as 10).
- A new prefix must be 1 to 32 characters without spaces; a stored blank one is read as `t!`, and a stored one with a space keeps working.
- The dashboard loads its Poppins font from the dashboard itself, not from Google Fonts.
- Removed Raider List entries go 30 days after their removal, with their evidence, once no server has a list action left to lift.
- Memory: the image-scan model gives back its load and scan buffers and its embedded bytes after loading (103 MB -> 43 MB measured), and the QR check keeps the codes of images it has already read (by SHA-256, 2,000 entries, 1 hour), so a reposted image costs a hash, not a decode (owner decision 11-18).
- Server resources: the updater image is plain Alpine with a copied `psql` (594 MB -> 183 MB on disk, measured on amd64), and Postgres runs with `shared_buffers=32MB` and `max_connections=40` (about 23 MB less RAM). Needs `git pull && docker compose pull && docker compose up -d` on the server once (owner decision 11-18).
- Dashboard download: the web app was built without wasm-opt (a 37.7 MB wasm, 3.1 MB gzipped). It is now 3.2 MB (1.2 MB gzipped): trunk's `rust` link with `data-wasm-opt` in `index.html` and a size-first release profile (owner decision 11-18).

### Security
- The erasure log's skip flag (`brim.erasing`) counts only when the owner's purge or restore set it (migration 4056: an owner-only marker per transaction); a role that set the flag itself had its grant deletes left out of the log, so a later restore brought them back. The bot also clears the dashboard's and the MCP role's own `ALTER ROLE ... SET` defaults at every start, so the MCP role cannot keep its read-only default turned off.

### Removed
- Tickets: access roles are removed (owner decision 11-15). Only the server owner, Extra Owners, Trusted Admins and permits with Manage Tickets handle tickets. The default Admins and Moderators permits get Manage Tickets, in Auto Setup and for existing servers (migration 3931). The `accessrole`, `modrole` and `supportrole` commands are gone. A role from an old access list keeps its view of the Tickets category until staff remove it there.
- Ban Sync is removed from the bot, the dashboard, MCP and the security score (owner decision 11-13). Bans already copied stay as normal bans. Migration 3924 removes queued Ban Sync jobs. `ban_sync_links`, its MCP view and the handover's `ban_sync_was_on` stay one release so an image rollback keeps the owner-change protection; a later migration drops them. An old export that still has a `ban_sync` section imports without it. The Raider List and the owner-change protection  stay.

### Fixed
- Dashboard Overview: leaving the page while its settings request failed could stop the dashboard with a "reactive value has already been disposed" error; the page now checks that it still exists first.
- Tickets: a plain message in a ticket channel is sent to the member only when its author has a Manage Tickets permit or an access role. Others get a short refusal (T-01).
- Tickets: the dashboard's ticket transcript needs a Manage Tickets permit or Admin level (was Viewer), and only files in a channel the server used as its ticket log are shown (T-02).
- Tickets: a ticket is marked closed only after its log is saved and its channel is deleted. A second close says the ticket is already closing, and `closeall` skips tickets that are closing. A close cut off by a restart is checked after 15 minutes: the ticket opens again (staff are told) or is closed when its channel is gone. A channel staff deleted during the close no longer leaves the ticket open. Migration 3930 (T-03).
- Tickets: a ticket that a restart left half opened no longer blocks the member's new tickets in that server for ever; it is dropped after 10 minutes. A ticket whose channel was deleted while the bot was offline is closed at the member's next DM, which asks them to send it again (T-04).
- Tickets: turning the ticket log off now says that closed tickets are deleted with no copy of the conversation, and the dashboard says it beside the log channel (owner decision 11-15).
- With anti-nuke off, a permit role given by someone who is not an Owner, Extra Owner or Trusted Admin is still taken back; nobody is punished.
- A role with only weak permits (cases, reports, notes, tickets, mod stats, word, link and report whitelists) given by someone who is not an Owner, Extra Owner or Trusted Admin is now taken back too, with anti-nuke on or off. Nobody is punished. Bots get no exception, so reaction-role and level bots can no longer give roles that carry a permit. The take-back is logged at most once per 10 minutes for the same person and roles, with a count of the repeats.
- Dangerous permissions (Administrator, Manage Roles, Ban and the rest of the dangerous list) come only from an Owner, Extra Owner or Trusted Admin (owner, 11-15). Giving them to any role, creating a role with them, giving a member or a bot a role with them, or adding a bot whose own role has them is undone by anyone else, also by a bot and a permit with the `antinuke` whitelist flag; the bot's own role is emptied. With anti-nuke on the actor (the adder, for a bot) is quarantined and their recent actions are reverted, which also removes an app they added; with anti-nuke off nobody is punished. This no longer needs Strict Mode or Strict Member Role Addition, which now change nothing; Monitor Public Roles only keeps the main roles to the owner and Extra Owners.
- With anti-nuke off, the quarantine hold, the lock guard and the permission guards (dangerous grants, channel permissions and vanity URL as switched on) still undo the change and log it. Nobody is quarantined, and nothing is counted. A kick, ban or member edit of a quarantined member cannot be undone, so it is not logged as undone. Roles given to a member who has not verified are taken back and logged. An undo is skipped (and logged) when the role or channel permission was changed again since.
- A mod command with no member target (for example a role mention) no longer replies "All members were warned!".
- A Discord AutoMod rule created or changed by someone without a permit triggers no TommyBot action until an Owner, Extra Owner, Trusted Admin or a dashboard-edit permit changes it. The change is logged. Migration 3925.
- TommyBot acts on a Discord AutoMod rule only while the rule is as an Owner, Extra Owner, Trusted Admin or a dashboard-edit permit approved it, also when the bot cannot read the audit log. A dashboard save, a trusted change in Discord and the bot's own keyword sync approve it. The dashboard's on/off switch approves only when nothing else changed; otherwise it asks to review and save the rule. Rules that exist when the bot starts after the update (or joins a server) are approved once, unless the audit log showed a change without a permit. Migration 3926.
- A server that adds the bot later, or comes back after its data was deleted, gets its Discord AutoMod rules approved once when the bot joins (owner decision).
- While verification holds new members in quarantine, a person with a `verify` permit can verify a member by hand in Discord: giving them a verification role now verifies them as the button does (anti-nuke on or off), instead of the role being taken back.
- With "Use Discord AutoMod" on, TommyBot owns its whole keyword rule in Discord: the roles of permits exempt from the word filter (`words` or `all`) are exempt there too, no channel is exempt, and a change to the rule's exemptions, actions or allow list in Discord is set back. Saving permits syncs the rule.
- A bot listed as Extra Owner or Trusted Admin, or on the quarantine whitelist, gets no Owner-like trust or quarantine-whitelist exemption from it at runtime either; the permit on its own role still counts.

The dashboard (Permits, rollback, import) refuses it with a reason, and refuses when Discord cannot be asked. Every permit lookup (bot and dashboard) skips these roles: the bot reads them from Discord when it joins or starts and on each server update, the dashboard each time it checks permit roles. A permit already on such a role is ignored, and the anti-nuke log says so once. Migration 3927.

### Added
- After anti-nuke stops a nuke, the owner's DM says who was responsible and what was done to them, how many steps were undone, which steps could not be undone (the first 10, then a count) and what cannot be undone (kicked members to re-invite, deleted channels or roles with no backup, roles from an older backup without dangerous permissions), with the case and nuke id. The anti-nuke report log lists the same failed steps. This DM has its own limit of one per server per minute, so a panic or raid alert just before no longer hides it.
- Invite Tracking commands: `/invites show`, `top`, `who`, `status` and `create`, also as `t!invites`. Anyone sees invite counts (members invited, still here, left), with a note when tracking is off, not working, or recent joins could not be tied to an invite. The leaderboard is public unless Misc > Invites says otherwise. `who` and `status` need the View Invites permit (or Owner, Extra Owner, Trusted Admin); the invite code shows only in the private slash reply. `create` makes a unique link that counts for the member, only when tracking works, no join lock is on, and the member and TommyBot both have View Channel and Create Invite in the channel; at most 3 working links per member and one new link per 15 minutes. The slash reply shows the link privately; `t!invites create` sends it by DM and never posts it in the channel. The four Invites settings are on the dashboard's Misc page.
- A banned or quarantined member's `/invites create` links are deleted, so they let nobody else in. A join quarantine (not verified yet) keeps them.
- Anti-nuke watches seven more actions: app additions (on by default; the app is removed, which also kicks its bot), app removals, emoji and sticker creations, soundboard sound deletions, scheduled event creations and server name or icon changes (all opt-in). Created emojis, stickers and events are deleted, and the old server name and icon are put back (the name and icon from before the first change, even when the changes are reverted in several steps). App removals and soundboard deletions cannot be undone in Discord, and the anti-nuke report says so. The Revert Center undoes the new actions too, and the setup wizard has "Monitor app additions".
- Anti-nuke watches mass voice disconnects and moves (opt-in dashboard cards "Voice disconnects" and "Voice moves", 10 a minute or 30 an hour by default). Discord merges these into one audit entry whose count grows with no new event, so after the first one TommyBot rereads the audit log on voice changes for 10 minutes and counts how much the entry grew. An entry made before that watch began counts only from then on, so moves spread over the minutes before are not counted at once. Voice disconnects and moves cannot be undone in Discord, and the anti-nuke report says so.
- Join Raid has a Voice Raid card (off by default): when 8 different members join voice within 10 seconds, everyone who joins voice for the next 5 minutes, and the members who started it, is disconnected and gets the card's action (a 10-minute timeout by default; Log, Warn, Kick and Ban are the other choices). Staff with any permit, bots and members on the Auto Mod spam whitelist are never flagged. Moving between channels is not a join, and one member joining again and again counts once. Reaching the count again during a raid extends it, and the new end survives a restart. The trigger and the report go to the Join Raid log, the trigger pings Join Raid's Warned Roles, the owner gets a DM, and the Full Raid Report page lists the members under a `voice-` code. The settings are also in `t!joinraid` (row 10).
- Security score row "Emojis, stickers, sounds and events" (Warn): @everyone, the main roles and Moderator roles that are not also Admin roles should not create or manage emojis, stickers, soundboard sounds or events (Discord gives @everyone Create Expressions and Create Events by default). Managed roles and roles above the bot are left out. **Strip permissions** on the Overview takes a backup and removes only those four permissions from the listed roles.
- NSFW image scan (Filters > NSFW, off by default). Posted images, link previews and GIF previews are scored by a small model that runs inside the bot, so images never leave the server and are never stored. A hit counts as NSFW heat (like an NSFW link), so the filter's action or the strike system decides, and the message is deleted. The Automod log gets the scores with **Not NSFW** (that image is allowed in the server from then on) and **Correct** buttons for anyone with the purge permit. Age-restricted channels are skipped. When the scan is turned on, and after a restart, the last 24 hours are read too; new posts always go first. Score threshold 50 to 99% (default 80%). MCP tool `nsfw_scans` shows the score spread for tuning. Migrations 3800 and 3801.
- Web verification can block VPNs and proxies (Verification, off by default, Web mode only). The visitor's IP is checked against free public lists of Tor exits, VPN ranges and hosting networks that the dashboard downloads every 12 hours; the check never stores the IP or sends it anywhere (Cloudflare Turnstile, when its keys are set, sees it as on any site that uses it). Hosting networks have their own switch, on by default. A refused member is told to turn the VPN off, and the Verification log says which list matched, at most once per member every 10 minutes. A broken or poisoned list download is refused and the old list kept; until a first list has loaded, nobody is blocked. Prefix rows `v 15` and `v 16`.
- Sticky roles (Miscellaneous, off by default): a member who leaves and rejoins gets their roles back, so leaving no longer sheds a Muted role. Roles that are managed, not below the bot, dangerous, a permit role, the Quarantine role or on the "never" list are skipped, a ban forgets the roles, a member who has to verify gets them after verifying, and roles of members who left are deleted after 30 days. - Auto-dehoist (Miscellaneous, off by default): symbols at the start of a name are removed on join and on every name change. Only the owner and Extra Owners are skipped. - Auto slowmode (Auto Mod, off by default): every message's heat also goes into a pool per channel. When the pool reaches 300% of max heat, the channel gets a 5 second slowmode, and the slowmode it had before comes back once the pool stayed under half the trigger for 2 minutes (at least 1 minute on by default; the setting takes 10 seconds to 1 hour). It only raises a slowmode, skips threads, spam-whitelisted channels and channels under a lockdown, and does not count bots, webhooks or members with server-wide Manage Messages, Manage Channels or Administrator. `/slowmode` ends it, and a slowmode staff set in Discord is left as it is when it ends. Settings on the dashboard, in the wizard's anti spam card and in `heat` panel group 11. Logged to the automod log. Each member adds at most max heat to a channel's pool, so 300% always takes at least three members and one member can never slow a channel alone, however heavy their messages are. The trigger is at least 200%. Changing max heat or heat degradation starts the pools over. #187 removed the Minimum Members row, so `heat` rows 11d-11f became 11c-11e: `heat 11c` now sets the slowmode length. (#176, #187)

### Changed
- Only users can be Trusted Admin, Extra Owner or on the quarantine whitelist (owner decision 11-13). The dashboard (Permits, the anti-nuke section, rollback, Keep after an owner change), MCP and `t!` (`statics 10`, `t!whitelist`) refuse a bot account, and refuse when Discord cannot say if the account is a bot. Bots already on these lists are removed when the bot starts (GuildCreate), as one config version, logged in the anti-nuke log and told to the owner by DM. A bot gets a bot permit instead: a normal permit on its own bot role, with exactly the exemptions you pick.
- Auto slowmode sets at most a 2 minute slowmode (was Discord's 6 hours), since it is only meant to calm a flood for a moment. A stored longer value is read as 2 minutes. `/slowmode` still goes up to 6 hours.
- Mentions auto lockdown: each member counts for at most about a third of the trigger count (17 of 50), so locking the server takes at least three members. One member's mass mention no longer locks everyone out; the mentions filter punishes it. With Anti Spam or the mentions filter off, or for a member whitelisted from it, mentions count in full as before. (#187)
- Channel Setup is rebuilt around the server's channel tree and replaces role profiles. Make, rename, move and delete categories and channels, and limit who can see one to some roles plus staff (the Admins and Moderators permit roles, which owners can leave out). Channels follow their category; a channel with its own settings is marked and keeps them when the category changes. Every change is a draft until Push, which checks what the draft changes with the security score's channel rules, refuses an unsafe change (with a Fix), and takes a backup. Problems elsewhere on the server stay on the Overview, which now also flags channels the quarantine role can see (with a Fix) and an unpushed Channel Setup draft that is not safe. Only the owner and extra owners can change channels and Push (with 2FA); trusted admins can view the page. Old role profiles are ignored, and old settings exports still import. (#166)
- `/revert` and the Revert Center leave out what an Owner, Extra Owner or Trusted Admin did; only an Owner or Extra Owner can include it. Saving the whitelist panel and adding Trusted Admins in Discord need a fresh dashboard 2FA step-up (account menu › Confirm 2FA). (#146)
- Permission checks are tighter: slowmode and lock refuse other servers' channels, unlocking needs the permit for each lock it lifts, releasing a quarantine checks the roles it gives back, a member cannot verify out of a non-join quarantine, verification never gives a permit role or a role with dangerous permissions, nobody can unwarn, close or edit their own case or an immune member's, and only owners can change anti-nuke whitelist flags or see the rescue key. (#146)
