# Design system files

The dashboard's colours, spacing, corners and font stacks come from the Brim design system
(the owner's design system artifact). These files are copies of it:

- `tokens.json`: the artifact's `project/tokens.json`, unchanged.
- `bundle.css`: the artifact's `project/components/bundle.css`, unchanged. Its classes all start with `tb-`, so they do not touch the dashboard's own classes.
- `tokens.css`: generated from `tokens.json`. Run `node tools/design-tokens.mjs` after you copy a new `tokens.json`. CI fails when it is stale.

`index.html` loads `tokens.css`, then `bundle.css`, then `style.css`. `style.css` maps its short names (`--b1`, `--b2`, `--fg`, `--primary` ...) onto the tokens at the top of the file. To change a colour, change it in the design system, copy the file here and regenerate. A new colour goes into the design system first, not straight into `style.css`.

## Rules follow the pages

A change to how a dashboard page looks or is laid out updates these rules in the same PR (this file, the shared tokens, `tools/ui-sizes.mjs` where a rule can be checked), and the design system artifact is brought in line (owner decision, 2026-11-20). A PR description says which rule it touched, or that none applied.

## Pages

- A page shows its settings as cards. There is no row of buttons that only scrolls to a card of the same page; a control that switches content is a tab (Channel Setup, Tickets) and shows only its own content.
- Server cards (Servers page): the server banner if Discord sends one; otherwise the server icon zoomed in and blurred so it fills the card as soft colour (the one allowed blur besides Loading dots), with the sharp round icon centred on top; no icon: plain grey surface with the initial in a circle. The card button ("Add to server") is always one line, fixed size, right of the name; only the name shortens.
- A hidden element is hidden (`[hidden]` always wins over a class's `display`).

## Screen scale (owner decision, 2026-11-20)

The dashboard grows with the screen. One rule at the top of `style.css` sets `zoom` on the app's box (`#app`, not the page root, so a password manager's button lands on its field) from a number `--z` that steps with the window width: 1.05 on a phone, 1.1 from 900 px, then 1.2 (1800), and 1.25 from 1920 px up (it stops there). Text, cards, controls, sidebar and the 1200 px page column all scale together, so every size in this file is the size at scale 1; on a 1920 px screen they are 1.25 times larger. From 2300 px the extra width goes to columns, not to size: every page widens to 1600 px (one `--w-wide` on `:root`, the same for every page and state), from 3200 px to up to 2300 px; Cards get 3 columns, then 4; the two `.col` boxes dissolve and the cards flow down the columns in list order. Media queries read the real window, so the phone and desktop layouts switch where they did. Rules: (1) never set `zoom` anywhere else; (2) never write a bare `vw` or `vh`, because the browser does not zoom them: use `calc(N * var(--vw))` and `calc(N * var(--vh))`; (3) code that places something from window coordinates (popups, tooltips) divides by `screen_zoom` in `common.rs`. `tools/ui-sizes.mjs` checks the first two. The design system artifact needs the same rule before a new copy is taken from it.

## Spacing rule: 4 px

Every spacing in the dashboard (margin, padding, gap and offsets such as `top` or `left`) is 4 px or a multiple of 4 (owner decision, 2026-11-20). Use a `--space-N` token (`space-4`, `space-8`, `space-12` ...); a raw px value is allowed only if it is also a multiple of 4. The sizes of boxes, fonts, borders, radii and `em` values are not spacings and may vary. `--stroke-2` is the width of a border, outline or ring, not a spacing. `node tools/ui-sizes.mjs` fails on a spacing that is off the grid. Since 2026-11-20 `tokens.json` and `bundle.css` differ from the design system artifact on this point: the artifact must get the same change before a new copy is taken from it.

## Text sizes: five (owner decision, 2026-11-20)

The dashboard uses five sizes: `page-title` 44 px (32 on a phone), `figure` 26 px, `section-title` 18 px (section and card titles, the crumb line, the server name, the brand name), `ui` 14 px (body text, inputs, buttons, toasts) and `caption` 12 px (help lines, captions, chips, table headers, code and IDs). Old 17 and 19 px fold into 18, old 15 and 16 into 14, old 11 and 13 into 12. `tools/ui-sizes.mjs` fails on any other `--fs-*` in `style.css`. The landing page's own types (headline, lead, ...) are outside this scale. Heading weights are not changed yet.

## Universal page layout (approved 2026-11-20, being built in steps)

Every module page has the same frame: header (crumb, big title, "?"), tabs if any, notices, then content in one centred column of `--w-wide` (1200 px) for every page; lists, tables and the How it works box fill it. Detail pages extend the crumb; there is no back button. Content is a cards grid (two columns from 900 px, one below; cards flow in two columns and move up under the card above, no gaps), a stack, a table card, a sortable list, or a workspace (Channel Setup and the message editor are the declared exceptions; Channel Setup's reorderable rows still use the sortable-list look). Rhythm: 24 px between blocks, 20 px inside a card, 12 px between rows. Delete lives in a row's Edit dialog. Plan and pictures: in the data repo. Steps built so far: 1 (text sizes), 2 (page column 1200 px / `--w-narrow` 900 px as tokens in `style.css`, 24 px between blocks, 20 px card padding; `tools/ui-sizes.mjs` fails on any other page-wide `max-width`), 3 (every header is `Head` and every tab row is `PageTabs`, both in `common.rs`; tabs are an orange underline row, not a pill box; a detail page extends the crumb with its parent instead of a "Go Back" button; `tools/ui-sizes.mjs` fails on a hand-written `class="head"` or `class="tabs"` and the e2e sweep checks the open tab's underline), 4 (cards grid: see below; every add button is `AddButton`; number steppers are small circles), 5 (table card: see below), 6 (custom pages: see below).

## Controls (owner decision, 2026-11-20)

- **Add button:** a green pill with a circle plus and a text naming the thing ("Add new permit"). No bare "+", no grey "+ Add", no dashed wide button.
- **Help text (owner decision, 2026-11-22):** the small grey explanation of a setting or field goes behind the info icon (`Tip` in `common.rs`) next to its name, never as a grey line under it. `Field` does this for every schema setting. Status lines, counts, time stamps, empty-list notes, errors and loading words stay visible. A warning that must be read before a risky action keeps its full text in the pop-up.
- **The picker is universal (owner decision, 2026-11-22):** every field that takes a channel, a role, a category or a member uses the shared picker (`ListPick` in `form.rs`: opens a list on click, search as you type; members: `UserPick`). Never a plain text or ID box, a native `<select>` or a `<datalist>`, and no own variant. Why: one control that looks and works the same everywhere, and nobody has to type or paste an ID. The only exceptions are the Appeals list filter ("User ID/tag", a search of past records, not a setting) and the time zone box in `msgrules.rs`. `tools/ui-sizes.mjs` checks it.
- **Round buttons:** an icon-only button is a perfect circle (square box, radius 50%). A button with text is a pill.
- **Tabs (fixed by the owner, must not change):** one quiet row, no pill box; the open tab has an orange underline; never wraps, scrolls sideways when it does not fit.
- **Sortable list:** rows in a card (`.slist` / `.srow` in `style.css`, `Grip` in `common.rs`; Permits). The whole row is the drag target with a mouse; three grey three-line marks (25% opacity) on the left say it can be moved; the dragged row lifts with an orange outline and an orange line shows where it lands; the focused row moves with the up and down arrow keys, keeps the focus and a screen reader hears its new place; a fixed row shows a lock and does not move. On a phone the drag starts from the three lines (`.touch-grip`, a 40 px zone; provisional, owner decision "yes for now": ask him once whether to keep it). Up, down and Delete buttons are not used on the row: Delete is in the row's Edit dialog. Channel Setup keeps its own tree and row menu but uses the same grey lines and the same lift while a row moves. Exception (owner, 2026-11-23): the saved messages list shows no grey lines; it looks exactly like the Default messages list (`HubRow` rows), the whole row drags with a mouse and the arrow keys move the focused row.
- **Outlines:** orange outline (`--ol-pick`) means selected or being moved; hover on a clickable or movable row or card is a quiet grey outline (`--ol-hover`). Both are defined once in `style.css`; every sortable or selectable row (Permits, Channel Setup, the saved messages list) uses them, no own colour.

- **Cards grid (owner decision, 2026-11-20 "no empty spaces"):** settings cards sit in two fixed columns from 900 px (one below), each card right under the card above it, 24 px apart. `Cards` in `common.rs` keeps the list order (left column top to bottom, then right) and splits it so both columns are about equally tall. It is not CSS columns or a grid: a card that grows when a switch shows more rows stays in its column. `tools/ui-sizes.mjs` fails if `.cards` becomes a grid again.

- **Table card:** every table is `table.data` inside a card: one header row of small muted 600 text, 12 px cell padding, a grey line between rows; a button column is `.tact` (right aligned; not `.act`, which is the settings card action row). On a phone (600 px and below) each row becomes a block: the first cell on top, then the other cells in two columns, each with its column name from `data-label`; buttons take the full width. A grid of cells (Channel Setup's Advanced grid) is `table.data matrix`: same header and row lines, but it stays a table on a phone and scrolls. Empty tables show one muted row or line, never a second add button: a page has one add button (Permits: "Add new permit" at the top, also with no permits of your own). `tools/ui-sizes.mjs` fails on a `<table>` without class `data`.

- **Custom pages (step 6):** the hand-built pages use the same patterns. Home is two cards grids (Setup Wizard and Overview, then the task cards), no own 900 px grid. One backup is its own route (`#/<server>/backups/<code>`, crumb "Backups › Backup #code", the code is the big title) with its Load and Delete buttons on the right and its Channels and General Settings cards in the cards grid; no "Go back". Commands keeps all its text and the list in one narrow column. Pages checked and left as they are because they already fit: Overview (see "Overview" below), Tickets, Cases, Notes, Update, MCP tokens, Data requests, Saved messages (the editor is the declared message-editor exception).

Built: Add button (`AddButton` in `common.rs`, also inside `Empty`; `tools/ui-sizes.mjs` fails on a button text starting with "+" or a dashed button), round number steppers, cards grid, table card. Built in step 6: the custom pages above. Built after step 6: sortable list (Permits) and outlines.

## Bot messages

- An entry with a required placeholder (`{text}`, "Bot text") shows one notice at the top of its editor: yellow while the placeholder is in the first embed, red with an "Insert Bot text" button when it is not. The notice says what Brim puts there. The save is refused while it is missing.
- A short reply (one sentence, like "You are already verified.") is an entry of its own, named "Reply: ..." and listed in the group of its area. Its default is message text with no embed; it has no required placeholder.
- A list row whose edited version has no required placeholder carries a red "Needs Bot text" chip next to "Edited".

## Feeds page (feeds plan F1, 2026-11-20)

- A list page in the page column: one row per feed (a card-like row: on switch, source icon, name with a "Stopped" or "Paused" chip, details line, ⋮ menu). The ⋮ menu holds Send latest, Edit message and Delete; Edit is a button at the right end of the row; it is a round 40 px button. The menu look is the Channel Setup row menu (`.rowmenu`).
- Above the list: the limit counter ("3 / 10 feeds"), the per-channel limit, a sort control (Name, Channel, Last post) and the "Add new feed" add button (`AddButton`). An empty list shows one card with what to do first and the same add button.
- Add and Change open one dialog: source (RSS / YouTube / GitHub / GitLab), address, channel, ping role, and a folded "Name, picture and sender" part with the "Send as Brim" switch (off by default).
- Edit message opens the message editor on the feed's own version, with "Own version" or "Server's version" and a "Use the server's version" button.
- GitHub and GitLab feeds: the dialog has no address; it shows one switch per event type in a framed group ("Post these events"). After Add, a setup window shows the steps, the address and the secret (blurred until Show) with Copy buttons; the secret is shown only then. Their ⋮ menu holds Turn on again (only when stopped), Show setup, Make new secret, Send latest (it says that a webhook feed cannot fetch), Edit message and Delete. Edit message has an Event picker above the editor: each event has its own message.
- The required placeholder notice of the Bot messages editor names the entry's placeholder: `{feed_link}` for feed entries, which may sit in the message text (their default is the plain link), `{text}` for the others.

## Bot Profile page (owner decision, 2026-11-20)

- One panel in one card: images left (avatar and banner tiles you click to upload), fields in the middle (bot name, bio, bot status, activity type, status text), a live member list preview and profile preview on the right. Two columns below 1200 px (previews under the fields), one column on a phone. The change history is a folded "Recent changes" box under the panel.
- One "Save changes" sends only the fields that changed, one after another, and stops at the first refusal with what was saved. It is off while nothing changed. "Reset to default" removes this server's name, bio, avatar and banner; status and activity stay.
- Name, bio, avatar and banner are per server. Status and activity are bot-wide: everyone on the page sees them, only the bot's owner can change them (greyed out for others, with a line that says so). This page is the only place to set them; the Update page has no status card.
- Not tied to one bot account: the page shows the name and images the server sends, never a fixed bot. If one server ever runs under its own bot account (own token, not built), only the server side changes: which bot sends the profile change, and where that bot's status is kept. No token is stored for this page.

## Front page top section (owner decision, 2026-11-20)

The front page opens with a hero (`.hero` in `landing.rs`, rules in `style.css` under "Hero"): steel and copper drawn in CSS and one inline SVG, not from a picture, so it fits any width. "Brim", the slogan and the two main buttons are text on the left; the Brim mascot (`assets/mascot/brim.svg`) is on the right and above the text on a phone. There is no glow behind Brim. The section ends in one full-width copper line (version A, class `line`); removing the class gives version B, a long fade into the page colour. Below it the page keeps the normal dark colour. The hero's colours and its two big type sizes are custom properties at the top of the `.land` rule; they belong in the design system when it is next updated. No animation.

## Front page feature area (owner decision, 2026-11-22)

Below the hero, each feature block (`SECTIONS` in `landing.rs`, rules in `style.css` under "One layered group per scene") has a gradient title ending in a full stop, a list of plain text lines with a marker, and one stage. Clicking a line switches the stage to that line's scene. The switch is a cross-fade: the old scene fades out while it moves down 48 px, the new one fades in while it moves up into place, 300 ms, linear. Both scenes keep their own layer (`will-change`), so the last frame of the motion is pixel for pixel the resting frame.

- **Colour.** `--orange-grad` is the one orange gradient (`linear-gradient(135deg, #ffc27a, var(--accent) 55%, #d4581a)`, defined on `.land`). It is for large headings, the active marker and the effect shapes; never for body text. Every shape shows a slice of this one token (`--gp` moves the slice), not its own colours. `--brand` (the four-colour logo and score-ring gradient) is only for the logo, the score ring and the setup progress bar; do not use it on the front page feature area. No colour glow behind a piece, no tilt, no transparency. `--orange-grad` stays on `.land` in `style.css`: `tokens.json` is an unchanged copy of the external design system, so the token is pending in the external design system.
- **Stars are the only effect.** The effect shape is the four-point star (`--star`), defined once as a custom property on `.land`: a mix of filled and outline stars (outline = the page colour inside a thin gradient edge), each with an orange glow (`drop-shadow` in `--accent`), in a big (32 px) and a small (24 px) size, scaled with the scene. A block has six places, in three pairs: left of the group, above the second piece, and under the first piece beside the third; a seeded random (`effects` in `landing.rs`) hides 0 to 2 of them, so a block shows 4 to 6, the same on every load. Stars are fixed in the block's box and are the same for every scene of the block, so they never move when a scene switches. They lie in front of the pieces (`z-index` above them), may lie a little over a button, and never over text a person has to read. Why: the reference page has no other effect, and a fixed place makes the stage calm. Choose the places so that any scene of the block passes: `fit` measures the groups and `landing.rs` has a check over all scenes that finds no star over text. The list marker is the shield (`--shield`): outline when inactive, filled with `--orange-grad` when active. No hexagon, no hat, no other shape, no particles, no glow behind a piece.
- **What a scene shows.** A scene shows what Brim does, as one small story, not a settings page: something that happens (a member's message, a raid, a rogue admin), Brim's real reply (`E`, a sample from `/api/previews`), and a real dashboard view that is not a settings card as the main piece. Real views: Cases rows (`K`: number, kind, open or closed, member by moderator, reason, proofs; one of each real kind from the code: ban, kick, timeout, warn, quarantine, slowmode, purge), action and member logs (`T`), incident lists for anti-nuke (`K`), the Raider List, History and Backups rows (`L`), tickets. A settings card (`P`) is the last choice and small; a scene that can be told without one has none. Why: owner decision 2026-11-22/23 \"we aren't showing anything other than settings, it's boring\"; the reference shows one idea per picture, not a form.
- **Alone or split.** A view that is strong on its own may stand alone as the one large piece of its scene: the message builder is the real editor (Title, Description, Field name, Footer text, Add field, Add button row) beside its live preview, two pieces and no third. A view may also be split into the thing and its detail: Channel Setup is the channel tree as the page draws it (Information, Text Channels, Voice Channels, Logs, Staff, with the access each has under the standard layout Auto Setup and the Overview Fix build) beside the \"Who can see this\" panel with the real levels. Pick per scene what looks best; do not give every scene three pieces.
- **Content comes from the code.** Case kinds, channel and category names, levels and labels are read from the code on main, never from memory. Member and staff names are made up (Mika, Sam, Lee, Jo) and there are no real Discord ids or real member names anywhere in the repo. Numbers (limits, durations, counts) are plausible, not claims.
- **Readable.** No piece hides another piece's text or controls. A row is one line (no wrap) and short enough to show next to the piece in front of it; a member's message sits behind Brim's reply and is narrow enough to wrap in the part that stays visible. A long report ends at a whole block (below), so its first meaningful lines show. Check a scene by looking at it, not by the code (see Process).
- **Scene layout.** One layered layout for every scene, the proportions the owner approved (measured from a reference page and then fixed in his layout editor): the first piece sets the size; the second lies 84% of the first one's width to the right and 31% of its height down (a 16% overlap across); the third lies 23% in and 88% down (a 12% overlap down). A message (Brim's reply) is in front of the other pieces; a member's message (`.mm`) is behind it. The scenes of a block all start at the same corner of the union of their groups, and the block has one fixed box (784 px wide, as tall as the tallest group plus 48 px above and below, centred), so the lines and the page never move when a scene switches. A phone (760 px and below) stacks the pieces full width in the same order, the big orange label (`C`) is hidden, and the box is 392 px. All pieces are straight (0 degrees, no tilt) and solid (no transparency, no fade, no mask). A long message ends at a whole block: fields go from the end (name and value together, an inline row as one), the first stays, to about 1.3 times the first panel (at least 280 px); no fade, no half line. Pieces: `M` member message, `E` Brim's message, `K` Cases rows, `T` log rows, `L` list card, `P` settings card, `C` the big orange label that names the result (Ban, Stopped, Logs).
- **Real settings only.** Every card title, setting label, option and button a scene shows is one the dashboard itself shows (from `schema.rs`, the wizard cards or the page source), written the same. The test `landing::tests::scenes_name_real_settings` fails when one is missing. Sample values (names, ids, times) are not settings.
- **Hover.** Nothing happens when the pointer is over a piece: no lift, scale, glow or cursor change. A list line goes from grey to white on hover; the active line is white with the filled marker, and the small arrow beside it fades in over 0.2 s (the shorter fade). The weight of a line never changes. The marker star's outline fades to white with the text (no glow, no fill); only the selected line is filled with the glow. The big buttons do not lift and show nothing on hover or when pressed (owner decision, 2026-11-23); the button only presses to 97 % at the click. Footer links only turn white.
- **Switching.** A click on a line fades the old scene out while it moves down 24 px and fades the new one in while it moves up into place, 0.3 s, `opacity` and `transform` only, inside the stage; it never moves the page: no scroll, no focus jump, no zoom, no recentring. It runs at 60 fps. The stage is as tall as the tallest scene of its block (`--sh`, set by `fit` in `landing.rs`), so the lines and the page stay still.
- **Motion.** The stars stay where they are, in the fixed box of the block, while scenes switch (static places); they are still, upright, with one static glow (owner choice 2026-11-23; the twinkle is kept for later). Page motion is always on: there is no switch and the system setting does not stop it. Only `opacity` and `transform` animate, so it runs on the compositor like the loading dots.
- **Content.** Embeds are the real default messages from `/api/previews` (public, one source of truth), so a changed default changes the page. The bot test `previews::front_page::scenes_name_real_samples` checks that every scene names a real sample. Numbers may appear (limits, durations) with varied, plausible values; they are not precise claims or statistics. On a phone (390 px) the pieces stack full width at readable sizes (embed text about 12.6 px, chips about 11 px).
- **Turf (owner decision 2026-11-22, "for now").** Every feature heading has a connected turf under its first letters: one shape (`--turf`, set with `--star` and `--shield` on `.land`), filled with `--orange-grad`, solid and static. Its flat top sits just under the baseline with a small gap and the blades hang fully below the letters. When one of the first four letters has a descender (g, j, p, q, y) the heading gets class `deep` and the turf hangs lower, so it never touches a glyph. It takes `--space-20` below the heading and does not push the lines.

## Emojis and icons (owner decision, 2026-11-22)

- The 306 emoji pictures (`assets/icons/<name>.svg`, 128x128, checked by `node tools/emojis.mjs check`) are static, with one orange gradient from left to right (`x1=16`, `x2=112`, one `<name>-grad` per file). The 29 pass, fail and caution pictures run from orange into green, red or amber instead of rust. No animation, no second effect. Why: one calm look in Discord and in the dashboard, and the colour says the result before the word does.
- The dashboard draws the same pictures through `icon` in `icons.rs`. An icon on a coloured button (a green Load, a red Delete) must stay readable: draw it in the button's text colour, not in its own gradient, so orange on green or red never happens. Check the real button in the browser, in both a green and a red state, when you add an icon to a coloured button.

## Overview (owner decision, 2026-11-22)

All modules are cards on the Overview, in `pages.rs`: the five systems first, then Moderation, Tickets, Messages and Logging (`MODULE_CARDS`). Each card has the module's name, one line, a Settings link and the same on/off switch as the left menu. All cards have the same size (every row as tall as the tallest) and sit 5 to a row on desktop; a short last row stays in the middle. At 1200 px and below two cards sit in a row, and on a phone (600 px and below) the cards are one column. Why: every module is one click from the score and none is hidden in the menu. After a switch changes, the score checks load again.

## Loading (owner decision, 2026-11-22)

Every loading state uses the one `Working` indicator (`common.rs`): four dots in the logo colours that swap corners, and a made-up fun word (`fun-words.md`). A button that waits shows it in place of its label (`busy_label`). No spinner, no bare \"Loading...\", no own variant. Why: one recognisable sign that Brim is working, and the wait is a little fun.

## Modules (owner decision)

A module's setup is simple: one on/off switch, a few clear fields, and defaults that work without any change. A message Brim sends is edited in the visible message builder (the embed editor with its live preview), never in a plain text box. A setting that most servers never touch is folded or left out. Why: the person is a server owner, not an engineer, and a fresh server must be safe on the first switch.

**Showing a message (owner decision):** every message Brim posts is shown the same way, by the one shared `embeds::split`: the editor on the left and the live preview on the right, both open, both cards the same height; on a phone the editor comes first and the preview below. A click on a part of the preview edits that part in the editor (it is not a second editor). The phone preview sits beside the desktop one only when both fit, else the Desktop/Phone switch stays. Several messages of one place (for example the four giveaway messages) are one tab row, the shared `PageTabs`, above the editor. Outside the Messages pages the same editor opens in place, with a button to the full editor for more tools. A new place that shows a message uses this component and adds no layout of its own.

## Look rules that apply everywhere

- Orange is one gradient (`--orange-grad`) and the accent colour; there is no second brand colour. Effects are stars only. The star is the list marker (orange outline idle, white outline on hover, filled with the static glow only when selected). No tilt, no transparency, no blur (the Servers page is the one allowed blur besides Loading dots). Every feature heading has the turf under its first letters (see above) for now.
- Nothing is called by another bot's name in the repo (code, comments, docs, UI, commit text); describe the behaviour.

## Process for visual work

1. Look at the reference in a real browser first (a saved copy of the page; the reference is never named in the repo) and write down what it does: how many pieces, how big, what moves.
2. Show one block, side by side with the reference, before you do all of them. Fix what the owner says on that one, then do the rest.
3. Look at your own result in a browser at desktop and phone width before you report it. A script that finds no star over text is not enough: look at the picture.
4. A change that alters the page flow updates `tests/e2e/dashboard.js` in the same change.
5. This file, `PITFALLS.md` and `MAP.md` change in the same commit as the page.

## Brim poses (2026-11-21)

Twelve poses of Brim, `assets/mascot/poses/<name>.webp` (384 px on the long side, about 20 KB each; originals in the private data repo), shown with `Pose` and the `Brim` enum in `common.rs`. Each pose means one thing and is used only there, beside text that says the same; it is decoration (`alt=""`). The list with each rule is on the style page `#/ui` (`Brim::rule`). Sizes are set by `--pose` in `style.css`: 80 px beside a page title (hidden at 1200 px and below), 104 to 112 px in an empty or error card, 88 px in a dialog, 40 to 56 px in a toast, search list, button row or the menu.

- On Guard: Anti-nuke, Anti-nuke filters, the panic pages (title). Stop: No access, wrong 2FA code. Pointing Right: empty lists (`Empty`). Pointing Left: the wizard's first step, at Auto Setup. Thumbs Up: the big "Saved" toast, the wizard's "All done!". Asleep On Duty: only while Brim is offline or restarting for an update.
